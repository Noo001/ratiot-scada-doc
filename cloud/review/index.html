О протоколе

Объект: RatioT.Cloud_FTT.docx, редакция v004 от 14.09.2026. Основной документ не изменялся — все предложения собраны здесь, одним перечнем. Статус: на согласовании с автором ФТТ. Версия протокола: v2 от 18.09.2026 (первая волна П-1…П-10 — 15.09.2026).

Что нового в v2: ключевое замечание П-11 — платформенная независимость backend (AggreGate как допустимый вариант, а не предписание; раздельная смета «собственная платформа / AggreGate») и вторая волна замечаний П-12…П-21 по итогам сплошного анализа текста ФТТ (3718 строк) с материалами ревью. Вывод v1 «противоречий с baseline, включая backend на AggreGate, не выявлено» по П-11 пересматривается.

Формат позиций: где в ФТТ → что сейчас → что предлагаем (готовый текст, где возможно) → почему → влияние на бюджетную оценку.

Рабочие материалы ревью: полный реестр замечаний (REVIEW_PROTOCOL.md) и проект заполнения раздела 2 (SECTION2_DRAFT.md). На этой странице — согласованная для передачи автору выжимка.

Блокеры: без этого оценка подрядчика неоднозначна

П-1. Раздел 2.1 — таблица оборудования первой очереди

Что сейчас: таблица из строк «ЗАПОЛНИТЬ».

Что нужно: конкретный перечень SKU (производитель, модель, тип, интерфейс, протокол, роль; нужны ли System Device Template и Visual Template; предоставляются ли образец и документация). Зацепки из исходной заготовки — семейство Mitra и приборы ДКС (системный каталог первого этапа — приборы ДКС).

Почему: состав таблицы — база бюджетной оценки; без неё System Library, Device Templates, Visual Templates и испытания неоценимы. Влияние на бюджет: определяет объём (ориентир для обсуждения: 5–15 SKU).

П-2. Раздел 2.2 — конкретное MQTT-устройство

Что сейчас: «Выбранное устройство SKU: ЗАПОЛНИТЬ».

Что нужно: одно стороннее MQTT-устройство и пакет документации (topic structure, формат сообщения, телеметрия, команды, аутентификация/TLS, подтверждения/ошибки, примеры обмена или симулятор). Критерий выбора: доступность для закупки/испытаний, желательно JSON без Protobuf (иначе Protobuf войдёт в объём).

Почему: абстрактный «любой MQTT» неоценим; расширение на иные MQTT-протоколы — отдельный объём. Влияние на бюджет: определяет трудоёмкость профиля MQTT.

Решения для раздела 2 (проекты — требуют подтверждения владельца продукта)

П-3. Раздел 2.3 — подтвердить границу Gateway первой очереди

Предлагаем: отметить «Подтверждаю указанную границу» и добавить в 9.2 фразу:

«Первая поставка принимается на сценарии с одним Device. Протокол Gateway↔Cloud и конфигурационная модель не должны требовать переработки при расширении до нескольких устройств на одном шлюзе; промышленная многоустройственная эксплуатация одного шлюза — отдельный объём оценки по change request.»

Почему: иначе «одно Device» и «архитектурная возможность расширения» читаются по-разному, и второе устройство через тот же шлюз станет неожиданным платным change request. Фраза не увеличивает объём, но защищает архитектурно. Влияние на бюджет: нет.

П-4. Разделы 2.5 и 18.5 — отчёт по наработке моточасов

Предлагаем: отметить «Отчёт по наработке моточасов не входит в первую поставку». В 18.5 остаются два обязательных Jasper-шаблона (потребление ресурсов за период; журнал аварий и действий персонала). Техническая возможность сохраняется: моточасы = вычисляемый параметр через Automation (7.9) → параметр виртуального устройства → архив → типовой отчёт/CSV.

Почему: для универсального IIoT-продукта отчёт не обязателен (журнал решений); снижает scope первой поставки. Альтернатива — включить и расписать содержание (период, группировка по Assets/оборудованию, суммарная наработка и по периодам), тогда в бюджет добавится шаблон и сценарии ПМИ. Влияние на бюджет: не меняет/снижает; при альтернативе — небольшое увеличение.

Правки текста ФТТ

П-5. Финальная вычитка — подтверждённые опечатки

«стандратного» (2.3); «Изенить» в поле решения владельца (2.3); «зависисмостей» (1.3); «ПОльзователем» (11.1); «конфигрурации», «не зависимо» (5.9); «приофиля» (7.7); «лолжна» (21.2); «в рамкахдругих», «техпроцесс процесс» (4.5); пункт после 6.6 — заголовок без номера. Почему: документ уходит на оценку; опечатка в поле решения выглядит как незаполненность. Влияние на бюджет: нет.

П-6. Маркировка обоснований решениями (DEC-xxx, P-00x)

В конец ключевых требований — ссылки вида (DEC-142), (P-003) на журнал решений; минимум разделы 2, 4, 5, 9, 12, 19. Текст требований не переписывается. Почему: ~190 принятых решений сейчас в ФТТ не прослеживаются; ссылки защищают их при будущих правках. Влияние на бюджет: нет.

П-7. Разделы 19.4 / 24.6 / 3.4 — определение «одновременных интерактивных UI-пользователей»

Что сейчас: тарифное поле и NFR ≥500 пользователей; механизм учёта — на ТЗ. Предлагаем: минимум — в 3.4 потребовать от каждого подрядчика в допущениях указать механизм учёта; предпочтительно — зафиксировать до оценки продуктовое определение («аутентифицированная сессия web-клиента с активным соединением; лимит проверяется при установке соединения»). Почему: иначе оценки несравнимы, спор всплывёт на приёмке. Влияние на бюджет: низкое.

П-8. Раздел 23.2 — проверка alarm flood в regression suite

Добавить в области покрытия: «контрольный сценарий с большим числом одновременных таймерных состояний Alarm Rules (TON/TOFF, anti-flapping); параметры — ТЗ/sizing». Почему: Alarm Rules на общем движке с Automation (11.4), квоту экземпляров не расходуют (12.13) — корректно, но при 50 000 устройствах граница по одновременным состояниям ничем не проверяется. Объём не меняет. Влияние на бюджет: нет.

П-9. Раздел 25.8 — хранение Security Audit после удаления Space

Предлагаем: принцип «записи аудита, относящиеся к удалённому Space, подлежат обезличиванию либо удалению по истечении retention; механизм — ТЗ» (либо явный срок независимого хранения с оценкой объёма). Почему: в аудите есть персональные данные; бесконечное хранение противоречит требованиям к ПДн, объём влияет на sizing. Влияние на бюджет: низкое.

П-10. Разделы 3.4 / 22.7 — сравнимость оценок маршрутизации FQDN→Space

Инварианты сформулированы правильно (Space до auth; frontend Space ID недоверен). Предлагаем: в 3.4 — «подрядчик в допущениях указывает предполагаемый механизм маршрутизации FQDN→Space и защиту от подмены tenant». Почему: критичный multi-tenancy механизм, оценки могут разойтись; требование к допущениям делает их сравнимыми, реализация остаётся на ТЗ. Влияние на бюджет: снижает риск разброса оценок.

Платформенная независимость backend — ключевое замечание (П-11)

Что сейчас: ФТТ жёстко фиксирует серверную платформу: «Backend строится на Tibbo AggreGate Server» (1.3, повторено в 1.5, 4.4, 17.1, 24.1); AggreGate — обязательная часть контура поставки и результата проекта (22.2, 27.2, 27.5, 28.2); обязателен блок оценки лицензий AggreGate (3.2); HA — только штатными механизмами AggreGate, собственный failover запрещён (24.1). При этом версия и стоимость AggreGate намеренно не фиксируются (22.5 — «в ТЗ»).

Что не устраивает: (1) смета привязана к платформе, версия и стоимость которой не определены — кластерная лицензия под 50 000+ устройств и HA может стать доминирующей и неконтролируемой статьёй TCO; (2) исключается конкуренция подрядчиков и вариант разработки backend на собственной платформе Заказчика; (3) vendor lock-in — продуктовая функциональность описана через механизмы одного вендора, регрессионные требования привязаны к чужому циклу релизов.

Что предлагаем:

Серверная часть RatioT.Cloud реализуется по одному из допустимых вариантов: (А) собственная серверная платформа, разработка с нуля; (Б) платформа Tibbo AggreGate Server. Продуктовая функциональность (разделы 5–21) не меняется ни в одном варианте. Подрядчик представляет раздельную бюджетную оценку вариантов А и Б с обоснованием рекомендуемого выбора: TCO на 3–5 лет (для варианта Б лицензии AggreGate — отдельной строкой), риски, требования к команде, зависимость от вендора. Выбранный вариант фиксируется Заказчиком до разработки ТЗ.

Сопутствующие правки: формулировки «штатные механизмы AggreGate» → «штатные механизмы выбранной серверной платформы» (1.3 п.5, 4.2, 5.9, 10.5, 10.6, 15.2, 18.1, 22.2, 24.1–24.4, 25.1, 25.2, 25.7, 25.10, 26.1–26.2, 27.2); HA формулируется через обязательные свойства (отказоустойчивость, без очевидных SPOF, распределение Space по узлам) с приоритетом штатных механизмов выбранной платформы вместо абсолютного запрета собственного failover; политика версий (22.5, 23.4, 29.4) — нейтрально: «обновления платформы не должны блокировать выпуски RatioT.Cloud».

Почему важно: продуктовый объём не меняется, открывается конкуренция вариантов реализации и контроль TCO. Что ещё затрагивает: при принятии — пересмотр решений DEC-021, DEC-105, DEC-106, DEC-115, DEC-120 и пунктов системного портрета; перечитываются разделы 14, 16, 20. Влияние на бюджет: меняется структура сметы (два варианта backend), продуктовый объём — нет.

Внешние зависимости и противоречия (П-12…П-18)

П-12. Каналы уведомлений: провайдеры и стоимость не закреплены (11.7, 19.5, 20.7)

Что сейчас: Web Push, E-mail, Telegram, SMS — обязательные каналы, но чей Telegram-бот, какой SMTP и SMS-шлюз (платная внешняя зависимость) — не определено; для SaaS-контура провайдер SMS никем не закреплён (20.7 описывает только On-Premise). Предлагаем: в 3.4 — подрядчик в допущениях указывает внешние сервисы доставки и их эксплуатационную стоимость; в 19.5 — принцип «замена провайдера SMS/SMTP/Telegram не требует изменения Event/Alarm-логики и маршрутизации» (по аналогии с MAX, DEC-140); корпоративные SMTP/SMS-шлюзы SaaS-контура — отдельной строкой оценки. Влияние на бюджет: снижает разброс оценок, делает видимой стоимость SMS.

П-13. Ёмкость Space 5000 параметров vs тарифные лимиты (10.7, 19.4)

Что сейчас: «не менее 5000 Parameters как минимальную целевую ёмкость» при тарифном поле Max Parameters per Space и сетке 100/500/2000. Предлагаем: «архитектура обеспечивает ёмкость до 5000 параметров на Space; фактический лимит задаётся тарифом» — убрать слово «минимальную». Почему: иначе низкие тарифы невозможны, а подрядчик заложит архитектуру под максимум. Влияние на бюджет: без правки — завышение.

П-14. «Шлюз» как источник Событий противоречит протоколу Gateway↔Cloud (11.1, раздел 9)

Что сейчас: 11.1 перечисляет «Шлюз» среди источников Event, но протокол передаёт только телеметрию, команды и конфигурацию. Предлагаем: убрать «Шлюз» из перечня либо явно добавить передачу событий в протокол (расширение объёма). Влияние на бюджет: низкое / небольшое увеличение.

П-15. Состав ежедневного backup, retention и RPO не определены (21.1–21.2, 24.9)

Что сейчас: «полное резервное копирование» (21.1) против «не требуется ежедневный полный дамп телеметрии» (21.2); retention, off-node копия, шифрование и RPO не заданы, а HA-сценарии в ПМИ (29.2) проверять нечему. Предлагаем: ежедневный backup = конфигурация всех Space + БД приложения без сырых телеметрических массивов; retention и off-node копия — ТЗ; целевой RPO (ориентир ≤ 24 ч) — в ТЗ до ПСИ №1. Влияние на бюджет: среднее (сопоставляет оценки).

П-16. Ответственность за альбом UX/UI в Figma (13.5, 28.6, 3.1)

Что сейчас: альбом «спроектирован в рамках этапа ТЗ+UX/UI» и «входит в поставку», но кто производит — не сказано. Предлагаем: зафиксировать дословно: «альбом UX/UI (desktop + mobile) разрабатывается подрядчиком в составе этапа ТЗ+UX/UI (блок 3 оценки по 3.1) и передаётся в Figma как часть комплекта поставки». Влияние на бюджет: определяет принадлежность крупного блока.

П-17. Критерий «совместимая On-Premise инсталляция» для переноса Space (21.5)

Что сейчас: перенос SaaS → On-Premise заявлен, критерий совместимости не определён, модели SaaS и On-Premise различаются. Предлагаем: «совместимая инсталляция = та же major-версия RatioT.Cloud; переносится конфигурационный пакет Space (21.3) со всеми смысловыми ID; тарифные ограничения SaaS заменяются лимитами лицензии On-Premise; пользователи пересоздаются мастером импорта». Влияние на бюджет: сопоставляет оценки.

П-18. Проверяемость NFR и критерии приёмки HA (24.6, 24.9, 29.2)

Что сейчас: числа NFR — «целевые ориентиры», профиль нагрузки — на ТЗ; ПМИ обязана включать HA-сценарии без заданных RTO/RPO. Предлагаем: принцип «каждое число 24.6 имеет критерий приёмки в ПМИ на согласованном профиле нагрузки»; RTO/RPO и режимы отказа узла — в ТЗ до ПСИ №1. Влияние на бюджет: низкое–среднее; снимает спор на приёмке.

Мелкие правки (П-19…П-21)

П-19. Сервисный вход SuperAdmin: уведомление владельца Space (16.3, 25.8)

Добавить: «о факте сервисного входа SuperAdmin владелец Space получает уведомление (in-app и/или e-mail); механизм — ТЗ». Для мультиаренды прозрачность сервисного доступа — стандартное ожидание клиентов. Влияние на бюджет: низкое.

П-20. Неудаляемая учётка admin: смена первичного пароля и контроль (16.1, 25.12)

Добавить: «первый вход в admin требует обязательной смены пароля; использование admin вне первичной настройки — отдельное оповещение SuperAdmin-ов». Break-glass учётка не должна оставаться «тихой». Влияние на бюджет: низкое.

П-21. Мелкие нестыковки и терминология (вычитка второй волны)

1) 2.3 — дубль пункта «внутренний MQTT/TLS-протокол Gateway↔Cloud»; 2) раздел 11 — уровень severity «Авария» совпадает с именем сущности Alarm, переименовать в «Критическая авария» / Critical; 3) 18.1 — «Aggregate средства» (опечатка) и JasperReports как обязательная технология — либо лицензии Jasper в 3.3/3.4, либо напомнить принцип допустимости аналога; 4) 7.8/8.8 — Internal Space Store описан дважды, три названия виртуального устройства — привести к одному термину; 5) 7.6 — кто документирует CSV-формат массового создания Devices; 6) 11.11/19.7 — поведение при снижении retention журнала Event/Alarm не описано; 7) 18.5 — «отчёт по потреблению ресурсов»: расшифровать, ресурсов чего; 8) 19.4 — взаимодействие Max owned Spaces и Max client Spaces у интегратора; 9) дополнить список опечаток П-5: «Польщователь» (19.2), «лолжна» (21.2), артефакты конвертации (2.2, 7.8, 8.8, 12, 13, 29). Влияние на бюджет: нет (кроме п.3 — видимость стоимости лицензий Jasper).
