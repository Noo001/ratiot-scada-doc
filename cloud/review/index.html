О протоколе

Объект: RatioT.Cloud_FTT.docx, редакция v004 от 14.09.2026. Основной документ не изменялся — все предложения собраны здесь, одним перечнем. Статус: на согласовании с автором ФТТ.

Формат позиций: где в ФТТ → что сейчас → что предлагаем (готовый текст, где возможно) → почему → влияние на бюджетную оценку.

Рабочие материалы ревью: полный реестр замечаний (REVIEW_PROTOCOL.md) и проект заполнения раздела 2 (SECTION2_DRAFT.md). На этой странице — согласованная для передачи автору выжимка.

Блокеры: без этого оценка подрядчика неоднозначна

П-1. Раздел 2.1 — таблица оборудования первой очереди

Что сейчас: таблица из строк «ЗАПОЛНИТЬ».

Что нужно: конкретный перечень SKU (производитель, модель, тип, интерфейс, протокол, роль; нужны ли System Device Template и Visual Template; предоставляются ли образец и документация). Зацепки из исходной заготовки — семейство Mitra и приборы ДКС (системный каталог первого этапа — приборы ДКС).

Почему: состав таблицы — база бюджетной оценки; без неё System Library, Device Templates, Visual Templates и испытания неоценимы. Влияние на бюджет: определяет объём (ориентир для обсуждения: 5–15 SKU).

П-2. Раздел 2.2 — конкретное MQTT-устройство

Что сейчас: «Выбранное устройство SKU: ЗАПОЛНИТЬ».

Что нужно: одно стороннее MQTT-устройство и пакет документации (topic structure, формат сообщения, телеметрия, команды, аутентификация/TLS, подтверждения/ошибки, примеры обмена или симулятор). Критерий выбора: доступность для закупки/испытаний, желательно JSON без Protobuf (иначе Protobuf войдёт в объём).

Почему: абстрактный «любой MQTT» неоценим; расширение на иные MQTT-протоколы — отдельный объём. Влияние на бюджет: определяет трудоёмкость профиля MQTT.

Решения для раздела 2 (проекты — требуют подтверждения владельца продукта)

П-3. Раздел 2.3 — подтвердить границу Gateway первой очереди

Предлагаем: отметить «Подтверждаю указанную границу» и добавить в 9.2 фразу:

«Первая поставка принимается на сценарии с одним Device. Протокол Gateway↔Cloud и конфигурационная модель не должны требовать переработки при расширении до нескольких устройств на одном шлюзе; промышленная многоустройственная эксплуатация одного шлюза — отдельный объём оценки по change request.»

Почему: иначе «одно Device» и «архитектурная возможность расширения» читаются по-разному, и второе устройство через тот же шлюз станет неожиданным платным change request. Фраза не увеличивает объём, но защищает архитектурно. Влияние на бюджет: нет.

П-4. Разделы 2.5 и 18.5 — отчёт по наработке моточасов

Предлагаем: отметить «Отчёт по наработке моточасов не входит в первую поставку». В 18.5 остаются два обязательных Jasper-шаблона (потребление ресурсов за период; журнал аварий и действий персонала). Техническая возможность сохраняется: моточасы = вычисляемый параметр через Automation (7.9) → параметр виртуального устройства → архив → типовой отчёт/CSV.

Почему: для универсального IIoT-продукта отчёт не обязателен (журнал решений); снижает scope первой поставки. Альтернатива — включить и расписать содержание (период, группировка по Assets/оборудованию, суммарная наработка и по периодам), тогда в бюджет добавится шаблон и сценарии ПМИ. Влияние на бюджет: не меняет/снижает; при альтернативе — небольшое увеличение.

Правки текста ФТТ

П-5. Финальная вычитка — подтверждённые опечатки

«стандратного» (2.3); «Изенить» в поле решения владельца (2.3); «зависисмостей» (1.3); «ПОльзователем» (11.1); «конфигрурации», «не зависимо» (5.9); «приофиля» (7.7); «лолжна» (21.2); «в рамкахдругих», «техпроцесс процесс» (4.5); пункт после 6.6 — заголовок без номера. Почему: документ уходит на оценку; опечатка в поле решения выглядит как незаполненность. Влияние на бюджет: нет.

П-6. Маркировка обоснований решениями (DEC-xxx, P-00x)

В конец ключевых требований — ссылки вида (DEC-142), (P-003) на журнал решений; минимум разделы 2, 4, 5, 9, 12, 19. Текст требований не переписывается. Почему: ~190 принятых решений сейчас в ФТТ не прослеживаются; ссылки защищают их при будущих правках. Влияние на бюджет: нет.

П-7. Разделы 19.4 / 24.6 / 3.4 — определение «одновременных интерактивных UI-пользователей»

Что сейчас: тарифное поле и NFR ≥500 пользователей; механизм учёта — на ТЗ. Предлагаем: минимум — в 3.4 потребовать от каждого подрядчика в допущениях указать механизм учёта; предпочтительно — зафиксировать до оценки продуктовое определение («аутентифицированная сессия web-клиента с активным соединением; лимит проверяется при установке соединения»). Почему: иначе оценки несравнимы, спор всплывёт на приёмке. Влияние на бюджет: низкое.

П-8. Раздел 23.2 — проверка alarm flood в regression suite

Добавить в области покрытия: «контрольный сценарий с большим числом одновременных таймерных состояний Alarm Rules (TON/TOFF, anti-flapping); параметры — ТЗ/sizing». Почему: Alarm Rules на общем движке с Automation (11.4), квоту экземпляров не расходуют (12.13) — корректно, но при 50 000 устройствах граница по одновременным состояниям ничем не проверяется. Объём не меняет. Влияние на бюджет: нет.

П-9. Раздел 25.8 — хранение Security Audit после удаления Space

Предлагаем: принцип «записи аудита, относящиеся к удалённому Space, подлежат обезличиванию либо удалению по истечении retention; механизм — ТЗ» (либо явный срок независимого хранения с оценкой объёма). Почему: в аудите есть персональные данные; бесконечное хранение противоречит требованиям к ПДн, объём влияет на sizing. Влияние на бюджет: низкое.

П-10. Разделы 3.4 / 22.7 — сравнимость оценок маршрутизации FQDN→Space

Инварианты сформулированы правильно (Space до auth; frontend Space ID недоверен). Предлагаем: в 3.4 — «подрядчик в допущениях указывает предполагаемый механизм маршрутизации FQDN→Space и защиту от подмены tenant». Почему: критичный multi-tenancy механизм, оценки могут разойтись; требование к допущениям делает их сравнимыми, реализация остаётся на ТЗ. Влияние на бюджет: снижает риск разброса оценок.
