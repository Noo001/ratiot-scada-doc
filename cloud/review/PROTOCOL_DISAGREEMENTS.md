## Блок 0. Блокеры: без этого оценка подрядчика неоднозначна

### П-1. Раздел 2.1 — заполнить таблицу оборудования первой очереди

**Что сейчас:** таблица состоит из строк «ЗАПОЛНИТЬ».
**Что нужно:** конкретный перечень SKU (производитель, модель, тип, интерфейс, протокол, роль, нужны ли System Device Template и Visual Template, предоставляются ли образец и документация). Из исходной заготовки зацепка — семейство Mitra и приборы ДКС (DEC-031: системный каталог первого этапа — приборы ДКС).
**Почему:** состав таблицы — база бюджетной оценки; без неё System Library, Device Templates, Visual Templates и испытания неоценимы.
**Влияние на бюджет:** определяет объём. Ориентир для обсуждения: 5–15 SKU.

### П-2. Раздел 2.2 — выбрать конкретное MQTT-устройство

**Что сейчас:** «Выбранное устройство SKU: ЗАПОЛНИТЬ».
**Что нужно:** одно стороннее MQTT-устройство + пакет документации (topic structure, формат сообщения, телеметрия, команды, аутентификация/TLS, подтверждения/ошибки, примеры обмена или симулятор).
**Почему:** абстрактный «любой MQTT» неоценим; расширение на иные MQTT-протоколы — отдельный объём. Критерий выбора: устройство реально доступно для закупки/испытаний, желательно JSON без Protobuf (иначе Protobuf войдёт в объём, DEC-158).
**Влияние на бюджет:** определяет трудоёмкость профиля MQTT.

## Блок 1. Продуктовые решения для раздела 2 (проекты — требуют подтверждения владельца продукта)

### П-3. Раздел 2.3 — подтвердить границу Gateway первой очереди

**Что предлагаем:**
> ☒ Подтверждаю указанную границу. ☐ Изменить границу следующим образом: ___

и добавить в раздел 9.2 одну фразу:
> «Первая поставка принимается на сценарии с одним Device. Протокол Gateway↔Cloud и конфигурационная модель не должны требовать переработки при расширении до нескольких устройств на одном шлюзе; промышленная многоустройственная эксплуатация одного шлюза — отдельный объём оценки по change request.»

**Почему:** иначе «одно Device» и «архитектурная возможность расширения» читаются по-разному, и второе устройство через тот же шлюз превратится в неожиданный платный change request после оценки. Фраза не увеличивает объём, но защищает архитектурно.
**Влияние на бюджет:** нет (при подтверждении текущей границы).

### П-4. Раздел 2.5 и 18.5 — отчёт по наработке моточасов

**Что предлагаем:** отметить
> ☒ Отчёт по наработке моточасов **не входит** в первую поставку.

В 18.5 остаются два обязательных Jasper-шаблона (потребление ресурсов за период; журнал аварий и действий персонала). Техническая возможность моточасов сохраняется без отдельной разработки: вычисляемый параметр через Automation (раздел 7.9, DEC-142) → параметр виртуального устройства → архив → типовой отчёт/CSV-экспорт.

**Почему:** DEC-151 — для универсального IIoT-продукта отчёт не обязателен; это снижает scope первой поставки. Если первые клиенты критично нуждаются в готовом шаблоне — альтернатива: включить и расписать содержание (период, группировка по Assets/оборудованию, суммарная наработка и по периодам), это добавит в бюджет шаблон и сценарии ПМИ.
**Влияние на бюджет:** снижает/не меняет при предложенном варианте; небольшое увеличение при альтернативе.

## Блок 2. Правки текста ФТТ

### П-5. Весь документ — финальная вычитка (подтверждённые опечатки)

Список проверенных мест: «стандратного» (2.3), «Изенить» в поле решения владельца (2.3), «зависисмостей» (1.3), «ПОльзователем» (11.1), «конфигрурации» и «не зависимо» (5.9), «приофиля» (7.7), «лолжна» (21.2), «в рамкахдругих» и «техпроцесс процесс» (4.5); пункт после 6.6 оформлен заголовком без номера.
**Почему:** документ уходит на бюджетную оценку; опечатка в поле решения владельца выглядит как незаполненность.
**Влияние на бюджет:** нет.

### П-6. Весь документ — маркировка обоснований решениями (DEC-xxx, P-00x)

**Что предлагаем:** в конец ключевых требований — ссылки вида `(DEC-142)`, `(P-003)` на журнал решений и product-inputs. Минимум — разделы 2, 4, 5, 9, 12, 19. Текст требований не переписывается.
**Почему:** ~190 принятых решений сейчас в ФТТ не прослеживаются; любое требование можно оспорить и разбирать с нуля. Ссылки защищают принятые решения при будущих правках и ускоряют review.
**Влияние на бюджет:** нет.

### П-7. Разделы 19.4 / 24.6 / 3.4 — измеримое определение «одновременных интерактивных UI-пользователей»

**Что сейчас:** тарифное поле «Max simultaneous interactive UI users/Space» и NFR ≥500 одновременных пользователей; механизм учёта — на ТЗ.
**Что предлагаем:** минимум — в 3.4 потребовать, чтобы каждый подрядчик в допущениях оценки указал предполагаемый механизм учёта (иначе оценки несравнимы). Предпочтительно — зафиксировать продуктовое определение до оценки, напр.: «интерактивный UI-пользователь = аутентифицированная сессия web-клиента с активным соединением; лимит проверяется при установке соединения» (реализация — ТЗ).
**Почему:** без определения подрядчики оценят по-разному (сессии/websocket/активность за окно), спор всплывёт на приёмке.
**Влияние на бюджет:** низкое.

### П-8. Раздел 23.2 — добавить проверку alarm flood в regression suite

**Что предлагаем:** в области покрытия regression suite добавить: «защита от деградации при массовом числе одновременных таймерных состояний Alarm Rules (TON/TOFF, anti-flapping): контрольный сценарий с большим числом одновременных состояний; конкретные параметры — ТЗ/sizing».
**Почему:** Alarm Rules работают на общем движке с Automation (11.4), но тарифную квоту экземпляров не расходуют (12.13) — корректно, однако граница по одновременным таймерным состояниям при 50 000 устройствах не проверяется ничем. Правка не меняет продуктовый объём.
**Влияние на бюджет:** нет (в пределах существующих NFR-тестов).

### П-9. Раздел 25.8 — принцип хранения Security Audit после удаления Space

**Что сейчас:** аудит не удаляется при удалении Space (21.8), срок хранения — на ТЗ.
**Что предлагаем:** добавить принцип: «записи аудита, относящиеся к удалённому Space, подлежат обезличиванию либо удалению по истечении retention; механизм — ТЗ». Либо явно: «аудит хранится N лет независимо от удаления Space» — тогда нужна оценка объёма.
**Почему:** в аудите есть персональные данные (actor, приглашения по телефону/e-mail); бесконечное хранение противоречит требованиям к ПДн, а объём хранения влияет на sizing.
**Влияние на бюджет:** низкое.

### П-10. Разделы 3.4 / 22.7 — сравнимость оценок маршрутизации FQDN→Space

**Что сейчас:** механизм определения Space по custom FQDN до аутентификации целиком на ТЗ.
**Что предлагаем:** инварианты в ФТТ сформулированы правильно (Space определяется до auth; frontend Space ID недоверен). Добавить в 3.4: «подрядчик в допущениях указывает предполагаемый механизм маршрутизации FQDN→Space и защиту от подмены tenant».
**Почему:** критичный multi-tenancy механизм; оценки могут разойтись от nginx-маппинга до отдельного tenant-router. Требование к допущениям делает оценки сравнимыми, реализация остаётся на ТЗ.
**Влияние на бюджет:** снижает риск разброса оценок.
