## Блок 0. Блокеры: без этого оценка подрядчика неоднозначна

### П-1. Раздел 2.1 — заполнить таблицу оборудования первой очереди

**Что сейчас:** таблица состоит из строк «ЗАПОЛНИТЬ».
**Что нужно:** конкретный перечень SKU (производитель, модель, тип, интерфейс, протокол, роль, нужны ли System Device Template и Visual Template, предоставляются ли образец и документация). Из исходной заготовки зацепка — семейство Mitra и приборы ДКС (DEC-031: системный каталог первого этапа — приборы ДКС).
**Почему:** состав таблицы — база бюджетной оценки; без неё System Library, Device Templates, Visual Templates и испытания неоценимы.
**Влияние на бюджет:** определяет объём. Ориентир для обсуждения: 5–15 SKU.

### П-2. Раздел 2.2 — выбрать конкретное MQTT-устройство

**Что сейчас:** «Выбранное устройство SKU: ЗАПОЛНИТЬ».
**Что нужно:** одно стороннее MQTT-устройство + пакет документации (topic structure, формат сообщения, телеметрия, команды, аутентификация/TLS, подтверждения/ошибки, примеры обмена или симулятор).
**Почему:** абстрактный «любой MQTT» неоценим; расширение на иные MQTT-протоколы — отдельный объём. Критерий выбора: устройство реально доступно для закупки/испытаний, желательно JSON без Protobuf (иначе Protobuf войдёт в объём, DEC-158).
**Влияние на бюджет:** определяет трудоёмкость профиля MQTT.

## Блок 1. Продуктовые решения для раздела 2 (проекты — требуют подтверждения владельца продукта)

### П-3. Раздел 2.3 — подтвердить границу Gateway первой очереди

**Что предлагаем:**
> ☒ Подтверждаю указанную границу. ☐ Изменить границу следующим образом: ___

и добавить в раздел 9.2 одну фразу:
> «Первая поставка принимается на сценарии с одним Device. Протокол Gateway↔Cloud и конфигурационная модель не должны требовать переработки при расширении до нескольких устройств на одном шлюзе; промышленная многоустройственная эксплуатация одного шлюза — отдельный объём оценки по change request.»

**Почему:** иначе «одно Device» и «архитектурная возможность расширения» читаются по-разному, и второе устройство через тот же шлюз превратится в неожиданный платный change request после оценки. Фраза не увеличивает объём, но защищает архитектурно.
**Влияние на бюджет:** нет (при подтверждении текущей границы).

### П-4. Раздел 2.5 и 18.5 — отчёт по наработке моточасов

**Что предлагаем:** отметить
> ☒ Отчёт по наработке моточасов **не входит** в первую поставку.

В 18.5 остаются два обязательных Jasper-шаблона (потребление ресурсов за период; журнал аварий и действий персонала). Техническая возможность моточасов сохраняется без отдельной разработки: вычисляемый параметр через Automation (раздел 7.9, DEC-142) → параметр виртуального устройства → архив → типовой отчёт/CSV-экспорт.

**Почему:** DEC-151 — для универсального IIoT-продукта отчёт не обязателен; это снижает scope первой поставки. Если первые клиенты критично нуждаются в готовом шаблоне — альтернатива: включить и расписать содержание (период, группировка по Assets/оборудованию, суммарная наработка и по периодам), это добавит в бюджет шаблон и сценарии ПМИ.
**Влияние на бюджет:** снижает/не меняет при предложенном варианте; небольшое увеличение при альтернативе.

**Влияние на бюджет:** нет.

### П-7. Разделы 19.4 / 24.6 / 3.4 — измеримое определение «одновременных интерактивных UI-пользователей»

**Что сейчас:** тарифное поле «Max simultaneous interactive UI users/Space» и NFR ≥500 одновременных пользователей; механизм учёта — на ТЗ.
**Что предлагаем:** минимум — в 3.4 потребовать, чтобы каждый подрядчик в допущениях оценки указал предполагаемый механизм учёта (иначе оценки несравнимы). Предпочтительно — зафиксировать продуктовое определение до оценки, напр.: «интерактивный UI-пользователь = аутентифицированная сессия web-клиента с активным соединением; лимит проверяется при установке соединения» (реализация — ТЗ).
**Почему:** без определения подрядчики оценят по-разному (сессии/websocket/активность за окно), спор всплывёт на приёмке.
**Влияние на бюджет:** низкое.

### П-8. Раздел 23.2 — добавить проверку alarm flood в regression suite

**Что предлагаем:** в области покрытия regression suite добавить: «защита от деградации при массовом числе одновременных таймерных состояний Alarm Rules (TON/TOFF, anti-flapping): контрольный сценарий с большим числом одновременных состояний; конкретные параметры — ТЗ/sizing».
**Почему:** Alarm Rules работают на общем движке с Automation (11.4), но тарифную квоту экземпляров не расходуют (12.13) — корректно, однако граница по одновременным таймерным состояниям при 50 000 устройствах не проверяется ничем. Правка не меняет продуктовый объём.
**Влияние на бюджет:** нет (в пределах существующих NFR-тестов).

### П-9. Раздел 25.8 — принцип хранения Security Audit после удаления Space

**Что сейчас:** аудит не удаляется при удалении Space (21.8), срок хранения — на ТЗ.
**Что предлагаем:** добавить принцип: «записи аудита, относящиеся к удалённому Space, подлежат обезличиванию либо удалению по истечении retention; механизм — ТЗ». Либо явно: «аудит хранится N лет независимо от удаления Space» — тогда нужна оценка объёма.
**Почему:** в аудите есть персональные данные (actor, приглашения по телефону/e-mail); бесконечное хранение противоречит требованиям к ПДн, а объём хранения влияет на sizing.
**Влияние на бюджет:** низкое.

### П-10. Разделы 3.4 / 22.7 — сравнимость оценок маршрутизации FQDN→Space

**Что сейчас:** механизм определения Space по custom FQDN до аутентификации целиком на ТЗ.
**Что предлагаем:** инварианты в ФТТ сформулированы правильно (Space определяется до auth; frontend Space ID недоверен). Добавить в 3.4: «подрядчик в допущениях указывает предполагаемый механизм маршрутизации FQDN→Space и защиту от подмены tenant».
**Почему:** критичный multi-tenancy механизм; оценки могут разойтись от nginx-маппинга до отдельного tenant-router. Требование к допущениям делает оценки сравнимыми, реализация остаётся на ТЗ.
**Влияние на бюджет:** снижает риск разброса оценок.

## Блок 3. Архитектура платформы (ключевое замечание v2)

### П-11. Платформенная независимость backend: AggreGate — допустимый вариант, а не предписание

**Что сейчас.** ФТТ жёстко фиксирует серверную платформу:
- 1.3 п.1 — «Backend строится на Tibbo AggreGate Server»; 1.5 — определение «Системы» включает backend на AggreGate; то же предписание повторено в 4.4, 17.1, 24.1.
- AggreGate — обязательная часть контура поставки и результата проекта: 22.2, 27.2, 27.5, 28.2 («приложение AggreGate/low-code-компоненты» — в комплекте поставки).
- 3.2 обязывает выделить в оценке блок лицензий AggreGate; 24.1 обязывает использовать штатную кластеризацию/отказоустойчивость AggreGate и запрещает собственный failover.
- При этом baseline-версия, редакция и стоимость AggreGate намеренно не фиксируются (22.5 — «определяется в ТЗ»).

**Что не устраивает.**
1. Смета жёстко привязана к платформе, версия и стоимость которой намеренно не определены: кластерная лицензия под 50 000+ устройств, HA и 500 пользователей (24.6) может стать доминирующей и неконтролируемой статьёй TCO.
2. Исключается конкуренция подрядчиков и вариант разработки backend на собственной серверной платформе Заказчика.
3. Vendor lock-in: продуктовая функциональность описана через механизмы одного вендора; регрессионные требования (23.4, 29.4) привязаны к чужому циклу релизов.

**Что предлагаем.**
1. Платформенно-нейтральная формулировка: «серверная часть RatioT.Cloud реализуется по одному из допустимых вариантов: **(А)** собственная серверная платформа, разработка с нуля; **(Б)** платформа Tibbo AggreGate Server». Продуктовая функциональность (разделы 5–21) не меняется ни в одном варианте.
2. Формулировки «штатные механизмы AggreGate» заменяются на «штатные механизмы выбранной серверной платформы». Места правки: 1.3 п.5, 4.2, 5.9, 10.5, 10.6, 15.2, 18.1, 22.2, 24.1–24.4, 25.1, 25.2, 25.7, 25.10, 26.1–26.2, 27.2.
3. В раздел 3 добавить требование: подрядчик представляет **раздельную бюджетную оценку вариантов А и Б** с обоснованием рекомендуемого выбора: TCO на 3–5 лет (для варианта Б — лицензии AggreGate отдельной строкой), риски, требования к команде, оценка зависимости от вендора. Выбранный вариант фиксируется Заказчиком до разработки ТЗ.
4. Блок 3.2 (оценка лицензий AggreGate) становится обязательным только для варианта Б; для варианта А действует общий принцип 3.3 (коммерческие компоненты отдельными строками с обоснованием).
5. Требования кластеризации/HA (24.1–24.4) формулируются через обязательные свойства — отказоустойчивость, отсутствие очевидных SPOF, распределение Space по узлам при единой логической системе — с приоритетом штатных механизмов **выбранной** платформы; абсолютный запрет собственного failover заменяется требованием обоснования.
6. Политика версий (22.5, 23.4, 29.4) формулируется нейтрально: «обновления серверной платформы не должны блокировать выпуски RatioT.Cloud; baseline и порядок обновлений — ТЗ».

**Почему важно:** продуктовый объём не меняется, но открывается конкуренция вариантов реализации и появляется контроль TCO; снимается зависимость сметы от нефиксированной версии вендорской платформы.
**Что ещё затрагивает:** при принятии — пересмотр решений DEC-021, DEC-105, DEC-106, DEC-115, DEC-120 и соответствующих пунктов системного портрета; перечитываются разделы 14 (autotests), 16 (SuperAdmin/IAM), 20 (этапы) после правки формулировок.
**Влияние на бюджетную оценку:** меняется структура сметы (два варианта backend); продуктовый объём — нет.

## Блок 4. Внешние зависимости, противоречия и уточнения (вторая волна, v2)

### П-12. Каналы уведомлений: внешние зависимости и стоимость не закреплены (11.7, 19.5, 20.7, 3.3/3.4)

**Что сейчас:** Web/in-app, Web Push, E-mail, Telegram и SMS — обязательные каналы первой версии (11.7, 19.5). Провайдеры не определены: чей Telegram-бот и где он хостится, какой SMTP-сервис используется, через какой SMS-шлюз (платная внешняя зависимость) идёт отправка, какие требования к Web Push (VAPID, управление подписками). Раздел 20.7 описывает SMS-провайдера только для On-Premise; SaaS-контур никем не закреплён.
**Что предлагаем:** (1) в 3.4 — подрядчик в допущениях указывает внешние сервисы доставки по каждому каналу и их эксплуатационную стоимость; (2) в 19.5 — принцип: «интеграция с провайдерами доставки реализуется через адаптер; замена провайдера SMS/SMTP/Telegram не требует изменения Event/Alarm-логики и маршрутизации» (по аналогии с уже принятым принципом для MAX, DEC-140); (3) зафиксировать, что для SaaS-контура корпоративные SMTP/SMS-шлюзы предоставляет Заказчик/ДИТ, а внешний SMS-агрегатор — отдельной строкой оценки и эксплуатационных расходов.
**Почему:** сейчас каждый подрядчик оценит по-своему (покупной агрегатор против корпоративного шлюза), а эксплуатационная стоимость SMS для Заказчика не прозрачна.
**Влияние на бюджет:** снижает разброс оценок; делает видимой эксплуатационную стоимость SMS.

### П-13. Целевая ёмкость Space (5000 параметров) против тарифных лимитов (10.7, 19.4, 2.6)

**Что сейчас:** «не менее 5000 Parameters на одно Пространство как минимальную целевую ёмкость» при тарифном поле `Max Parameters per Space` и иллюстративной сетке 100/500/2000/5000+.
**Что предлагаем:** переформулировать: «архитектура должна обеспечивать ёмкость до 5000 параметров на Space; фактический лимит задаётся тарифом (поле `Max Parameters per Space`)». Слово «минимальную» убрать.
**Почему:** «минимальная ёмкость 5000» читается как гарантия для любого тарифа — низкие тарифы становятся невозможны, а подрядчик заложит архитектуру под максимум.
**Влияние на бюджет:** без правки — завышение; после правки — нейтрально.

### П-14. «Шлюз» как источник Событий противоречит составу протокола Gateway↔Cloud (11.1, раздел 9)

**Что сейчас:** раздел 11.1 перечисляет среди источников Event «Шлюз», но функции агента и внутренний протокол Gateway↔Cloud (раздел 9) передают только телеметрию, команды и конфигурацию — передачи событий там нет.
**Что предлагаем:** выбрать одно: (а) убрать «Шлюз» из перечня источников Event; либо (б) добавить в протокол Gateway↔Cloud передачу событий/ошибок шлюза (это расширение объёма оценки — тогда явно).
**Почему:** иначе подрядчики по-разному включат или не включат этот объём, а на приёмке появится спор.
**Влияние на бюджет:** низкое (вариант а) / небольшое увеличение (вариант б).

### П-15. Состав ежедневного backup, retention и RPO не определены (21.1–21.2, 24.9)

**Что сейчас:** 21.1 требует «полное резервное копирование эксплуатационного состояния инсталляции», 21.2 — «не требуется ежедневный полный дамп всей телеметрии». Что именно входит в ежедневный автоматический backup — не сказано. Retention копий, off-node/off-site размещение, шифрование не заданы. Целевой RPO в ФТТ отсутствует (24.9 прямо не задаёт SLA/RTO/RPO, а 29.2 требует HA-сценарии в ПМИ — проверять нечему).
**Что предлагаем:** определить: ежедневный backup включает конфигурацию всех Space и БД приложения без сырых телеметрических массивов (стратегия телеметрии — DB-native, выбор подрядчика); retention и off-node копия — ТЗ; целевой RPO (ориентир ≤ 24 ч) согласуется в ТЗ до ПСИ №1 и попадает в ПМИ.
**Почему:** подрядчик может понять от «ежедневного backup конфигурации» до «backup всей БД» — разброс оценок кратный; у Заказчика скрытый риск потери до суток телеметрии.
**Влияние на бюджет:** среднее (сопоставляет оценки), снимает спор на приёмке.

### П-16. Ответственность за альбом UX/UI в Figma не зафиксирована (13.5, 28.6, 3.1)

**Что сейчас:** 13.5 — альбом «должен быть спроектирован в рамках отдельного этапа ТЗ+UX/UI»; 28.6 — Figma «входит в поставку» и «достаточна для разработки frontend без самостоятельного додумывания UI». Кто производит альбом — прямо не сказано.
**Что предлагаем:** зафиксировать дословно: «альбом UX/UI (desktop + mobile) разрабатывается подрядчиком в составе этапа ТЗ+UX/UI (блок 3 оценки по 3.1) и передаётся в Figma как часть комплекта поставки».
**Почему:** если прочитать как вход от Заказчика — подрядчик не заложит в смету огромный объём; если как его работу — наоборот. Разброс смет кратный.
**Влияние на бюджет:** определяет принадлежность крупного блока оценки.

### П-17. Критерий «совместимая On-Premise инсталляция» для переноса Space не определён (21.5)

**Что сейчас:** перенос Space «SaaS → совместимый On-Premise» — целевой сценарий (21.5), но критерий совместимости нигде не определён, при этом модели SaaS (тарифы, глобальные учётки) и On-Premise (три installation-wide лимита: Spaces/Devices/Parameters) принципиально различаются.
**Что предлагаем:** добавить определение: «совместимая инсталляция — та же major-версия RatioT.Cloud; переносится конфигурационный пакет Space (21.3) со всеми смысловыми ID; тарифные ограничения SaaS не переносятся и заменяются лимитами лицензии On-Premise; несовместимые ссылочные сущности (пользователи) пересоздаются мастером импорта по правилам 21.3».
**Почему:** иначе «перенос Space» может быть оценён от копирования конфига до полноценного транслятора моделей.
**Влияние на бюджет:** сопоставляет оценки.

### П-18. Проверяемость NFR и критерии приёмки HA (24.6, 24.9, 29.2)

**Что сейчас:** числа NFR (1.5 с; ≥500 одновременных UI-пользователей; 50 000+ Devices; 5000 параметров/Space; архив до 1 с) заявлены как «целевые ориентиры», а профиль нагрузки и методика — на ТЗ. ПМИ обязана включать HA-отказные сценарии, но SLA/RTO/RPO не заданы.
**Что предлагаем:** (1) зафиксировать принцип: каждое число раздела 24.6 проверяется нагрузочным/функциональным тестом согласованного профиля и имеет критерий приёмки в ПМИ; (2) RTO/RPO и допустимые режимы отказа узла согласуются в ТЗ до ПСИ №1 и попадают в ПМИ.
**Почему:** «ориентиры без критерия приёмки» — классический конфликт на приёмке: подрядчик минимизирует профиль, Заказчик читает числа как обязательство.
**Влияние на бюджет:** низкое–среднее; главное — снимает спор на приёмке.

### П-19. Сервисный вход SuperAdmin: уведомление владельца Space (16.3, 25.8)

**Что сейчас:** SuperAdmin имеет audited service access в любой Space без приглашения; аудит фиксирует вход и действия. Требования уведомлять владельца Space о сервисном входе нет.
**Что предлагаем:** добавить: «о факте сервисного входа SuperAdmin владелец Space получает уведомление (in-app и/или e-mail); механизм — ТЗ».
**Почему:** для мультиарендного продукта прозрачность сервисного доступа — стандартное ожидание клиентов; реализация стоит почти ничего.
**Влияние на бюджет:** низкое.

### П-20. Неудаляемая системная учётка admin: первичная смена пароля и контроль использования (16.1, 25.12)

**Что сейчас:** системный `admin` с привилегией SuperAdmin неудаляем (16.1); при этом 25.12 не задаёт ни обязательной смены первичного пароля, ни отдельного контроля использования admin.
**Что предлагаем:** добавить: «первый вход в системную учётку admin требует обязательной смены пароля; использование admin вне процедур первичной настройки фиксируется отдельным оповещением пользователей с привилегией SuperAdmin».
**Почему:** break-glass учётка с неизменённым паролем — стандартный риск безопасности; второй механизм break-glass (SuperAdmin-привилегия обычного аккаунта) уже описан в 16.3, поэтому admin не должен оставаться «тихим».
**Влияние на бюджет:** низкое.

### П-21. Мелкие нестыковки и терминология (вычитка второй волны)

1. **2.3** — пункт «внутренний MQTT/TLS-протокол Gateway↔Cloud» продублирован дважды подряд; убрать дубль.

4. **7.8 / 8.8** — Internal Space Store описан дважды с разными акцентами; виртуальное устройство называется то «Virtual Device», то «виртуальное устройство "Переменные пространства"», то «Virtual/Internal Device». Привести к одному термину (предложение: «Внутреннее устройство Space (Internal Space Store)»), определение дать один раз.
5. **7.6** — массовое создание Devices «в документированном формате, как минимум через CSV»: кто и когда документирует формат — не сказано. Добавить: «формат фиксируется в документации поставки (API/экспорт)».
6. **11.11 / 19.7** — поведение при снижении retention журнала Event/Alarm не описано (для архива телеметрии — описано через Restricted); добавить аналогичный принцип или явную ссылку на 19.7.
7. **18.5** — «отчёт по потреблению ресурсов за период»: ресурсов чего — не определено (электроэнергия/тепло/вода по параметрам учёта? SMS?). Расшифровать состав, иначе шаблон неоценим.
8. **19.4** — взаимодействие полей `Max owned Spaces` и `Max client Spaces` у интегратора-владельца не описано (одно считает принадлежность, другое — делегированные Space клиентов; предположительно независимы — зафиксировать).
9. Опечатки и артефакты конвертации второй волны (дополнить П-5): «Польщователь» (19.2), «лолжна» (21.2), «соз``данное» (19), «rollbac``k» (29), склеенные маркеры (7.8), артефакты вида `` `Gateway`` / ``RatioT`.``Cloud` `` (2.2, 7.8, 8.8, 12, 13), «стандартратного» (2.3).
