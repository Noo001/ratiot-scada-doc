## 2.1 Оборудование первой очереди — ⬜ НУЖЕН ПЕРЕЧЕНЬ SKU

**Что требуется от Марко:** заполнить таблицу по каждому SKU первой очереди. Без этого подрядчик не сможет оценить объём System Library, Device Templates, Visual Templates, интеграционных работ и испытаний.

Колонки таблицы ФТТ: производитель | точный SKU/модель | тип устройства | интерфейс | протокол | роль в первой очереди | нужен ли System Device Template | нужен ли Visual Template | предоставляется ли реальный образец | предоставляется ли документация.

**Известные зацепки из исходных материалов:**
- Исходная заготовка продакт-менеджера упоминает классы оборудования и семейство **Mitra** — точные модели не названы.
- Журнал решений (DEC-031): основной системный каталог первого этапа формируется из приборов **ДКС**; навигация — иерархические категории + поиск по SKU.
- Modbus-устройства покрываются универсальным профилем (DEC-182) — для них критичны точная регистровая карта и документация, но не нужна разработка драйвера.
- OPC UA-устройство в таблицу добавлять **не нужно** (испытания на независимых программных реализациях, см. 2.4).

**Правило scope (уже в ФТТ, поддерживаем):** состав таблицы = база бюджетной оценки; добавление SKU после оценки — изменение объёма работ.

**Рекомендация Kimi:** попросить у ДКС производственное подразделение список приоритетных SKU с регистровыми картами; строк, где Visual Template не нужен, лучше избегать без причины — визуализация «из коробки» для первых клиентов важнее, чем экономия на этом столбце. Количество SKU держать в рамках разумного (ориентир для обсуждения: 5–15), иначе System Library и испытания раздувают первую поставку.

## 2.2 Пользовательский MQTT-профиль — ⬜ НУЖНО УСТРОЙСТВО И ПРОТОКОЛ

**Что требуется от Марко:** выбрать одно конкретное стороннее MQTT-устройство первой версии и собрать пакет документации:
1. производитель и точный SKU;
2. документация на topic structure;
3. формат сообщения / схема;
4. поток телеметрии;
5. команды и запись параметров;
6. идентификация устройства, аутентификация на платформе, требования к TLS;
7. подтверждения, ошибки, состояния выполнения команд;
8. примеры обмена «запрос-ответ» и/или программный симулятор производителя.

**Критерий выбора (рекомендация Kimi):** устройство должно быть реально доступно для закупки и испытаний (образец или симулятор), протокол — документирован, тип сообщений — JSON (иначе в объём попадёт Protobuf, см. DEC-158). Идеально — устройство, которое уже фигурирует в планах первых клиентов: тогда MQTT-профиль сразу окупится.

**Готовая формулировка для ФТТ после выбора:**
> **Выбранное устройство SKU:** <производитель, модель>
> **Ссылка на комплект документации:** <ссылка/архив у владельца продукта>

## 2.3 Граница Gateway первой очереди — ✅ ПРОЕКТ РЕШЕНИЯ

**Предлагаемый выбор:** ✅ **Подтверждаю указанную границу.**

**Готовая формулировка для ФТТ:**
> **Решение владельца продукта перед оценкой:** ☒ Подтверждаю указанную границу. ☐ Изменить границу следующим образом: ___

**Дополнительно (связано с CR-005):** предлагается добавить в 9.2 одну фразу, чтобы снять двусмысленность «одно Device vs расширение»:
> «Первая поставка принимается на сценарии с одним Device. Протокол Gateway↔Cloud и конфигурационная модель не должны требовать переработки при расширении до нескольких устройств на одном шлюзе; промышленная многоустройственная эксплуатация одного шлюза — отдельный объём оценки по change request.»

Обоснование: без этой фразы подрядчик может законно реализовать шлюз «в лоб» под одно устройство, и второе устройство через тот же шлюз станет неожиданным paid change request.

**Основание:** DEC-022…024, DEC-125…128, DEC-179; рекомендация product-inputs.md.

## 2.5 Типовой отчёт по наработке моточасов — ✅ ПРОЕКТ РЕШЕНИЯ

**Предлагаемый выбор:** ☒ **Отчёт по наработке моточасов не входит в первую поставку.**

**Готовая формулировка для ФТТ:**
> ☒ Отчёт по наработке моточасов **не входит** в первую поставку.
> ☐ Отчёт по наработке моточасов входит в первую поставку как обязательный базовый Jasper-шаблон — содержание: ___

**Обоснование:**
- DEC-151: для универсального IIoT-продукта отчёт не считается автоматически обязательным.
- Техническая возможность сохраняется без отдельной разработки: моточасы = вычисляемый параметр через Automation (7.9, DEC-142), запись в параметр виртуального устройства, история в архиве, выгрузка через типовой отчёт по потреблению/экспорт CSV.
- Если первые клиенты (тепловые пункты, генераторы) критично нуждаются в готовом шаблоне — вернуть вопрос владельцу; тогда в 2.5 нужно расписать содержание (период, группировка по Assets/оборудованию, наработка суммарно и по периодам, перерывы), и в бюджет добавится шаблон + сценарии ПМИ.

Решение по этому пункту — за Марко/владельцем (см. CR-004).
