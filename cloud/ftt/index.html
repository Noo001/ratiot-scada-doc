1. Общие сведения

1.1. Наименование проекта

RatioT.Cloud — сервис облачной автоматизации и удалённой диспетчеризации класса Cloud Mini-SCADA / Industrial IoT.

Заказчик — АО «ДКС».

1.2. Назначение настоящего ФТТ

Настоящие функционально-технические требования определяют функциональный объём, существенные архитектурные ограничения, требования к поставке, испытаниям и эксплуатации RatioT.Cloud на уровне, достаточном для подготовки подрядчиком бюджетной оценки полного проекта.

ФТТ фиксирует, что должно быть реализовано, а также обязательные границы и эксплуатационные свойства решения. Детальная техническая реализация, схемы данных, конкретные внутренние интерфейсы, состав библиотек реализации и иные проектные решения, не влияющие на зафиксированный объём работ, разрабатываются и согласуются на этапе ТЗ.

После получения и согласования бюджетной оценки Заказчик и подрядчик совместно разрабатывают детальное ТЗ, включая UX/UI-проектирование и полный комплект экранов для desktop и mobile-представлений web-интерфейса.

1.3. Общие принципы реализации

  1. Backend RatioT.Cloud строится на Tibbo AggreGate Server с приоритетным использованием штатных механизмов AggreGate и стандартных общедоступных программных компонентов.
  2. Пользовательский frontend является отдельным адаптивным web-приложением. Конкретный frontend-стек выбирается подрядчиком при соблюдении требований настоящего ФТТ.
  3. Frontend и backend взаимодействуют через формализованный контракт и общий документированный Application API. Бизнес-логика, RBAC и тарифные ограничения должны применяться на backend и не дублироваться как независимая логика frontend.
  4. Подрядчик проектирует и поставляет весь программный контур, необходимый для работоспособности RatioT.Cloud выше уровня ОС, в границах ответственности, установленных настоящим ФТТ.
  5. При наличии подходящего штатного механизма AggreGate или стандартного общедоступного компонента предпочтительно его использование вместо разработки собственной подсистемы с аналогичной функцией.
  6. Решение должно поставляться Заказчику в воспроизводимом виде. Для сборки, развёртывания и сопровождения не должно быть зависисмостей от закрытой инфраструктуры подрядчика.

1.4. Порядок использования документа до начала разработки

До передачи ФТТ подрядчику на окончательную бюджетную оценку владелец продукта заполняет раздел 2 «Исходные данные от владельца продукта». Незакрытые в нём пункты должны быть явно отражены подрядчиком как допущения или исключения оценки.

После согласования бюджета этап разработки начинается с подготовки ТЗ, включающего задание на UX/UI. ТЗ уточняет технические параметры и технические решения, которые настоящим ФТТ сознательно не фиксируются, без изменения согласованного функционального объёма без отдельного запроса на изменения.

1.5. Основные термины

Система / RatioT.Cloud — совокупность backend на Tibbo AggreGate, отдельного web-приложения и необходимых программных компонентов инфраструктурного контура (все что выше ОС), обеспечивающих функции, описанные в настоящем ФТТ.

Space / Пространство — это tenant и основная единица изоляции пользовательских данных, прав, конфигурации и эксплуатационного состояния. Space одновременно является корневым Asset.

Asset / Объект — узел произвольной пользовательской иерархии внутри Space, предназначенный для размещения, организации, поиска и разграничения доступа к оборудованию (цеха, задния, щиты, этажи и т.п.).

Device / Экземпляр устройства — цифровое представление конкретного физического или виртуального устройства в Space.

Заготовка устройства / Device Template — версионируемая библиотечная конфигурация, определяющая смысловые параметры и команды устройства, профиль сопряжения, профильные настройки и значения по умолчанию.

Профиль сопряжения / Coupling Profile — системный расширяемый механизм связи Device с реальным оборудованием или внутренним источником данных Платформы.

Parameter / Параметр — элемент данных Device с определённым типом, значением, временной меткой и признаком качества; может быть доступен для чтения и/или записи.

Dashboard / Дашборд — интерактивное рабочее место пользователя внутри одного Space, предназначенное для визуализации данных и выполнения разрешённых управляющих действий.

Visual Template / Визуальная заготовка — библиотечное визуальное представление, связываемое со смысловыми параметрами и командами Device.

Event / Событие — неизменяемый зафиксированный факт, формируемый системными или пользовательскими сущностями RatioT.Cloud.

Alarm / Авария — Event с дополнительным жизненным циклом, severity и механизмом квитирования.

Automation — пользовательская No-Code автоматизация, выполняющая сценарии по событиям, условиям и расписаниям средствами контролируемого backend runtime.

Gateway / Шлюз — программный пограничный агент, обеспечивающий обмен между локальным оборудованием и RatioT.Cloud. В первой очереди термин относится к PC Gateway PoC в границах раздела 9.

SaaS — многопользовательская облачная эксплуатация RatioT.Cloud на инфраструктуре Заказчика.

On-Premise — отдельная лицензируемая инсталляция RatioT.Cloud в инфраструктуре клиента.

4. Назначение и границы RatioT.Cloud

4.1. Назначение

RatioT.Cloud должна представлять собой мультиарендную клиент-серверную платформу класса Cloud Mini-SCADA / Industrial IoT, предназначенную для подключения распределённого оборудования, сбора и хранения телеметрии, удалённого диспетчерского управления, визуализации, аварийного оповещения, отчётности и пользовательской No-Code автоматизации.

Платформа ориентирована на эксплуатацию технологического и инженерного оборудования через web-браузер без установки пользовательского «толстого клиента».

RatioT.Cloud должна поддерживать два варианта эксплуатации:

  • SaaS — многопользовательская облачная инсталляция с изолированными Space;

5. Базовая информационная модель

5.1. Пространство / Space

Пространство / ``Space является tenant и основной единицей изоляции пользовательских данных, конфигурации, прав доступа и эксплуатационного состояния.

Все пользовательские сущности RatioT.Cloud должны иметь однозначную принадлежность Пространству, кроме учётных записей пользователей (они глобальны) и платформенных сущностей уровня SuperAdmin.

Учётные записи пользователей и сущности Личной библиотеки пользователя являются глобальными относительно Пространств. Платформенные системные сущности также не принадлежат отдельному Пространству.

Пространство одновременно является безусловно существующим корневым Объектом / ``Asset. Пользователь не обязан создавать дополнительные Объекты (Assets): Device может размещаться непосредственно в корне Пространства.

Одна пользовательская учётная запись может иметь доступ к нескольким Пространствам, включая Пространства, физически обслуживаемые разными узлами одной логической инсталляции.

Для Пространства должен задаваться часовой пояс (timezone). Внутреннее хранение и передача timestamps выполняются в UTC; пользовательское представление времени в интерфейсе, журналах, трендах, отчётах и расписаниях выполняется в часовом поясе (timezone) Пространства.

5.2. Объект / Asset

Объект / ``Asset является универсальным узлом иерархии внутри Пространства.

Назначение Объекта (Asset):

  • организационное размещение оборудования;
  • инвентаризация;
  • поиск и фильтрация;
  • наследование прав доступа;
  • географическая группировка.

Типы уровней «предприятие / цех / этаж / шкаф» не должны быть жёстко зашиты в модель. Иерархия должна поддерживать произвольную структуру и без специальных ограничений обеспечивать не менее 10 уровней вложенности.

Объект (Asset) не определяет поток данных и не ограничивает использование Устройств на Дашборде.

Объект (Asset) может иметь:

  • имя и описание;
  • пользовательские ярлыки/теги;
  • необязательное текстовое описание/адрес места установки;
  • список изображений для нужд будущего расширения (при этом реализация системы загрузки и отображения изображений в реализацию не входит);
  • необязательные latitude``/``longitude для географической карты (при этом сложная адресная модель и геокодинг в первую поставку не входят).

5.3. Экземпляр устройства, Устройство / Device

Экземпляр устройства / ``Device является цифровым представлением конкретного физического или виртуального устройства.

Device:

  • принадлежит одному Пространству;
  • размещается в одном Объекте (Asset), включая корневой Объект Пространства;
  • существует независимо от Дашборда;
  • может использоваться на нескольких Дашбордах;
  • может иметь пользовательские ярлыки/теги;
  • наследует геопривязку от Объекта/Asset;
  • содержит параметры, команды и настройки, определённые Заготовкой устройства и Профилем сопряжения.

Удаление визуального представления с Дашборда не должно удалять Device.

Учётная запись пользователя является глобальной на платформе. Один пользователь может состоять в нескольких Пространствах и иметь в них разные группы и права.

5.6. Параметр / Parameter

Параметр принадлежит Устройству/Device. Отдельные параметры непосредственно к Объекту (Asset) не прикрепляются.

Сквозной контракт параметра Устройства должен быть единым для Modbus, MQTT, OPC UA, Internal Space Store, Профилей сопряжения, Виджета.

Для текущего значения параметра должны быть доступны как минимум:

  • значение / value;
  • тип данных;
  • время возникновения / source timestamp;
  • качество (quality или status).

При необходимости для диагностики отдельно хранится server``/``receive`` ``timestamp для данных, проходящих через Шлюза.

Нормализованный верхнеуровневый quality должен различать как минимум:

  • Good;
  • Uncertain;
  • Bad.

При этом должна сохраняться возможность передать более детальный протокольный status конкретного профиля сопряжения.

Метаданные параметра могут включать:

  • отображаемое имя (display name);
  • стабильный семантический ID;
  • единица измерения (engineering unit);
  • признак read/write;
  • необязательные границы диапазона min``/``max (engineering range);
  • расширяемые атрибуты.

Engineering range не является обязательным элементом для сработки аварий и событий и не заменяет аварийные уставки HH/H/L/LL (или иные аварийные уставки).

5.7. Команды / Commands

Команды Device являются смысловыми операциями, доступность и фактическое исполнение которых обеспечиваются Профилем сопряжения.

Механизм команды должен возвращать унифицированный результат выполнения, включая success/error/timeout и расширенную диагностическую информацию(например текстовую расшифровку кода ошибки и т.п.), достаточную для frontend, Automation и журналирования .

Проверка доступности канала перед управляющим действием не должна реализовываться пользовательской последовательностью check`` → ``command; профиль сопряжения должен учитывать текущее состояние канала при выполнении команды и возвращать фактический результат (ошибку, например, если канал связи не доступен).

5.8. Дашборд / Dashboard и границы модели

Дашборд принадлежит одному Пространству, но не является дочерним Объектом (Asset).

Дашборд может одновременно использовать разрешённые данные Devices из разных ветвей дерева Объектов (Asset) своего Пространства. Иерархия Объектов (Assets) не определяет структуру Дашборда и не создаёт обязательную иерархию экранов.

5.9. Логическое разделение данных приложения (application data) и пользовательских данных (user data)

Компоненты приложения RatioT.Cloud и эксплуатационные пользовательские данные должны быть логически разделены так, чтобы пользовательское состояние могло резервироваться, восстанавливаться и переноситься предусмотренными механизмами не зависимо от конфигрурации приложения (в терминологии Aggregate) или “кода приложения” в общетехнической терминологии.

Настоящее ФТТ не предписывает обязательное физическое размещение application data и user data в двух отдельных БД или СУБД. Конкретная физическая топология определяется подрядчиком на этапе ТЗ с учётом архитектуры Tibbo AggreGate, HA и требований к backup/restore.

6. Библиотеки и версионирование

6.1. Библиотеки первой версии

В RatioT.Cloud библиотечными сущностями являются:

  • Заготовки устройств / Device Templates;
  • Визуальные заготовки / Visual Templates.

Для каждой из этих сущностей поддерживаются три области:

  1. Системная библиотека / System Library — системная библиотека RatioT.Cloud/DKC, поставляемая и сопровождаемая как часть продукта;
  2. Библиотека Пространства / Space Library — библиотека конкретного Пространства, принадлежащая Пространству независимо от конкретного сотрудника;
  3. Личная библиотека пользователя / User Library — личная библиотека пользователя, доступная этому пользователю в разных Пространствах, где у него есть соответствующие права.

В UI эти области могут быть представлены единым каталогом с фильтрами по источнику, однако права и жизненный цикл сущностей должны учитывать их фактическую область принадлежности.

Библиотека отвечает на вопрос «что можно создать/добавить», а рабочие сущности Пространства — «что уже создано».

Отдельные пользовательские библиотеки Дашбордов и Automation не требуются. Дашборд и Automation являются объектами конкретного Пространства. Jasper-шаблоны отчётов входят в поставку системы и отдельно регулируются разделом 18, в библиотеках не фигурируют и никаким особым образом не организуются.

6.2. Системная библиотека / System Library

Системная библиотека должна содержать готовые Заготовки устройств (Device Templates) оборудования, входящего в согласованный перечень первой очереди, и соответствующие Визуальные заготовки (Visual Templates), если это указано в разделе 2.1.

Готовое оборудование должно находиться:

  • через иерархические категории/смысловую навигацию;
  • быстрым поиском по SKU.

Использование готовых системных шаблонов не должно требовать от пользователя навыков программирования или предварительного создания собственной Заготовки.

6.3. Версионирование Заготовок устройств

Заготовки устройств должны иметь неизменяемые версии.

Изменение существующей Заготовки создаёт новую версию. Ранее созданные Device не переводятся на новую версию автоматически.

Внутренние semantic ID параметров и команд должны оставаться стабильными при совместимых изменениях и позволять изменять display name без разрушения ссылок.

К совместимым изменениям относятся, например:

  • изменение настроек Профиля сопряжения (profile-specific settings) и значений по умолчанию (defaults);
  • изменение масштабирования/вычислений, не меняющее смысловой ID;
  • изменение display name при сохранении semantic ID;
  • добавление нового параметра.

К потенциально несовместимым относятся, например:

  • удаление используемого параметра;
  • несовместимое изменение типа;
  • изменение/утрата стабильного semantic ID.

Для существующего Экземпляра устройства пользователь должен иметь возможность явно выбрать переход на более новую версию Заготовки устройства. Перед применением система должна проверить совместимость новой версии с текущей конфигурацией экземпляра и существующими ссылками на его Параметры и Команды. При совместимом переходе существующие привязки, в том числе на Дашбордах, в Авариях и Автоматизации, должны сохраняться за счёт стабильных смысловых идентификаторов (semantic ID).

Для несовместимого перехода система должна требовать явного разрешения конфликтов пользователем, а не выполнять скрытую автоматическую перепривязку.

Смена Профиля сопряжения при сохранении той же смысловой модели оформляется новой версией Заготовки.

6.4. Удаление и архивирование версий

Пользователь должен иметь возможность “убрать” созданную им Заготовку из библиотеки визуально - скрыть по сути.

Однако, если на конкретную версию ссылаются существующие Devices, такая версия не должна физически уничтожаться. Она переводится в скрытое/архивное состояние и остаётся доступной для среды исполнения и нужд диагностики до исчезновения всех зависимостей.

Удаление элемента из библиотеки не должно разрушать работающие Devices и существующие визуальные привязки.

6.5. Визуальные заготовки / Visual Templates

Визуальные заготовки (Visual Templates) являются отдельными от Заготовок устройств (Device Templates) библиотечными сущностями.

Визуальная заготовка определяет повторно используемое визуальное представление, состоящее из одного или нескольких Виджетов, и входной смысловой контракт (input contract) — набор требуемых Параметров и Команд с указанием их смысловых идентификаторов (semantic ID), типов и назначения.

Входы одной Визуальной заготовки могут относиться к одному или нескольким Устройствам. Визуальная заготовка не должна быть жёстко связана с одной конкретной Заготовкой устройства или с физической топологией оборудования.

Для Визуальной заготовки может быть задан справочный список рекомендуемых SKU и/или Заготовок устройств (Recommended SKU/Device Templates). Этот список используется для упрощения поиска и подбора совместимого оборудования, но не является обязательным составом оборудования и не создаёт Экземпляры устройств автоматически.

При подборе совместимых Визуальных заготовок система должна учитывать входной смысловой контракт — смысловые идентификаторы (semantic ID), типы и назначение требуемых Параметров и Команд, а не только наименование конкретной Заготовки устройства.

Визуальная заготовка может храниться в Системной библиотеке, Библиотеке Пространства или Личной библиотеке пользователя (System / Space / User Library).

6.6. Тиражирование между Пространствами

Рабочий Экземпляр устройства (Device) напрямую между Пространствами не переносится как единый объект с эксплуатационной историей.

Для тиражирования настроенного устройства его конфигурация сохраняется как Заготовка устройства в подходящую библиотеку, после чего в целевом Пространстве создаётся новый Экземпляр устройства.

Аналогично, повторно используемое визуальное представление сохраняется как Визуальная заготовка в Библиотеку Пространства или Личную библиотеку пользователя и затем может быть использовано в другом Пространстве, где у пользователя есть соответствующие права.

Экземпляр Визуальной заготовки, размещённый на конкретном Дашборде, является частью конфигурации этого Дашборда и напрямую между Пространствами не переносится. При использовании той же Визуальной заготовки в другом Пространстве её входы должны быть заново сопоставлены с конкретными Параметрами и Командами Экземпляров устройств целевого Пространства.

Эксплуатационная история, архив телеметрии и история Аварий/Событий исходных Устройств при таком тиражировании не переносятся.

Отдельные сценарии резервного копирования, восстановления и миграции (backup/restore/migration) целого Пространства регулируются разделом 21 и не заменяют библиотечный механизм тиражирования.

7. Устройства и Конструктор Заготовок устройств (Device Template Builder)

7.1. Заготовка устройства

Пользовательская модель оборудования строится вокруг Заготовки устройства / ``Device`` ``Template и конкретного Устройства Device.

Отдельная видимая пользователю сущность «Функциональная модель устройства» не вводится. Протоколонезависимая смысловая часть и Профиль сопряжения должны быть архитектурно разделены, но для пользователя по смыслу объединяются в одной Заготовке устройства.

Заготовка должна содержать как минимум:

  • смысловые параметры;
  • команды;
  • типы данных;
  • единицы измерения;
  • атрибуты чтения/записи (read/write);
  • стабильные семантические ID (semantic ID);
  • необязательные инженерные min/max (engineering min/max);
  • расширяемые атрибуты метаданных (metadata attributes);
  • выбранный Профиль сопряжения;
  • профильные настройки;
  • фиксированные значения и значения по умолчанию (defaults);
  • обязательные к вводу настройки экземпляра (instance settings);
  • при необходимости типовые правила аварий (Alarm Rules).

7.2. Конструктор Заготовок устройств / Device Template Builder

Система должна предоставлять визуальный Конструктор Заготовок устройств (Device Template Builder), позволяющий создавать и изменять Заготовки устройств без необходимости программирования пользователем.

Конструктор должен состоять из общей части, предназначенной для описания смысловой модели Устройства, и профильной части, состав и настройки которой определяются выбранным Профилем сопряжения.

В общей части пользователь должен иметь возможность определять Параметры и Команды Устройства, их типы, единицы измерения, смысловые идентификаторы (semantic ID), атрибуты чтения/записи, значения по умолчанию и иные свойства, не зависящие непосредственно от используемого протокола обмена.

Профильная часть Конструктора должна предоставлять пользователю настройки, необходимые для выбранного Профиля сопряжения, и обеспечивать связывание смысловых Параметров и Команд Заготовки с данными и операциями конкретного протокола.

В первой версии должны использоваться, в частности, универсальные Профили сопряжения Modbus RTU и Modbus TCP, определённые в разделе 8. Они должны позволять средствами Конструктора создавать Заготовки устройств для различных совместимых Modbus-устройств без разработки отдельного программного драйвера для каждого SKU.

Для таких Заготовок пользователь должен иметь возможность настроить карту данных и правила преобразования между протокольным представлением и смысловыми Параметрами и Командами Устройства. Конкретный состав поддерживаемых настроек и возможностей универсальных Modbus-профилей определяется разделом 8 и не дублируется в настоящем разделе.

Конструктор должен позволять задавать фиксированные значения, значения по умолчанию и поля, обязательные для заполнения при создании конкретного Экземпляра устройства.

Протокольная специфика и преобразования физического оборудования должны оставаться в Профиле сопряжения и Заготовке устройства и не переноситься в Автоматизацию (Automation) или Дашборды.

7.3. Создание экземпляра устройства (Device)

Создание Device выполняется через единый мастер (Wizard), формируемый по метаданным (metadata-driven).

Wizard формируется на основе выбранной Заготовки устройства и Профиля сопряжения и должен позволять в одном последовательном пользовательском процессе:

  • выбрать Пространство/Объект (Space/Asset) размещения;
  • задать имя;
  • заполнить поля конкретного экземпляра (instance-specific);
  • задать профильные параметры подключения;
  • при необходимости указать серийный номер/исполнение/опции;
  • выполнить проверку связи, если профиль это поддерживает;
  • завершить создание Device.

Добавление нового SKU в Системную библиотеку (System Library) не должно требовать разработки отдельного мастера (Wizard) во frontend для каждого типа устройства.

Если явно Объект (Asset) не выбран, Device может создается по умолчанию в корневом Объекте - Пространстве.

7.4. Простой старт с готовым оборудованием

Пользователь должен иметь возможность подключить готовое устройство из Системной библиотеки без входа в Конструктор Заготовок устройств (Device Template Builder).

После выбора готового SKU система должна запросить только данные конкретного экземпляра и параметры подключения, необходимые выбранному профилю.

Базовый пользовательский сценарий должен обеспечивать быстрое получение текущих данных с устройств и переход к визуализации без предварительного изучения пользователем внутренней модели RatioT.Cloud.

7.5. Массовое создание

Система должна поддерживать массовое создание/настройку однотипных Devices на основе Заготовки.

Должен быть предусмотрен массовый ввод данных конкретных экземпляров (instance-specific) в документированном формате, как минимум через CSV. Конкретный UX массовой операции определяется ТЗ.

Массовое создание не должно обходить серверную валидацию (server-side validation), тарифные ограничения (entitlement) и RBAC.

7.6. Импорт и экспорт Заготовок

Для Заготовок устройств обязательны документированные форматы:

  • JSON — основной машинно-ориентированный формат полного импорта/экспорта;
  • CSV — формат для табличных/массовых операций там, где структура допускает однозначное представление.

Отдельный XML-формат в первой версии не требуется.

Импорт должен проверять корректность структуры, версии и зависимостей и не создавать частично применённую Заготовку при критической ошибке.

7.7. Изменение Профиля сопряжения

Если смысловая модель Device сохраняется, допускается замена Профиля сопряжения с повторным заданием сопоставления (mapping)/настроек подключения.

Для библиотечной Заготовки такая смена оформляется новой неизменяемой версией. Для конкретного Device смена профиля не должна разрушать semantic ID параметров/команд, если соответствие остаётся совместимым.

Например если один и тот же прибор может одинаково подключаться по mqtt и через шлюз по ModbusRTU то смена приофиля подключения должна быть возможна.

7.8. Внутреннее хранилище переменных и событий Пространства / Internal Space Store

Система должна иметь системный Профиль сопряжения Internal`` ``Space`` ``Store, не использующий внешний транспорт.

Параметры виртуального устройства Virtual Device с таким профилем сопряжения хранятся постоянно в Пространстве и переживают перезапуск backend (restart).

При создании нового Пространства автоматически создаётся видимый пользователю виртуальное устройство «Переменные пространства» с некоторым набором параметров базовых типов. Точный стартовый набор определяется на этапе ТЗ. Архивирование этих параметров по умолчанию выключено.

Параметры Internal Space Store должны поддерживать как минимум:

  • начальное значение/значение по умолчанию (initial/default value);
  • тип данных;
  • признак «только чтение» (read-only);
  • обычный доступ через Дашборд, API, Alarm и Automation;
  • включаемое при необходимости архивирование.

7.9. Вычисляемые параметры

Отдельный тип «вычисляемый параметр» и отдельный движок формул (formula engine) не создаются, но этот функционал реализуется механизмом: - Вычисляемое значение формируется Automation-сценарием и записывается в параметр Virtual Device. - После записи такой параметр является обычным параметром RatioT.Cloud и может использоваться Дашбордом, Archive, Event/Alarm, API и другими Automation без специальных связок.

7.10. Диагностический просмотр Device

До создания Дашборда для каждого Device должен быть доступен стандартный диагностический экран текущих параметров, содержащий как минимум:

  • отображаемое имя (display name) и семантический ID (semantic ID);
  • текущее значение;
  • единица измерения (engineering unit);
  • качество/статус (quality/status);
  • временная метка (timestamp);
  • при необходимости исходное значение (raw value);
  • для параметров, доступных для записи (writable) — штатную запись с обязательной backend-проверкой RBAC.

8. Профили сопряжения

8.1. Общая модель

Профиль сопряжения / Coupling Profile является системным расширяемым механизмом связи Экземпляра устройства (Device) с физическим оборудованием либо внутренним источником/хранилищем данных RatioT.Cloud.

Профили сопряжения разрабатываются разработчиками Платформы. Пользователь выбирает доступный Профиль сопряжения и задаёт предусмотренные им настройки, но не программирует транспорт или стек протоколов (protocol stack).

Профиль сопряжения должен скрывать специфику конкретного протокола или источника данных и обеспечивать преобразование обмена с ним в единую смысловую модель Параметров и Команд Устройства, определённую в разделе 5. Конкретные возможности и настройки отдельных Профилей сопряжения определяются следующими подразделами.

8.2. Универсальный профиль сопряжения Modbus RTU

Первая версия должна включать универсальный профиль Modbus RTU, переиспользуемый различными SKU.

Обязательный минимум:

  • функции 01, 02, 03, 04, 05, 06, 15, 16;
  • Slave ID;
  • настройки serial-интерфейса (serial settings), необходимые для подключения;
  • поддерживаемые типы данных;
  • Big-endian / Little-endian;
  • word-swap;
  • byte-swap;
  • масштабирование/коэффициенты преобразования (scaling);
  • преобразование Raw→Engineering value;
  • разные группы/циклы опроса (polling groups/cycles) для параметров одного Device;
  • чтение и запись согласно карте конкретной Заготовки.

Конкретная карта регистров/катушек и семантика SKU должны задаваться Заготовкой устройства, а не быть зашиты в профиль.

8.3. Универсальный профиль сопряжения Modbus TCP

Первая версия должна включать универсальный профиль Modbus TCP, использующий ту же модель Заготовки и карт параметров, что Modbus RTU, с профильными настройками (profile-specific) сетевого соединения.

Профиль должен поддерживать те же обязательные функции Modbus, типы, ordering, scaling и группы опроса (polling groups), что и Modbus RTU, если соответствующая операция применима к TCP-варианту.

8.4. Универсальный профиль сопряжения MQTT

В первую версию входит MQTT-профиль стороннего оборудования только для конкретного устройства/протокола (device/protocol), указанного владельцем продукта в разделе 2.2.

Объём профиля (scope) определяется документацией выбранного устройства и должен включать только согласованные:

  • топики (topics);
  • сообщения телеметрии (telemetry messages);
  • команды/поток записи (commands/write flow);
  • идентификация устройства (device identification);
  • подтверждения/ошибки (acknowledgements/errors);
  • authentication/TLS;
  • формат/схема сообщений (message format/schema).

Абстрактное требование «поддержать любой MQTT» не предъявляется, поскольку объективно невозможно.

Поддержка Protobuf обязательна только при её наличии в протоколе выбранного устройства. Иначе первая версия не обязана реализовывать Protobuf только ради общей возможности.

ВАЖНО: >Служебный MQTT-протокол Шлюз↔︎Cloud (Gateway↔︎Cloud) не является пользовательским Профилем сопряжения и в каталоге профилей Device не отображается.

8.5. OPC UA Client

Первая версия должна включать OPC UA Client с объёмом Data Access (scope) как минимум:

  • просмотр адресного пространства (browse/address space);
  • чтение;
  • запись узлов, доступных для записи (writable nodes);
  • подписки/отслеживаемые элементы (subscriptions/monitored items);
  • согласованные типы данных;
  • временные метки (timestamps);
  • качество/статус (quality/status);
  • переподключение/восстановление (reconnect/recovery);
  • режимы безопасности (security modes), согласованные на этапе ТЗ.

Не требуется в первой версии:

  • OPC UA Methods;
  • Historical Access;
  • Alarms & Conditions.

Архив (Archive) и Аварии (Alarm) RatioT.Cloud остаются собственными подсистемами платформы.

8.6. OPC UA Server

RatioT.Cloud должна предоставлять данные разрешённых Devices внешним OPC UA-клиентам через OPC UA Server.

Server должен обеспечивать Data Access в границах, согласованных на этапе ТЗ, включая чтение, запись разрешённых узлов, доступных для записи (writable nodes), временные метки (timestamps) и качество/статус (quality/status) с обязательным применением прав доступа backend.

8.7. Испытания OPC UA

OPC UA Client RatioT.Cloud должен испытываться на независимом программном OPC UA Server, а OPC UA Server RatioT.Cloud — на независимом программном OPC UA Client. Допустимы open62541, UaExpert или эквивалентные реализации.

Проверка только связкой «собственный Client ↔︎ собственный Server» недостаточна.

Эталонные программные стенды (software stands) и автоматизируемая часть проверок должны быть включены в backend regression suite.

8.8. Внутреннее хранилище Пространства / Internal Space Store

Internal`` ``Space`` ``Stor``e является штатным Профилем сопряжения без внешнего транспорта и используется для промежуточного хранения постоянных внутренних параметров Пространства, в том числе для результатов вычислений Automation. Предоставляет по сути решение по организации переменных и констант Пространства.

Он должен соблюдать тот же канонический контракт параметров (parameter contract), что и внешние профили (profiles).

8.9. Расширяемость

Архитектура Профилей сопряжения должна позволять добавлять новые протоколы/адаптеры (protocols/adapters) без изменения базовой модели Пространство / Объект / Device / Параметр и без переноса протокольной логики в Дашборд или Automation.

9. Прототип Шлюза (Gateway) и внутренний протокол

9.1. Назначение Программного прототипа Шлюза (Cloud Gateway Agent)

В первой очереди подрядчик реализует программный агент Шлюза (Cloud Gateway Agent) как проверочный прототип (proof-of-concept) для стандартного ПК.

Цель Программного прототипа Шлюза — подтвердить архитектурную возможность безопасного подключения локального Modbus RTU-оборудования к RatioT.Cloud через управляемый из Cloud агент.

Программный прототип Шлюза не является заданием на разработку серийного аппаратного Шлюза (Gateway), а используется при испытаниях для подтверждения работоспособности принятых архитектурных решений в части взаимодействия Шлюза с RatioT.Cloud, включая протоколы обмена и модель данных.

9.2. Обязательный функционал Программного прототипа Шлюза

В составе Программного прототипа Шлюза программный агент Шлюза (Cloud Gateway Agent) должен обеспечивать:

  • работу в режиме Modbus RTU Master через последовательный интерфейс;
  • обслуживание одного Экземпляра устройства (Device) в рамках Программного прототипа Шлюза; при этом архитектура агента, внутренний протокол и модель конфигурации не должны препятствовать последующему расширению до нескольких Экземпляров устройств;
  • соединение с RatioT.Cloud через внутренний MQTT-протокол;
  • получение эксплуатационной конфигурации из RatioT.Cloud;
  • постоянное локальное хранение последней валидной применённой конфигурации;
  • периодическую проверку наличия новой версии конфигурации;
  • проверку и атомарное применение новой валидной конфигурации;
  • сбор и передачу телеметрии в RatioT.Cloud;
  • получение управляющих команд из RatioT.Cloud;
  • выполнение соответствующих операций Modbus RTU;
  • возврат результата выполнения, ошибки или тайм-аута (timeout) с идентификатором корреляции (correlation ID);
  • восстановление соединения после временной потери связи с RatioT.Cloud.

9.3. Начальная конфигурация (Bootstrap)

Для первоначального запуска программного агента Шлюза (Cloud Gateway Agent) допускается минимальная локальная начальная конфигурация (bootstrap configuration), содержащая только данные, необходимые для установления связи с RatioT.Cloud, например:

  • адрес MQTT-брокера / RatioT.Cloud;
  • идентификатор Шлюза (Gateway ID);
  • учётные данные (credentials);
  • минимальные настройки TLS и сети.

Настройки Modbus RTU, последовательного интерфейса, опроса, сопоставления Параметров и Команд и иная эксплуатационная конфигурация Программного прототипа Шлюза должны управляться из RatioT.Cloud и не должны требовать постоянного ручного ведения в локальной конфигурации программного агента Шлюза.

9.4. Внутренний MQTT-протокол Шлюз↔︎Cloud (Gateway↔︎Cloud)

Внутренний протокол является служебным transport платформы и не отображается пользователю как обычный Профиль сопряжения Устройства.

Базовые требования:

  • MQTT over TLS;
  • человекочитаемый формат первой версии, предпочтительно JSON;
  • версионирование протокола и схемы сообщений;
  • расширяемость;
  • идентификаторы Шлюза (Gateway), Device и Parameter;
  • временная метка источника значения переменной (source timestamp);
  • качество/статус (quality/status);
  • сообщения телеметрии (telemetry messages);
  • команды;
  • результаты выполнения команд/ошибки выполнения;
  • correlation ID (уникальный идентификатор конкретной операции, позволяющий связать отправленную из Cloud команду с ответом Шлюза);
  • проверку текущей версии эксплуатационной конфигурации Шлюза, получение новой версии при её наличии и подтверждение результата её применения;

Документация на протокол должна входить в комплект поставки документации.

9.5. Аутентификация (Authentication) и ACL

Каждый Шлюз (Gateway) должен иметь индивидуальные учётные данные (credentials).

Использование общей учётной записи для всех Шлюзов (Gateway) запрещается.

Доступ Шлюза (Gateway) к топикам MQTT (topics) должен ограничиваться ACL брокера.

Предпочтительно использовать штатные возможности стандартного брокера (broker), например Dynamic Security/ACL Eclipse Mosquitto или эквивалент, вместо разработки собственной подсистемы аутентификации (auth subsystem).

mTLS допускается как развитие или как решение, выбранное на этапе ТЗ, но не является обязательным первым механизмом при наличии достаточного MQTT/TLS authentication/ACL.

9.6. Локальная рабочая конфигурация

Последняя применённая эксплуатационная конфигурация должна храниться локально постоянно и позволять Шлюзу (Gateway) продолжить предусмотренный режим работы после перезапуска (restart) без обязательного немедленного повторного получения конфигурации из Cloud.

Обновление конфигурации должно применяться только после её успешного получения и валидации; неудачное обновление не должно разрушать последнюю рабочую конфигурацию.

9.7. Границы Программного прототипа Шлюза

Если разделом 2.3 не принято иное решение, в объём разработки Программного прототипа Шлюза не входят:

  • локальное накопление телеметрии при потере связи с последующей передачей в RatioT.Cloud (Store-and-Forward);
  • автономное локальное выполнение Автоматизации (Automation);
  • встраиваемый программный агент для ПЛК/HMI;
  • разработка серийного аппаратного Шлюза (Gateway);
  • поддержка CAN/CANopen/J1939;
  • производственный процесс регистрации и привязки серийных Шлюзов к RatioT.Cloud (provisioning/factory workflow);
  • поддержка жизненного цикла серийно выпускаемых Шлюзов.

Архитектура программного агента Шлюза и внутреннего протокола взаимодействия с RatioT.Cloud не должна препятствовать последующему добавлению этих возможностей.

10. Сбор и хранение телеметрии

10.1. Единая модель данных

Телеметрия от разных Профилей сопряжения должна приводиться к единому каноническому контракту Параметра RatioT.Cloud.

Для каждого текущего значения Параметра должны быть доступны как минимум:

  • нормализованное значение (engineering value);
  • тип данных;
  • временная метка источника (source timestamp);
  • качество/статус (quality/status);
  • при наличии — исходное значение до преобразования (raw value), используемое для диагностики.

При необходимости для диагностики отдельно хранится серверная/приёмная временная метка (server/receive timestamp).

Нормализованное качество (quality) верхнего уровня должно различать как минимум:

  • Good;
  • Uncertain;
  • Bad.

При этом должна сохраняться доступная более детальная диагностическая информация, полученная от конкретного Профиля сопряжения или протокола.

Исходное значение (raw value) является диагностическим атрибутом и не обязано поддерживаться Профилями сопряжения, для которых преобразование исходного представления в нормализованное значение не применяется.

10.2. Временная модель

Внутреннее хранение и обмен временными метками (timestamps) выполняются в UTC.

Пользовательское отображение в Дашборде, журналах, трендах, отчётах и расписаниях выполняется в часовом поясе (timezone) соответствующего Пространства.

UTC должен оставаться доступен в API и диагностике, представление в локальной таймзоне - ответственность фронтенда и механизмов формирующих представление данных на бэкенде (например отчеты, оповещения и т.п).

10.3. Режимы сбора

Система должна поддерживать, в зависимости от возможностей конкретного Профиля сопряжения:

  • периодический сбор;
  • разные интервалы сбора для разных параметров одного Device;
  • обновление по событию/изменению (event/on-change);
  • зону нечувствительности (deadband).

Для периодического сбора должен быть поддержан рабочий диапазон примерно от 1 секунды до нескольких часов. Точный набор допустимых интервалов и профиль нагрузки определяется на этапе ТЗ.

Для Modbus разные интервалы реализуются группами/циклами опроса (polling groups/cycles), а не обязательным единым периодом на весь Device.

10.4. Архивирование

Для каждого отдельного параметра система должна поддерживать архивирование с дискретностью до 1 секунды.

Это требование не означает обязательную одновременную запись всех параметров всех Devices с частотой 1 Hz.

Глубина хранения архива должна ограничиваться тарифом/ограничениями (entitlement) Пространства и настраиваться в пределах доступного лимита.

Безопасное поведение при снижении лимита срока хранения (retention quota) регулируется разделом 19: существующая история не должна автоматически удаляться только из-за смены тарифа до явного приведения настройки Пространства к новому лимиту.

10.5. Агрегаты

Исторические данные должны поддерживать как минимум агрегаты:

  • Avg;
  • Min;
  • Max;
  • Last.

Агрегаты должны быть доступны по типовым временным интервалам. Конкретный способ предрасчёта, хранения и грануляции выбирает подрядчик с приоритетным использованием штатных механизмов AggreGate и выбранной СУБД.

10.6. Хранение и сжатие

Отдельный собственный compression engine RatioT.Cloud не требуется.

Эффективное хранение и сжатие исторических данных должны обеспечиваться штатными возможностями Tibbo AggreGate и/или выбранного хранилища данных (data storage).

Выбранное решение должно быть совместимо с HA, backup/restore, расчётом ресурсов (sizing) и нагрузочными требованиями настоящего ФТТ.

10.7. Целевая ёмкость Пространства

Архитектура должна поддерживать не менее 5000 Parameters на одно Пространство как минимальную целевую ёмкость модели и обработки.

Общие целевые NFR (target NFR) для 50 000+ Devices и 500 одновременных пользователей UI (simultaneous UI users) приведены в разделе 24 и не означают обязательное одновременное сочетание всех максимальных значений в одном экстремальном нагрузочном тесте (extreme load test).

10.8. Использование архива

Архив должен быть доступен:

  • трендам Дашборда;
  • отчётам;
  • пользовательскому экспорту телеметрии;
  • диагностическим и эксплуатационным функциям, предусмотренным ФТТ.

Automation первой версии работает только с текущими значениями Параметров и не должна предоставлять пользователю произвольные запросы к историческим данным Архива.

Если для сценария требуется сохраняемое промежуточное или вычисляемое значение, оно должно записываться в обычный Параметр Устройства, например с Профилем сопряжения Internal Space Store, и далее использоваться Automation как текущее значение.

10.9. Экспорт телеметрии

Пользователь должен иметь возможность выбрать параметры и период и выгрузить телеметрию.

Минимально:

  • CSV — прямой экспорт данных и заголовков без Jasper template;
  • XLSX и PDF — через соответствующие JasperReports templates/отчёты.

Для больших объёмов допускается асинхронная подготовка файла с последующим получением готового результата.

Отдельный proprietary binary/archive dump RatioT.Cloud для пользовательской телеметрии не требуется.

11. События, аварии и уведомления (Events, Alarms, Notifications)

11.1. Событие / Event

RatioT.Cloud должна содержать общесистемную подсистему событий, не зависящую от конкретного протокола подключения оборудования.

Событие / ``Event является неизменяемым зафиксированным фактом, который может формироваться Устройством, Параметром, Шлюзом , Пространством, ПОльзователем, Системой , Automation и другими сущностями платформы.

Журнал событий (Event Journal) должен строиться по append-only принципу: возникновение, изменение состояния, снятие, квитирование и иные существенные переходы фиксируются новыми связанными записями, а не перезаписью предыдущей истории.

Допускается хранение производного снимка (snapshot) текущего состояния (например сразу с учетом состояний типа подавлено или квитировано) для ускорения работы, если он полностью восстанавливается из журнала.

11.2. Авария / Alarm

Авария / ``Alarm является Событием (Event) с дополнительной аварийной семантикой и жизненным циклом.

Минимально должны поддерживаться состояния/переходы:

  • RAISED;
  • CLEARED;
  • ACKNOWLEDGED.

Физическое состояние аварийного условия и операторское квитирование должны учитываться независимо: Авария (Alarm) может быть уже снята по технологическому условию, но оставаться неквитированной.

Для Правила аварии (Alarm Rule) должен поддерживаться признак Acknowledgement`` ``required. Если он установлен, снятие физического условия не завершает операторский цикл до ACK уполномоченным пользователем.

Расширенные состояния вроде ручного закрытия/подавления (manual close/suppress) не являются обязательными для первой версии, но модель журнала не должна препятствовать их добавлению позднее.

11.3. Уровень важности / Severity

Первая версия должна поддерживать три базовых уровня:

  • Информационное;
  • Предупреждение;
  • Авария.

Модель должна допускать последующее расширение набора уровней важности (severity) без изменения базовой архитектуры Событий/Аварий (Event/Alarm).

11.4. Правила аварий / Alarm Rules

Правила аварий (Alarm Rules) должны использовать единый движок с Automation, но иметь отдельный специализированный пользовательский UX.

Правило аварии (Alarm Rule) должно поддерживать как минимум:

  • пороговые условия, включая типовые HH/H/L/LL;
  • дискретные булевы условия;
  • TON (задержка включения);
  • TOFF (задержка отключения);
  • гистерезис/зону нечувствительности (hysteresis/deadband);
  • подавление дребезга/частых переключений (debounce/anti-flapping);
  • защиту от потока аварий (alarm flood);
  • уровень важности (severity);
  • признак обязательного ACK;
  • формирование событий жизненного цикла (lifecycle) при возникновении и снятии условия.

Типовые Правила аварий (Alarm Rules) могут входить в Заготовку устройства с порогами по умолчанию (default thresholds) и другими настройками. После создания Device они должны становиться редактируемыми правилами конкретного экземпляра.

Обновление Заготовки устройства не должно молча перезаписывать локальные пользовательские переопределения (overrides) Правил аварий (Alarm Rules) существующего Устройства.

Сложные правила, использующие несколько Устройств или иные сущности Пространства, реализуются через общий движок Automation, а не отдельный специальный механизм аварий.

11.5. ACK и права доступа

Квитирование Аварии (Alarm) должно выполняться отдельным атомарным разрешением AcknowledgeAlarm.

Оно не должно быть жёстко связано с правом Control на оборудование. Стандартные пресеты могут выдавать эти права совместно, но модель должна допускать раздельное назначение.

Все операции ACK должны журналироваться с идентификацией пользователя, времени и Аварии (Alarm).

11.6. Маршрутизация уведомлений

Жизненный цикл Аварии (Alarm lifecycle), маршрутизация и фактическая доставка уведомлений должны быть разделены архитектурно.

Правило аварии (Alarm Rule) формирует Событие жизненного цикла (lifecycle Event). Реакции на RAISED, CLEARED, отсутствие ACK и другие события задаются отдельным механизмом маршрутизации/действий (routing/actions).

Получатели должны задаваться через Группы пользователей Пространства. Отдельную параллельную сущность «группа уведомлений» вводить не требуется.

Для каналов доставки, поддерживающих общих адресатов, могут дополнительно настраиваться адресаты самого канала, например групповой чат Telegram. Такие адресаты не являются пользователями Пространства и не требуют создания отдельной пользовательской группы.

Связь правил с получателями должна быть доступна как минимум:

  • из настроек конкретного Правила аварии (Alarm Rule);
  • из общей матрицы маршрутизации Пространства.

Подсистема уведомлений должна поддерживать дедупликацию, задержку/подавление (cooldown/suppression) и настраиваемую эскалацию, чтобы исключать избыточную повторную доставку при частых переключениях/потоке событий (flapping/flood).

11.7. Каналы доставки

В первую версию входят:

  • Web/in-app - “Центр уведомлений” (Notification Center) в веб- интерфейсе;
  • Web Push;
  • E-mail;
  • Telegram;
  • SMS.

Telegram должен поддерживать как персональную доставку, так и доставку (delivery) в групповые чаты Telegram (group chats)/диспетчерские группы.

MAX в первую версию не входит. Архитектура каналов должна позволять позднее добавить MAX или иной адаптер мессенджера (messenger adapter) без изменения логики Событий/Аварий (Event/Alarm) и маршрутизации (routing).

Web/in-app, Web Push, E-mail и Telegram являются базовыми каналами и не должны включаться/выключаться тарифом. SMS является отдельно лимитируемым расходуемым ресурсом тарифа.

11.8. Пользовательские настройки доставки

После маршрутизации на группы система определяет конкретных пользователей и применяет их персональные настройки доставки.

Каждый пользователь должен иметь личную матрицу вида тип сообщения × канал и возможность отключить внешние каналы доставки.

Персональная матрица доставки пользователя не применяется к общим адресатам канала, например групповым чатам Telegram.

Пространство не должно жёстко навязывать конкретный внешний канал отдельному пользователю.

Push в пользовательской матрице является абстрактным каналом. Один пользователь может иметь несколько Push-точек доставки (endpoints); конкретная транспортная технология (transport technology) не фиксируется данным ФТТ.

11.9. Центр уведомлений / Notification Center

Web/in-app должен включать постоянный Центр уведомлений (Notification Center), а не только временное всплывающее сообщение (transient popup).

Для пользовательского сообщения достаточно состояний:

  • прочитано;
  • непрочитано.

Статус прочитано не означает ACK связанной Аварии (Alarm).

Если Уведомление (Notification) связано с одной или несколькими неквитированными Авариями (Alarm), интерфейс должен позволять выполнить обычный ACK над связанными Авариями при наличии соответствующего разрешения.

Отдельная сущность «квитирование уведомления» не требуется.

Срок хранения (retention) Центра уведомлений (Notification Center) и срок хранения Журнала событий/аварий (Event/Alarm Journal) должны настраиваться независимо. Удаление пользовательского сообщения не должно удалять факт Аварии (Alarm) из эксплуатационного журнала.

11.10. Журнал доставки / Delivery Log и повторные попытки (retry)

Каждая попытка доставки должна фиксироваться отдельной записью Журнала доставки (Delivery Log) как минимум со следующими данными:

  • уведомление/сообщение (notification/message);
  • пользователь/адресат;
  • канал;
  • время;
  • статус;
  • техническая диагностика ошибки.

Минимальные статусы:

  • QUEUED;
  • SENT;
  • DELIVERED, если транспорт подтверждает доставку;
  • FAILED.

Количество повторных попыток (retry) и интервалы повторов должны настраиваться по каналам.

После исчерпания повторов доставка фиксируется как окончательно неуспешная.

При достижении критерия отказа самого канала платформа должна формировать системное Событие/Аварию (Event/Alarm). Такая Авария (Alarm) не должна создавать рекурсивный бесконечный цикл попыток через тот же неисправный канал.

Автоматическое резервное переключение (fallback) между различными каналами в первой версии не обязательно.

11.11. Срок хранения / Retention

Глубина хранения Журнала событий/аварий (Event/Alarm Journal) задаётся в Пространстве и ограничивается тарифными ограничениями (entitlement) Владельца Пространства.

Снижение срока хранения (retention), которое приведёт к удалению данных, должно сопровождаться явным предупреждением о необратимости и рекомендацией предварительного экспорта.

Правила безопасного поведения при снижении тарифа (tariff downgrade) приведены в разделе 19.

11.12. Разделение журналов

Журнал событий/аварий (Event/Alarm Journal), Центр уведомлений (Notification Center), Журнал доставки (Delivery Log) и Журнал аудита безопасности (Security Audit) являются разными журналами с разной предметной семантикой и сроком хранения (retention).

Они не должны подменять друг друга.

12. Автоматизация / Automation

12.1. Назначение

RatioT.Cloud должна содержать лёгкую SCADA-подобную No-Code подсистему Automation для пользовательских сценариев «Событие–Условие–Действие» (Event–Condition–Action), расписаний и последовательностей действий.

Automation не является SoftPLC, системой жёсткого реального времени (hard real-time) или долговременным движком рабочих процессов (durable workflow engine).

Правила аварий (Alarm Rules) и Правила Automation (Automation Rules) должны использовать единое ядро движка, но иметь разные специализированные пользовательские интерфейсы.

12.2. Среда выполнения / runtime

Подсистема Automation должна иметь общую интерпретируемую среду выполнения (runtime).

Логика сценария должна иметь исполняемое текстовое представление на языке общего назначения либо специализированном сценарном языке, сопоставимом по возможностям с Lua, JavaScript, Python, Groovy или аналогичным подходом.

Конкретный язык данным ФТТ не фиксируется.

No-Code представление является пользовательским источником истины (source of truth). Сгенерированный текст не редактируется пользователем и может быть доступен только для чтения (read-only) для диагностики разработчиком/поддержкой.

Реализация Automation как набора несвязанных жёстко заданных условий и действий без общей среды выполнения (runtime) не допускается.

12.3. No-Code редактор

Первый редактор не обязан быть Node-RED/n8n-подобным потоковым полотном (Flow Canvas). Допускается редактор правил (Rule Editor) или иной простой визуальный интерфейс поверх той же модели среды выполнения (runtime).

Архитектура должна позволять позднее заменить или дополнить редактор более развитым блочным/потоковым UI (block/flow) без замены исполнительного механизма.

Минимальные конструкции первого редактора:

  • сравнения =, !=, >, <, >=, <=;
  • вложенные AND / OR / NOT;
  • арифметика;
  • базовые строковые операции;
  • текущая дата/время и простые операции с ними;
  • преобразования типов;
  • безопасные стандартные математические функции;
  • IF / THEN / ELSE с вложенностью;
  • последовательность действий;
  • локальные переменные;
  • WAIT — приостановка текущего выполнения сценария на заданное время с последующим продолжением;
  • START — асинхронный запуск другого сценария без ожидания его завершения;
  • CALL — запуск другого сценария с ожиданием его завершения и возможностью получить возвращаемое значение;
  • RETURN — завершение текущего сценария с возвратом значения вызвавшему его сценарию.
  • чтение текущих значений Device;
  • запись параметров, доступных для записи (writable parameters), и вызов команд Device;
  • создание События (Event) или Аварии (Alarm) через общую подсистему Событий/Аварий.

Циклы могут поддерживаться средой выполнения (runtime) архитектурно, но не обязаны выводиться пользователю в первом No-Code UI.

12.4. Состояние и переменные

Локальные переменные принадлежат одному экземпляру выполнения (execution instance) и не являются долговременным состоянием.

Долговременное пользовательское состояние, уставки, вычисляемые значения и иные сохраняемые переменные по задумке системы должны храниться в Параметрах (Parameters) виртуальных Устройств с Профилем сопряжения Internal`` ``Space`` ``Store, в том числе в автоматически создаваемом Device «Переменные пространства».

Постоянные (persistent) переменные сценария и отдельная именованная конструкция CONST (named CONST) в первой версии не требуются - реализуются через виртуальное Устройство с Профилем сопряжения Internal`` ``Space`` ``Store.

Вычисляемый параметр реализуется как обычный Параметр (Parameter) Virtual/Internal Device, значение которого записывает Automation. После записи он без специальной семантики используется Дашбордом, Архивом (Archive), Авариями (Alarm), API и другими Automation.

12.5. Триггеры

Один сценарий должен поддерживать несколько независимых триггеров (triggers).

Обязательные типы первой версии:

  • изменение Параметра (Parameter) Device;
  • событие жизненного цикла События/Аварии (Event/Alarm lifecycle Event);
  • периодическое расписание;
  • календарное расписание;
  • ручной запуск.

Для автоматического триггера (trigger) среда выполнения (runtime) создаёт доступный только для чтения (read-only) Контекст срабатывания / Trigger Con``text, содержащий тип, временную метку (timestamp), источник и относящиеся к срабатыванию данные, например ID События/Параметра (Event/Parameter ID), старое/новое значение (old/new value).

Пользовательские входные параметры (input parameters) сценария применяются для ручного запуска, START и CALL, но не заполняются автоматически контекстом триггера (trigger).

Автоматический запуск по триггерам (triggers) должен иметь отдельный переключатель. Его отключение не должно запрещать ручной запуск, START и CALL, а уже работающие экземпляры выполнения (instances) продолжают выполнение.

Каждый триггер (trigger) также должен иметь возможность отдельного включения/отключения.

12.6. Расписания

Первая версия должна поддерживать:

  • периодический запуск через интервал N (interval), с минимальным рабочим интервалом около 1 секунды;
  • календарный запуск по времени суток, дням недели и/или конкретным датам.

Секундная периодика является приблизительной и не содержит гарантии реального времени (real-time guarantee).

Календарное расписание (Calendar schedule) интерпретируется в часовом поясе (timezone) Пространства; внутренние временные метки (timestamps) хранятся в UTC.

Пропущенные расписания (missed schedules) во время остановки среды выполнения/server не догоняются и не ставятся автоматически в очередь.

12.7. START, CALL и RETURN

START должен асинхронно запускать другой сценарий без ожидания его завершения.

CALL должен запускать сценарий с ожиданием завершения и возвратом одного значения поддерживаемого типа, включая структурированное значение.

Сценарий может иметь именованные входные параметры (input parameters). Для ручного запуска форма ввода должна строиться по их описанию.

Ссылки между сценариями должны храниться по стабильным идентификаторам, независимо от пользовательского имени.

12.8. Ошибки действий

По умолчанию ошибка действия прекращает текущий экземпляр выполнения (execution instance).

Для конкретного действия должна быть доступна настройка продолжить при ошибке / ``continue`` ``on`` ``error.

Ошибка фиксируется стандартным техническим журналированием (logging). Ошибки, требующие внимания оператора, могут дополнительно порождать системное Событие/Аварию (Event/Alarm).

Полноценные пользовательские try/catch и сложный отладчик (debugger) в первой версии не требуются.

12.9. Управляющие операции и доступность канала

Automation не должна реализовывать отдельную протокольную проверку соединения (connection) Modbus/MQTT перед каждой командой.

Запись Параметра (Parameter) и выполнение команды Device выполняются через тот же единый механизм Device/Profile, что используется другими функциями RatioT.Cloud.

Профиль сопряжения должен учитывать текущее состояние соединения/сессии и возвращать нормализованный результат операции, например:

  • confirmed;
  • unavailable;
  • timeout;
  • failed.

Automation ожидает итог операции до тайм-аута (timeout). Тайм-аут по умолчанию (default timeout) задаётся профилем, конкретное действие может его переопределить.

Отдельная последовательность проверка соединения → команда / ``check`` ``connection`` → ``command не требуется, поскольку она дублирует логику Профиля (Profile logic) и создаёт состояние гонки (race condition).

Аудит управляющей операции должен позволять определить, что инициатором являлся конкретный сценарий Automation, целевой Device/операцию, время и результат.

12.10. Deploy и версии

Редактирование сценария не должно изменять выполнение в продуктивной эксплуатации (production execution) до явной операции Deploy`` / Применить.

После Deploy новая версия атомарно используется для следующих запусков. Уже работающие экземпляры выполнения (instances) продолжают исполнение той версии, с которой были запущены.

Должны храниться:

  • текущая активная развёрнутая версия (active deployed version);
  • три предыдущие развёрнутые версии (deployed versions).

Загрузка предыдущей версии в редактор не делает её активной до нового Deploy.

Отдельный пробный запуск или отладчик (dry-run/debugger) неприменённого черновика (draft) в первой версии не требуется.

12.11. Параллельность / Concurrency

Сценарий должен поддерживать три режима повторного запуска:

  • Parallel;
  • Single;
  • Restart.

В режиме Restart предыдущий экземпляр выполнения (instance) завершается штатно с отдельным результатом, а не как ошибка.

Автоматическая очередь ожидающих запусков не требуется.

12.12. Ограничения исполнения

Для сценария задаётся максимальное фактическое время выполнения (wall-clock time): конечное значение или ∞.

∞ означает отсутствие пользовательского ограничения по длительности, но не отменяет watchdog/защиту ресурсов среды выполнения (resource protection runtime).

Экземпляры выполнения (Execution instances) не сериализуются и не восстанавливаются после перезапуска (restart) Cloud/среды выполнения (runtime).

Среда выполнения (Runtime) не гарантирует порядок почти одновременных триггеров (triggers).

Технологическая последовательность, необходимая пользователю, должна задаваться логикой сценария.

12.13. Лимит живых экземпляров выполнения (instances)

Тариф определяет максимальное число одновременно живых экземпляров выполнения Automation (instances) на Пространство.

Администратор Пространства может задать меньший внутренний лимит, но не выше тарифного максимума (tariff max).

В лимит входят также экземпляры выполнения (instances) в WAIT и ожидании CALL.

При превышении действующего лимита (effective limit) новый запуск:

  • не создаётся;
  • не ставится в очередь;
  • увеличивает счётчик отброшенных/пропущенных триггеров (dropped/skipped triggers);
  • фиксируется в техническом журнале;
  • формирует системное Событие/Аварию (Event/Alarm).

Движок Аварий/Событий (Alarm/Event Engine) не должен расходовать эту пользовательскую квоту Automation (quota).

12.14. Монитор исполнения

Пользователь с соответствующим доступом должен видеть минимальный список текущих экземпляров выполнения Automation (instances) как минимум с полями:

  • сценарий (scenario);
  • время запуска (start time);
  • источник триггера (trigger source);
  • длительность (duration);
  • базовое состояние (basic state: RUNNING, WAITING, ожидание CALL или аналогичное).

Должна быть доступна команда остановки экземпляра выполнения (instance).

Пошаговый отладчик (debugger), просмотр локальных переменных (local variables) и UI стека вызовов (stack trace) в первую версию не входят.

12.15. Техническое журналирование

Среда выполнения Automation (Automation Runtime) использует стандартный механизм технического журналирования (logging) выбранной платформы/языка с уровнями не ниже:

  • DEBUG;
  • INFO;
  • WARNING;
  • ERROR;
  • CRITICAL.

Минимальный уровень по умолчанию (Default minimum level) сценария — INFO.

Детальная трассировка выполнения (execution trace) должна относиться к DEBUG и не создавать постоянный поток INFO-записей при штатной эксплуатации.

Техническое журналирование Automation отделено от Журнала событий (Event Journal), Журнала аудита безопасности (Security Audit) и Журнала доставки уведомлений (Notification Delivery Log).

12.16. Ограниченная “операционная поверхность”

Среда выполнения Automation (Automation Runtime) может выполнять только явно предусмотренные операции внутри своего Пространства.

В первой версии среда выполнения (runtime) не получает:

  • произвольный HTTP/MQTT/socket-клиент;
  • произвольный внешний сетевой доступ (network access);
  • shell/execute;
  • доступ к файловой системе/ОС (filesystem/OS access);
  • API администрирования платформы (platform administration API);
  • операции создания/удаления Пространства, Users, Groups, ACL, Дашборда и иные административные изменения;
  • прямой произвольный доступ к архивным данным.

Внешняя административная автоматизация выполняется через Application API, а не пользовательским Automation Runtime.

12.17. Владение сценарием и RBAC

После Deploy сценарий Automation является объектом Пространства и выполняется независимо от автора.

Удаление автора из Пространства, изменение его групп или удаление его аккаунта не должно автоматически останавливать сценарий в продуктивной эксплуатации (production scenario).

RBAC определяет, кто может просматривать, редактировать, применять (Deploy) и вручную запускать сценарии.

Каждый экземпляр скрипта выполнения Automation должен быть однозначно связан с Пространством, которому принадлежит сценарий, и иметь доступ только к сущностям этого Пространства.

При применении сценария (Deploy) backend должен проверять, что выполняющий Deploy пользователь имеет необходимые права на используемые сценарием Устройства, Параметры и Команды, включая Control для управляющих операций. После успешного Deploy сценарий выполняется как объект Пространства и последующие изменения прав его автора сами по себе не изменяют и не останавливают уже применённый сценарий.

12.18. Взаимодействие с режимом обслуживания / Maintenance interaction

В режиме обслуживания (maintenance mode) новые выполнения Automation (executions) не запускаются.

Существующим экземплярам выполнения (instances) по умолчанию должна быть предоставлена возможность штатно завершиться, насколько это допускает процедура обслуживания.

Администратор должен видеть остаточную активность Automation и иметь единую операцию принудительной остановки всех живых экземпляров выполнения (instances) с корректной фиксацией результата и аудита.

13. Дашборд (Dashboard) и визуализация

13.1. Роль Дашборда (Dashboard)

Дашборд является основной пользовательской рабочей областью RatioT.Cloud и представляет собой законченное автоматизированное рабочее место оператора/технолога или информационную панель ситуационного центра, например.

После самостоятельной регистрации пользователя должны автоматически создаваться первое Пространство и первый Дашборд. Стартовый Дашборд должен позволять начать работу без предварительного изучения внутренней архитектуры платформы и подсказывать добавление готового Device/визуализации.

Дашборд принадлежит ровно одному Пространству.

Device существует независимо от Дашборда. Удаление визуального элемента не удаляет Device; один Device может использоваться на нескольких Дашбордах и несколькими визуальными представлениями.

13.2. Навигация

Основные рабочие области должны быть доступны через единую панель навигации (navbar), включая как минимум:

  • Дашборды (Dashboards);
  • Библиотеки (Libraries);
  • События (Events);
  • Automation;
  • Пользователи/доступ (Users/Access);
  • Настройки (Settings);
  • дополнительные функции, доступные по тарифу (entitlement).

Дашборд не обязан соответствовать ветке Объектов (Asset). Один Дашборд может использовать разрешённые данные любых Devices своего Пространства.

Встроенная обязательная иерархическая/drill-down модель Дашборда не требуется. Переходы между Дашбордами создаются обычными ссылками/действиями и могут формировать произвольный граф.

Каждый Дашборд должен иметь стабильный URL.

13.3. Просмотр/редактирование (View/Edit)

Эксплуатация и конструирование выполняются на одном Дашборде в двух состояниях:

  • Просмотр (View);
  • Редактирование (Edit).

Режим редактирования (Edit mode) добавляет drag&drop, изменение размера (resize), свойства, привязки и другие средства редактирования, но не должен превращать Дашборд в отдельный несвязанный продуктовый редактор.

Должны поддерживаться сетка/выравнивание (grid/alignment) и возможность блокировки (lock) элементов от случайного перемещения.

13.4. Добавление Device и Parameter

Из Дашборда пользователь должен иметь быстрый вход в общий каталог Библиотеки (Library).

При переносе целого Device система должна предложить или применить подходящую комплексную Визуальную заготовку (Visual Template)/представление.

При переносе отдельного смыслового Параметра (semantic Parameter) система должна сразу создавать простое представление по умолчанию без обязательного дополнительного диалога.

Смена представления должна открывать каталог Визуальных заготовок (Visual Templates), отфильтрованный по смысловой/типовой совместимости (semantic/type compatibility).

Автоматическое сопоставление совместимых Параметров (Parameters) допускается как UX-оптимизация, но не должно неявно создавать Device или ограничивать Визуальную заготовку (Visual Template) одним Device.

Копирование/вставка (copy/paste) визуального элемента копирует представление и привязки (bindings), но не создаёт новый Device (сразу после клонирования на обоих экземплярах визуального элемента отображаются данные одних и тех же параметров).

13.5. Адаптивная и мобильная компоновка (responsive/mobile layout)

Текущий проект включает один адаптивный web frontend для desktop/tablet/mobile. Нативные приложения Android/iOS (native applications) в объём работ (scope) не входят.

Дашборд должен иметь:

  • автоматическую адаптивную компоновку (auto-responsive layout);
  • возможность отдельной мобильной компоновки (mobile layout) для того же набора элементов.

Если мобильная компоновка (mobile layout) не задана, должна использоваться автоматическая адаптивная компоновка по умолчанию (auto-responsive fallback).

Полный комплект UX/UI первой версии должен быть спроектирован в рамках отдельного этапа ТЗ+UX/UI и передан в Figma для desktop и mobile-представлений.

13.6. Киоск/полноэкранный режим (Kiosk/fullscreen)

Дашборд должен поддерживать полноэкранный/киоск-режим (fullscreen/kiosk mode) по стабильному URL.

Киоск-режим (Kiosk) не создаёт анонимный/публичный доступ (anonymous/public access): аутентификация (authentication), сессия (session) и RBAC продолжают действовать.

Публичный анонимный Дашборд (anonymous Dashboard) в первую версию не входит.

13.7. Дашборд (Dashboard) и RBAC

Дашборд проектируется как целое рабочее место для конкретной группы/роли.

RBAC на уровне виджетов (per-widget RBAC), при котором на одном Дашборде у разных пользователей активны разные отдельные кнопки/виджеты (buttons/widgets), в рамках этой разработки не требуется.

Для самого Дашборда используются права View и Edit. Выполнение управляющих действий через Виджеты Дашборда определяется правом Control на соответствующие Устройства/Объекты и не требует отдельного разрешения на уровне Дашборда.

При назначении группе доступа к Дашборду должны быть согласованы необходимые права доступа на связанные Devices/Объекты (Assets) - пользователь следит за этим самостоятельно.

Но backend в любом случае обязан повторно проверять Read``/``Control при чтении данных и при управляющих операциях, чтобы Дашборд не мог случайно повысить полномочия пользователя.

13.8 Виджет (Widget)

Это базовый системный визуальный компонент Дашборда, предназначенный для отображения данных или выполнения пользовательского управляющего действия. Виджет имеет настраиваемые свойства и привязки к Параметрам и Командам Устройств. Сам по себе Виджет не является библиотечной сущностью. Настроенные композиции одного или нескольких Виджетов могут сохраняться и повторно использоваться в виде Визуальных заготовок (Visual Templates).

13.8.1 Минимальный набор встроенных виджетов (widgets)

Первая версия должна включать как минимум:

  • сигнальные лампы/светофоры/бейджи;
  • числовые значения (numeric values);
  • стрелочные шкалы (gauges);
  • секторные шкалы (gauges);
  • индикаторы прогресса/уровня (progress/level bars);
  • импульсные кнопки (push buttons);
  • фиксируемые кнопки (latching buttons);
  • переключатели/ползунки (toggles/sliders);
  • селекторы/перечисления (selectors/Enum);
  • ввод аналоговой уставки (analog setpoint input).

Для изменяющих или потенциально опасных управляющих операций должно поддерживаться настраиваемое подтверждение (confirmation) перед отправкой команды/значения.

13.9. Визуальные заготовки / Visual Templates

Визуальные заготовки (Visual Templates), определённые в разделе 6.5, используются для быстрого размещения на Дашборде повторно используемых визуальных представлений из одного или нескольких Виджетов.

Визуальная заготовка может представлять, например:

  • один Параметр;
  • целое Устройство с отображением нескольких его Параметров и Команд;
  • технологический узел или фрагмент мнемосхемы, использующий Параметры и Команды нескольких Устройств.

При добавлении Визуальной заготовки на Дашборд её входы должны быть связаны с конкретными Параметрами и Командами Экземпляров устройств данного Пространства.

Система должна помогать пользователю подобрать совместимые Параметры, Команды и Устройства на основании входного контракта Визуальной заготовки. При наличии однозначного соответствия допускается автоматическое сопоставление с возможностью проверки и изменения пользователем.

Справочный список рекомендуемых SKU/Заготовок устройств может использоваться для упрощения такого подбора, но не должен ограничивать применение Визуальной заготовки только указанными моделями оборудования.

Размещение Визуальной заготовки на Дашборде не создаёт новые Экземпляры устройств и не изменяет структуру Объектов (Asset) Пространства.

13.10. SVG HMI

SVG создаётся внешним редактором, например Inkscape, и загружается в RatioT.Cloud.

В SVG используются стабильные идентификаторы элементов (element IDs).

Платформа должна позволять связывать идентификаторы (IDs) с Параметрами/Командами (Parameters/Commands) и управлять как минимум:

  • текстом/значением (text/value);
  • цветом/состоянием (color/state);
  • прозрачностью (opacity);
  • видимостью (visibility);
  • базовыми состояниями анимации (basic animation states);
  • поведением по клику/управлению (click/control behavior).

Встроенный полноценный редактор SVG (SVG editor) и отдельный редактор анимации (animation editor) в первой версии платформы не требуются.

13.11. GIS/картографический виджет (map widget)

Базовый картографический виджет (map widget) должен быть построен на Leaflet либо эквивалентной открытой библиотеке.

Источник тайлов (tile source) должен быть конфигурируемым стандартным XYZ. Допускаются OSM-совместимый источник и tile proxy Заказчика для иных источников, но при этом специальная интеграция с Yandex Maps API не требуется.

Минимально карта должна поддерживать:

  • маркеры объектов (Asset) и устройств (если они наследуют координаты Объекта) по сохранённым координатам (coordinates);
  • всплывающее окно (popup)/переход к Объекту/Device/Дашборду (Asset/Device/Dashboard);
  • отдельное различение состояния соединения/доступности (connection/availability state);
  • отдельное различение наличия и уровня важности (severity) активной Аварии (Alarm).

Конкретное визуальное объединение признаков определяется UX/UI.

Геозоны, маршруты и сложный редактор геометрии (geometry editor) в эту разработку не входят.

13.12. Тренды / Trends

Виджет трендов (Trend widget) должен поддерживать как минимум:

  • несколько Параметров (Parameters);
  • выбор периода;
  • панорамирование/масштабирование (pan/zoom);
  • легенду (legend);
  • значения/статистику (statistics) по видимому диапазону;
  • несколько осей Y (multiple Y axes);
  • наложение порогов Аварии/Предупреждения (Alarm/Warning thresholds);
  • экспорт видимого диапазона (export visible range);
  • работу с исходным архивом (raw archive) и агрегатами (aggregates).

Специализированный пакет аналитики исторических данных (historian analytics package) не требуется.

13.13. Диагностический просмотр Экземпляра устройства

Стандартный диагностический просмотр текущих Параметров Экземпляра устройства, включая просмотр текущих значений и выполнение разрешённых операций записи, определяется разделом 7.10.

Данный интерфейс является самостоятельным средством работы с Экземпляром устройства и не зависит от наличия или состава Дашбордов.

13.14. Локализация

Первая поставка содержит русский и английский UI.

Все системные строки frontend должны быть вынесены в документированные внешние словари/файлы ресурсов (resource files) так, чтобы добавление нового языка не требовало изменения программной логики и переработки экранов.

Пользовательские названия Объектов (Asset), Device, Дашбордов (Dashboard) и других пользовательских сущностей автоматически не переводятся и не транслитерируются.

Отсутствующий перевод отдельных строк не должен ломать интерфейс.

13.15. Поддерживаемые браузеры

Web frontend должен штатно работать в актуальных распространённых версиях Chrome, Edge и Firefox.

Точная политика поддерживаемых версий (supported-version policy) фиксируется на этапе ТЗ.

13.16. Потеря связи frontend↔︎backend

При потере связи с backend frontend должен явно показывать недоступность.

Команда или изменение состояния не должны отображаться как успешно принятые, если backend не подтвердил операцию.

После восстановления соединения frontend должен перечитать актуальное состояние и сохранить текущий рабочий контекст, если соответствующий маршрут/ресурс (route/resource) остаётся доступен пользователю.

Полноценный автономный режим (offline-mode) не требуется.

14. Пользователи, регистрация, RBAC и владение

14.1. Пользовательская модель

Пользовательская учётная запись является глобальной в Платформе.

Каждая учётная запись пользователя должна иметь внутренний неизменяемый уникальный идентификатор (User ID), используемый для связей между сущностями и внутренней идентификации пользователя. Логин, номер телефона, e-mail, имя, фамилия и другие пользовательские атрибуты не должны использоваться в качестве такого идентификатора и могут изменяться в установленном порядке без нарушения существующих связей, прав доступа, владения и истории действий пользователя.

Один пользователь может:

  • владеть одним или несколькими Пространствами в пределах своего тарифа;
  • быть участником других Пространств;
  • состоять в разных группах и иметь разные итоговые права (effective permissions) в каждом Пространстве.

Владелец Пространства является специальным свойством Пространства, а не обычной группой или ролью.

14.2. Регистрация SaaS

Первая версия должна использовать phone-first registration model.

Обязательные требования:

  • телефон является обязательным primary contact;
  • номер подтверждается SMS-code;
  • e-mail является optional contact;
  • указанный e-mail должен подтверждаться кодом/link/test message;
  • после успешной регистрации пользователю назначается Default tariff;
  • автоматически создаётся первое Пространство;
  • автоматически создаётся первый Дашборд.

Security SMS для регистрации, смены телефона, восстановления доступа и аналогичных security operations не должны расходовать commercial SMS notification quota.

14.3. Базовые группы Пространства

При создании Пространства автоматически создаются редактируемые группы по умолчанию (preset groups):

  • Мастера;
  • Операторы;
  • Наблюдатели.

Они получают разумные стартовые наборы прав, но Владелец (Owner)/уполномоченный администратор может изменять их.

Также должны поддерживаться произвольные дополнительные группы пользователей.

Владелец (Owner) не является группой.

14.4. Many-to-many RBAC

Пользователь может состоять в нескольких группах.

Один resource может иметь несколько ACL entries вида:

Группа (Group) → набор прав (permissions)

Явный запрет (DENY) не вводится.

Итоговые права (effective permissions) пользователя определяются суммой разрешений всех его групп.

14.5. Права на Объект (Asset) и Device

Для Объектов/Device (Asset/Device) используются как минимум:

  • Read — просмотр состояния/телеметрии;
  • Control — выполнение разрешённых commands и изменение эксплуатационных writable values;
  • Manage — изменение конфигурации, структуры, bindings и настроек.

ACL на Объект (Asset) наследуется вниз на дочерние Объекты (Assets) и Devices.

Разрешения, полученные по нескольким группам и путям наследования, суммируются.

Исходная сущность «Группа устройств» как отдельный ACL-ресурс не создаётся: её назначение выполняет поддерево Объектов (Asset subtree).

14.6. Права на Дашборд (Dashboard)

Для Дашборда используются как минимум:

  • View;
  • Edit.

Право Дашборда (Dashboard permission) не заменяет базовые права на Devices/Объекты (Assets). Backend должен отдельно проверять фактические права на данные и управляющие операции.

Per-widget RBAC не требуется.

14.7. Административные права Пространства

Административные функции Пространства не наследуются через дерево Объектов (Asset).

Отдельными разрешениями уровня Пространства (Space-level permissions) должны управляться как минимум:

  • пользователи и группы;
  • Библиотека Пространства (Space Library);
  • Automation;
  • настройки Пространства.

Исходное требование Группа × Ресурс → Панель настроек реализуется через такие функциональные административные права. Отдельный ACL-object «Панель настроек» не создаётся.

UI должен показывать пользователю только доступные ему административные разделы, но сокрытие UI не заменяет backend permission checks.

14.8. Специальные права (permissions)

Право AcknowledgeAlarm должно существовать отдельно от Control.

Набор атомарных административных и предметных прав (permissions) уточняется на этапе ТЗ, но архитектура должна позволять назначать их группам независимо в пределах принятой модели allow-only.

14.9. Тарифные ограничения (entitlement) и RBAC

Тарифные ограничения (entitlement) и пользовательские права (permissions) являются независимыми ограничителями.

Effective capability определяется как:

тарифные ограничения Пространства/Владельца (``Space``/``Owner`` ``entitlement``) ``AND`` права пользователя (``User`` ``RBAC`` ``permission``).

Backend обязан проверять оба ограничения независимо от состояния UI.

14.10. Управление членством и группами

Уполномоченный пользователь должен иметь возможность:

  • приглашать/добавлять пользователей в Пространство;
  • удалять их из Пространства;
  • создавать/редактировать/удалять группы;
  • добавлять/удалять пользователей из групп;
  • назначать/изменять ACL на resources;
  • изменять административные разрешения уровня Пространства (Space-level permissions).

Конкретный процесс приглашения/подтверждения личности (invitation/identity confirmation workflow) прорабатывается на этапе ТЗ при сохранении глобальной пользовательской модели.

14.11. Передача владения Пространством

Владелец (Owner) должен иметь возможность передать владение другому существующему пользователю RatioT.Cloud.

Новый Владелец (Owner) не обязан заранее быть участником Пространства (member). При необходимости добавление пользователя в Пространство и передача владения (transfer) выполняются одной атомарной операцией.

Перед передачей владения (transfer) обязательно выполняется предварительная проверка (preflight) тарифных прав/лимитов (entitlement/quotas) нового Владельца (Owner).

Transfer блокируется, если, например:

  • новый Владелец (Owner) не может владеть ещё одним Пространством;
  • используемые функции Пространства недоступны по его тарифным ограничениям (entitlement);
  • фактическое количество Devices/Parameters/Users, срок хранения (retention) или другие лимиты превышают допустимые значения.

Система должна показать конкретный перечень препятствий.

Несовместимая передача владения (transfer) не должна автоматически обрезать функции, удалять данные или переводить Пространство в ограниченный режим (Restricted mode) как побочный эффект операции.

14.12. Удаление аккаунта

Пользователь не может удалить свою учётную запись (account), пока владеет хотя бы одним Пространством.

Перед удалением аккаунта собственные Пространства должны быть:

  • переданы другому Владельцу (Owner); либо
  • удалены по штатной процедуре удаления Пространства.

Детали удаления персональных данных и security retention уточняются в разделе 25 и на этапе ТЗ.

14.13. Аудит RBAC

Все операции, изменяющие модель доступа и административные полномочия, должны попадать в Security Audit.

Минимально журналируются:

  • добавление пользователя в Пространство / удаление пользователя из Пространства;
  • добавление/удаление пользователя из групп;
  • создание/изменение/удаление групп;
  • назначение/изменение/удаление ACL;
  • изменение разрешений уровня Пространства (Space-level permissions);
  • transfer ownership;
  • критичные административные действия.

Запись аудита (Audit record) должна позволять определить инициатора (actor), время, субъект/ресурс (subject/resource) и характер изменения.

15. Рабочая область интегратора / Integrator Workspace

15.1. Назначение

Integrator Workspace является отдельной межпространственной (cross-space) сервисной рабочей областью для организаций-интеграторов, обслуживающих несколько клиентских Пространств.

Он входит в первую версию продукта как отдельная функция, доступная по тарифу (entitlement).

Обычный Дашборд при этом остаётся объектом одного Пространства.

15.2. Делегирование доступа

Клиент должен делегировать и отзывать доступ организации-интегратору как стабильному субъекту, а не управлять каждым сотрудником интегратора отдельно.

Интегратор самостоятельно управляет своим персоналом и назначением конкретных людей к клиентским Пространствам.

Конкретная реализация IAM/делегирования (delegation) выбирается на этапе ТЗ/прототипа с приоритетом штатных механизмов Tibbo AggreGate и минимального дополнительного кода.

Журнал аудита безопасности (Security Audit) должен фиксировать фактического пользователя (human actor), выполнившего действие.

15.3. Основной интерфейс

Integrator Workspace должен показывать как минимум:

  • список делегированных клиентских Пространств;
  • поиск и фильтрацию;
  • базовое эксплуатационное состояние Пространства (operational state);
  • активные аварии/проблемы (active alarms/problems);
  • переход внутрь доступного Пространства в разрешённом контексте.

15.4. Межпространственный (cross-space) аварийный обзор

Должен существовать общий межпространственный (cross-space) список активных Аварий/Событий (active Alarm/Event) для доступных клиентских Пространств с фильтрацией и переходом к источнику.

Копирование клиентских данных в отдельное Пространство интегратора для этого не требуется.

Универсальный конструктор межпространственных Дашбордов (cross-space Dashboard Builder) в первую версию не входит.

15.5. Ограничения доступа

Тарифные ограничения (entitlement) определяют доступность функции Integrator Workspace и максимальное число клиентских Пространств согласно тарифу.

Фактический доступ к конкретным клиентским Пространствам определяется делегированными правами/ACL и не возникает только из наличия тарифного права (entitlement).

Тариф интегратора не должен использовать число его сотрудников как лимит оплачиваемых мест (billing seat limit); управление персоналом является задачей IAM/RBAC.

16. SuperAdmin

16.1. Модель SuperAdmin

SuperAdmin является платформенной привилегией обычного пользовательского аккаунта, а не отдельным типом пользователя.

Привилегия должна назначаться и отзываться без удаления учётной записи (account) и без влияния на его обычное участие в Пространствах.

В системе должна существовать неудаляемая системная учётная запись admin с неудаляемой привилегией SuperAdmin для гарантированного административного доступа как частный случай.

16.2. Область полномочий

SuperAdmin должен иметь platform-level функции, включая как минимум:

  • управление users/учётными записями (accounts) в предусмотренных границах;
  • управление Пространствами;
  • создание и назначение SaaS tariffs;
  • управление On-Premise licenses;
  • просмотр operational state программного контура;
  • maintenance operations;
  • иные глобальные настройки платформы, определённые ТЗ.

16.3. Сервисный доступ в Пространство

SuperAdmin должен иметь сервисный доступ внутрь любого клиентского Пространства без предварительного приглашения.

При этом он всегда действует от собственной учётной записи (account).

Скрытая impersonation под клиента не требуется и не должна быть обязательным механизмом поддержки.

Факт входа и все выполняемые действия должны фиксироваться в Security Audit.

16.4. Эксплуатационный обзор / Operational overview

Интерфейс SuperAdmin должен показывать состояние критических программных компонентов/узлов (software components/nodes), достаточное для эксплуатационной диагностики RatioT.Cloud.

Полноценные длительные Дашборды CPU/RAM/disk/network и исторический мониторинг инфраструктуры (infrastructure monitoring) не являются функцией RatioT.Cloud и могут обеспечиваться внешними средствами ДИТ, например Zabbix/Grafana.

Точные индикаторы работоспособности (health indicators) определяются совместно с разделом 23.

16.5. Аудит платформенных операций

Назначение/отзыв SuperAdmin и критичные platform-level действия должны неизменно журналироваться в Security Audit с actor, временем, resource/subject и результатом операции.

17. Frontend/backend contract и Application API

17.1. Разделение frontend и backend

Backend RatioT.Cloud реализуется на Tibbo AggreGate Server.

Frontend должен быть отдельным адаптивным web application. Конкретный frontend stack выбирает подрядчик.

На этапе разработки ТЗ подрядчик должен сформировать формальный контракт frontend/backend, достаточный для независимой разработки frontend на имитационном backend (mock backend) и backend без жёсткой зависимости от конкретной реализации UI.

17.2. Единая бизнес-логика backend

Web frontend и внешние пользовательские приложения/скрипты должны использовать один документированный Application/REST API поверх той же backend-бизнес-логики.

Нельзя создавать отдельные несогласованные реализации RBAC, тарифных ограничений (entitlement), валидации (validation) и предметных правил для web UI и API.

Все проверки backend (backend checks) должны выполняться независимо от поведения frontend.

17.3. Полнота Application API

Все предметные пользовательские операции управления и конфигурирования, доступные через web frontend, должны быть доступны внешним приложениям и пользовательским скриптам через документированный Application API, если конкретная операция не является чисто визуальной функцией клиента.

В API должны входить, в частности, операции конфигурации Дашбордов (Dashboard).

Отдельный REST API для Дашбордов (Dashboard) не требуется и его функционал закрывается общим Application API.

17.4. Аутентификация / Authentication

Основная модель аутентификации API (API authentication) первой версии:

  1. неаутентифицированный клиент проходит штатную процедуру аутентификации пользователя, включая второй фактор (2FA), если он требуется действующей политикой безопасности;
  2. после успешной аутентификации клиент получает токен сессии/доступа (session/access token);
  3. последующие предметные запросы используют Authorization``: ``Bearer`` <``token``>.

Технические исключения для регистрации/восстановления (registration/recovery) согласуются в ТЗ и не должны создавать альтернативную модель прав.

Отдельный административный API только для bash/Python не создаётся.

Механизм API-key/service account не является обязательным требованием первой версии, если иное не будет зафиксировано в ТЗ.

17.5. RBAC и тарифные ограничения (entitlement)

Application API обязан использовать ту же модель RBAC и entitlement, что web frontend.

Наличие прямого API endpoint не должно позволять обойти:

  • изоляцию Пространств (Space isolation);
  • права на Объекты/Device (Asset/Device permissions);
  • права Дашбордов (Dashboard permissions);
  • административные разрешения Пространства;
  • тарифные/лицензионные ограничения (entitlement);
  • validation/business rules.

17.6. Документация API

Поставка должна включать актуальную документацию Application API, достаточную для независимой интеграции и написания пользовательских скриптов.

Документация должна включать как минимум:

  • процесс аутентификации (authentication flow);
  • основные ресурсы/сущности (main resources/entities);
  • operations;
  • модели запросов/ответов (request/response models);
  • ошибки/статусы (errors/statuses);
  • правила пагинации/фильтрации (pagination/filtering conventions), если применимо;
  • правила версионирования/совместимости (versioning/compatibility rules);
  • примеры типовых вызовов.

Предпочтительно использовать машиночитаемую спецификацию API (machine-readable API specification), если выбранный стек это поддерживает.

17.7. Adaptive web frontend

Текущий проект содержит один responsive web client для desktop/tablet/mobile.

Нативные мобильные приложения в scope не входят.

Frontend должен использовать требования раздела 13 по responsive/mobile layout, localization и reconnect behavior.

17.8. Потеря backend connection

Frontend/backend contract должен обеспечивать реализацию поведения, установленного разделом 13.16: обнаружение недоступности backend/session, отсутствие ложного подтверждения неподтверждённых операций и повторное чтение актуального состояния после восстановления связи.

Offline-mode не требуется.

18. Отчётность и экспорт

18.1. Общая модель

RatioT.Cloud не должна содержать собственный универсальный конструктор BI-отчётов (BI/report designer).

Для типовой отчётности подрядчик должен использовать предоставляемые Aggregate средства и подготовить требуемые базовые шаблоны (templates).

Базовые шаблоны отчётов (report templates) являются частью поставки, а не пользовательской библиотекой RatioT.Cloud.

18.2. Форматы

Минимально должны поддерживаться:

  • PDF — через Jasper template;
  • XLSX — через Jasper template;
  • CSV — прямой экспорт заголовков и данных без обязательного Jasper template.

Для больших выборок допускается асинхронная подготовка результата с последующим получением готового файла.

18.3. Отчёты по запросу / Manual reports

Пользователь с соответствующими правами должен иметь возможность сформировать отчёт вручную за выбранный период и в доступном контексте Пространства.

Параметры конкретных отчётов и формы ввода уточняются на этапе ТЗ.

Время и интервалы в пользовательском UI должны интерпретироваться в часовом поясе (timezone) Пространства; исходные timestamps внутри платформы остаются UTC.

18.4. Отчёты по расписанию / Scheduled reports

Первая версия должна поддерживать отчёты по расписанию (scheduled reports).

Отчёт по расписанию (Scheduled report) должен уметь:

  • запускаться по расписанию;
  • формироваться автоматически;
  • сохраняться/регистрироваться в предусмотренном механизме результата;
  • отправляться по e-mail указанным получателям (recipients).

Конкретная модель хранения сформированных файлов и срок хранения (retention) согласуются на этапе ТЗ.

18.5. Базовые шаблоны Jasper (Jasper templates)

В обязательную поставку входят как минимум:

  1. отчёт по потреблению ресурсов за период;
  2. отчёт по журналу аварий и действий персонала.

Для второго отчёта под действиями персонала понимаются технологически значимые операции, например:

  • ACK аварии;
  • управляющие commands;
  • изменение setpoints/эксплуатационных writable values;
  • аналогичные действия, для которых доступны actor и timestamp.

Полный Журнал аудита безопасности (Security Audit) не должен целиком подменяться этим отчётом и остаётся отдельным системным журналом.

Типовой отчёт по наработке моточасов включается только после подтверждения владельцем продукта в разделе 2.

18.6. Экспорт телеметрии

Экспорт телеметрии должен позволять выбрать Parameters и период.

Минимально:

  • CSV — прямые данные;
  • XLSX/PDF — через согласованные шаблоны отчётов (report templates).

Экспорт должен использовать тот же архив RatioT.Cloud, что тренды Дашборда и другие штатные функции, без отдельного параллельного хранилища исторических данных/отчётов (historian/report storage).

18.7. Экспорт конфигурации

Экспорт конфигурации Пространства и пакет резервного копирования/миграции (backup/migration package) не относятся к обычной отчётности и описаны отдельно в разделе 21.

CSV/JSON import/export Заготовок устройств также относится к разделу 7 и не должен смешиваться с report subsystem.

19. Тарифы SaaS

19.1. Границы первой версии

В текущий объём работ (scope) входит механизм тарифов/тарифных прав и ограничений (entitlements), но не коммерческий биллинг/платежи (billing/payments).

Не входят в первую версию:

  • денежный баланс клиента;
  • приём платежей;
  • самостоятельная покупка/смена тарифа Владельца (Owner);
  • пользовательский package configurator произвольных опций.

Эти функции не разрабатываются в данном проекте.

19.2. Управление тарифами

SuperAdmin должен иметь возможность:

  • создавать тарифы;
  • изменять их;
  • назначать их учётным записям (accounts);
  • видеть использование лимитов в предусмотренном объёме.

Польщователь должен видеть действующий тариф/лимиты (tariff/limits) в своем профиле.

Администратор Пространства должен видеть действующие лимиты (effective limits) Пространства и использование лимитов своего Пространства без обязательного раскрытия всех персональных данных/деталей тарифа Владельца (Owner).

Ровно один тариф должен иметь признак По умолчанию / ``Default и назначаться при регистрации до автоматического создания первого Пространства.

Тариф может изменяться на месте (in-place) и влияет на назначенные учётные записи (accounts).

Удаление тарифа запрещается, пока он назначен хотя бы одной учётной записи (account).

Индивидуальные overrides полей тарифа для отдельных клиентов не требуются; нестандартный набор условий оформляется отдельным тарифом.

19.3. Модель product fields

Не требуется универсальный конструктор произвольных тарифных прав key-value (universal arbitrary key-value entitlement builder).

Первая версия должна иметь фиксированный набор product fields с архитектурной возможностью дальнейшего расширения.

Количественный лимит должен поддерживать конечное значение и семантику Без ограничений / ``Unlimited.

Числа 100 / 500 / 2000 / 5000+, встречающиеся в исходной продуктовой концепции, являются примером возможной коммерческой сетки, а не обязательным набором предустановленных тарифов.

19.4. Обязательные tariff fields

Минимальный набор:

  • максимальное количество собственных Пространств (Max owned Spaces);
  • максимальное количество Devices на Пространство (Max Devices per Space);
  • максимальное количество Parameters на Пространство (Max Parameters per Space), включая физические и виртуальные параметры (physical/virtual parameters);
  • максимальное количество пользователей на Пространство (Max users per Space), включая Владельца (Owner);
  • максимальное количество одновременно работающих пользователей UI на Пространство (Max simultaneous interactive UI users per Space);
  • максимальный срок хранения телеметрии/архива на Пространство (Max telemetry/archive retention days per Space);
  • максимальный срок хранения журнала Event/Alarm на Пространство (Max Event/Alarm journal retention days per Space);
  • максимальное количество параллельных пользовательских экземпляров Automation (Max parallel user Automation instances per Space);
  • общий месячный лимит SMS Владельца для всех собственных Пространств (monthly SMS quota owner-wide across all owned Spaces);
  • Device Template Builder enabled;
  • White-label/customization enabled;
  • Integrator Workspace enabled;
  • максимальное количество клиентских Пространств в Integrator Workspace (Max client Spaces).

Трафик REST API не считается интерактивным пользователем UI (interactive UI user). Конкретный механизм учёта одновременных пользователей (simultaneous users) определяется на этапе ТЗ.

19.5. Что не тарифицируется в первой версии

Не должны являться tariff limits/features:

  • количество Шлюзов (Gateway);
  • количество Дашбордов (Dashboard count);
  • Reports;
  • Application/REST API;
  • polling/update frequency;
  • число Automation scenarios;
  • число Alarm Rules;
  • backup/export;
  • базовая Automation как функция.

Web/in-app, Web Push, E-mail и Telegram являются базовыми каналами Notification и не отключаются тарифом.

19.6. Отключение булевого тарифного права (Boolean entitlement downgrade)

Принцип: отключить инструмент, сохранить соз``данное / ``disable`` ``the`` ``tool``, ``keep`` ``what`` ``it`` ``produced.

При отключении White-label существующая конфигурация оформления сохраняется, но её редактирование блокируется.

При отключении Device Template Builder ранее созданные custom templates и Devices продолжают работать, но создание/редактирование templates блокируется.

Отключение булевого тарифного права (Boolean entitlement downgrade) само по себе не должно удалять пользовательские результаты.

19.7. Снижение лимита (Quota downgrade) и ограниченный режим (Restricted mode)

SuperAdmin может назначить тариф с лимитом (quota) ниже текущего использования (usage).

При этом лишние данные/сущности не удаляются автоматически.

Учётная запись/Пространство переходит в ограниченное состояние (Restricted).

В ограниченном режиме (Restricted) Владелец/Мастера (Owner/Masters) должны иметь возможность:

  • войти;
  • увидеть конкретные нарушения (violations);
  • читать current/history data;
  • выполнить export;
  • изменить конфигурацию;
  • удалить/уменьшить избыточное использование (excess usage).

До устранения нарушений (violations) блокируются штатная эксплуатация (normal operation), управляющие команды (control commands) и Automation.

Ограниченный режим (Restricted) снимается автоматически после достижения соответствия лимитам.

Снижение срока хранения (retention) не должно немедленно удалять архив. Пространство остаётся в ограниченном состоянии (Restricted) до явного уменьшения настройки срока хранения (retention-setting) администратором; после этого штатная политика хранения (retention policy) удаляет данные старше нового срока.

19.8. SMS quota

Коммерческая квота SMS (SMS quota) является общим месячным пулом Владельца (Owner) для всех собственных Пространств.

Денежный баланс SMS (SMS balance), расчёт стоимости, пополнение и списание в первой версии не реализуются.

Дополнительно должны быть защитные лимиты:

  • на Пространство;
  • на получателя (per recipient).

Они не резервируют квоту (quota), а ограничивают аномальную отправку.

SMS отправляется только если не превышены общий лимит Владельца (owner total) и защитные лимиты (protective limits).

При защитной блокировке (protective block) ветка SMS останавливается и формирует системное предупреждение (system warning); остальные каналы уведомлений (notification channels) продолжают работу.

Защитные/служебные SMS (security/service SMS) операций учётной записи (account) не расходуют коммерческий пул (commercial pool).

19.9. White-label entitlement

Тарифное право White-label уровня Владельца (Owner-level entitlement) разрешает индивидуальное оформление (custom appearance) и индивидуальный FQDN (custom FQDN) для собственных Пространств в пределах максимального количества собственных Пространств (Max owned Spaces).

Конфигурация Пространства включает как минимум:

  • colors/theme;
  • logo;
  • индивидуальное отображаемое имя (display name) проекта/Пространства;
  • custom FQDN.

White-label должен применяться уже на login page соответствующего FQDN.

DNS, domain ownership и certificate provisioning остаются зоной Заказчика/ДИТ; integration ingress/FQDN внутри software contour описывается в разделах 22 и 27.

20. Лицензирование On-Premise

20.1. Общая модель

On-Premise поставка должна использовать криптографически проверяемую архитектуру лицензирования (license architecture).

Необходим единый Менеджер прав / ``Entitlement`` ``Manager и расширяемый Провайдер лицензий / ``License`` ``Provid``er, чтобы потребители тарифных/лицензионных прав (entitlement) не зависели от конкретного способа идентификации инсталляции.

20.2. Подписанная лицензия / Signed license

Лицензия (License) должна содержать как минимум:

  • идентификатор инсталляции (Installation ID);
  • срок/условия действия (validity);
  • лимиты инсталляции (installation limits).

Лицензия подписывается закрытым ключом вендора (vendor private key), который отсутствует у клиента.

Среда выполнения (Runtime) содержит только открытый ключ проверки (public verification key) и проверяет подпись локально.

Лицензия может быть:

  • бессрочной (perpetual);
  • ограниченной датой окончания (expiration date).

20.3. Идентификатор инсталляции / Installation ID

Должна существовать точка расширения (extension point) InstallationIdProvider.

Для первой версии допускается простой идентификатор инсталляции (Installation ID) из фиксированного локального файла, например /``var``/``lib``/``ratiot``/``installation``-``id или эквивалентного расположения.

Аппаратный отпечаток (Hardware fingerprint) не является обязательным требованием первой версии.

Архитектура должна позволять позднее заменить провайдер (provider) на TPM, аппаратный/VM UUID (hardware/VM UUID), dongle, сервер лицензий (license server) или иной механизм без переработки потребителей прав (entitlement consumers).

20.4. Лимиты лицензии

Для On-Premise первой версии лицензией на всю инсталляцию (installation-wide) ограничиваются только:

  • общее число Пространств (total Spaces);
  • общее число Devices (total Devices);
  • общее число Parameters (total Parameters).

Остальные функции продукта доступны полностью и не повторяют тарифную матрицу SaaS (tariff matrix).

20.5. Некорректная или отсутствующая лицензия (license)

При некорректной/отсутствующей/истёкшей лицензии (invalid/missing/expired license) административный UI (admin UI) и функции диагностики/замены лицензии должны оставаться доступны.

Штатная лицензируемая среда выполнения (Normal licensed runtime) при этом блокируется.

Точный набор разрешённых административных действий фиксируется на этапе ТЗ.

20.6. Снижение лимитов

Если новая лицензия (license) имеет лимиты (limits) ниже текущего использования (usage), данные не должны удаляться автоматически.

Инсталляция/соответствующие Пространства переходят в аналог ограниченного режима (Restricted mode) до устранения нарушений (violations) или установки совместимой лицензии (license).

20.7. SMS On-Premise

On-Premise использует SMS-провайдера/договор клиента (SMS provider/contract) и не расходует коммерческую SMS-квоту SaaS (commercial SMS quota).

Техническая интеграция SMS-канала (integration SMS channel) должна при этом использовать общую подсистему уведомлений (Notification subsystem).

21. Резервное копирование, восстановление, переносимость и удаление (Backup, restore, portability, deletion)

21.1. Два уровня резервного копирования/восстановления (backup/restore)

RatioT.Cloud должна иметь два различных механизма:

  1. полное резервное копирование/восстановление (backup/restore) эксплуатационного состояния инсталляции;
  2. пользовательский экспорт/импорт (export/import) конфигурации одного Пространства или набора собственных Пространств.

Эти механизмы не должны смешиваться.

21.2. Полное резервное копирование инсталляции (Full installation backup)

Подрядчик должен реализовать:

  • автоматическое резервное копирование (automatic backup) не реже одного раза в сутки;
  • ручное административное резервное копирование (manual admin backup);
  • восстановление (restore) на чистой инсталляции (clean installation);
  • документированную процедуру восстановления (documented recovery procedure);
  • скрипты/конфигурации (scripts/configs) для воспроизводимого выполнения процедуры.

Не требуется ежедневный полный дамп (dump) всей телеметрии (telemetry). Полная/инкрементальная/нативная для БД стратегия (Full/incremental/DB-native strategy) выбирается подрядчиком с учётом HA, объёма данных и практичности RTO/восстановления (recovery practicality).

Процедура лолжна быть задокументирована и автоматизирована и не должна зависеть от ручного восстановления настроек «по памяти разработчика».

21.3. Логическое разделение приложения и эксплуатационных данных (application/operational data)

Прикладные компоненты RatioT.Cloud и эксплуатационные пользовательские данные должны быть логически разделены так, чтобы обновление/развёртывание приложения и резервное копирование/восстановление эксплуатационного состояния (backup/restore operational state) выполнялись независимо и воспроизводимо.

Физическое разделение на две отдельные БД/СУБД (DB/DBMS) данным ФТТ не предписывается.

21.4. Экспорт конфигурации Пространства

Экспорт/резервное копирование конфигурации Пространства должен быть самодостаточным (self-contained) и включать всю активную конфигурацию и зависимости, в том числе:

  • Объекты (Assets);
  • Devices;
  • Параметры (Parameters);
  • профили/сопоставления/конфигурацию (profiles/mapping/configuration);
  • Дашборды (Dashboards);
  • Визуальные заготовки Пространства (Space Visual Templates);
  • Automation;
  • правила/конфигурацию Аварий/Событий (Alarm/Event rules/configuration);
  • Группы (Groups);
  • ACL;
  • назначения/ссылки пользователей (user assignments/references);
  • конфигурацию уведомлений (notification configuration);
  • настройки индивидуального оформления (white-label);
  • иные необходимые зависимости активной конфигурации Пространства.

Телеметрия/история (Telemetry/history) в этот пакет (package) не включается и экспортируется отдельно.

21.5. Мастер импорта / Import wizard

Импорт ранее зарезервированного пакета Пространства должен выполняться через мастер (wizard).

Мастер (Wizard) анализирует ссылки на пользователей (user references).

Если пользователь уже существует — выполняется сопоставление (mapping).

Если пользователь по ссылке (referenced user) отсутствует — мастер (wizard) должен потребовать явного решения пользователя. Допустимые операции, например создать/сопоставить/оставить неразрешённым (create/map/leave unresolved), фиксируются на этапе ТЗ.

Целевые сценарии:

  • восстановление (restore);
  • миграция SaaS → совместимый On-Premise (compatible On-Premise);
  • миграция между совместимыми инсталляциями;
  • передача конфигурации другому оператору/владельцу Cloud (operator/owner).

21.6. Резервное копирование (Backup) всех собственных Пространств

Владелец (Owner) должен иметь возможность одной операцией сформировать экспорт/резервную копию (export/backup) всех принадлежащих ему Пространств.

Приглашённые чужие Пространства не включаются.

Результат логически представляет собой набор тех же самодостаточных (self-contained) пакетов Пространств и восстанавливается через общий мастер импорта (import wizard).

21.7. Экспорт истории

Телеметрия (Telemetry) и история Событий/Аварий (Event/Alarm history) должны экспортироваться отдельно от пакета конфигурации (config package).

Форматы и ограничения больших объёмов определяются в ТЗ, но пользовательский экспорт не должен требовать собственного бинарного дампа (proprietary binary dump) для обычных сценариев переноса/анализа.

21.8. Удаление Пространства

Удаление Пространства требует явного подтверждения (explicit confirmation).

На странице удаления должны быть доступны:

  • резервное копирование/экспорт конфигурации (config backup/export);
  • отдельный экспорт истории (history export), если пользователь хочет сохранить эксплуатационные данные.

После подтверждения должны удаляться:

  • активная конфигурация (active configuration);
  • телеметрия (telemetry);
  • журналы Событий/Аварий (Event/Alarm journals);
  • иные эксплуатационные/исторические данные (operational/history) Пространства.

Журнал аудита безопасности (Security Audit) платформы не удаляется автоматически вместе с Пространством.

22. Развёртывание и обновление

22.1. Воспроизводимое развёртывание

Подрядчик должен поставить воспроизводимый пакет развёртывания (deployment package) всего программного контура RatioT.Cloud выше ОС.

Развёртывание не должно зависеть от закрытого CI/CD (private CI/CD), недоступных Заказчику учётных данных/ресурсов (credentials/resources) или ручных действий, известных только подрядчику.

Первичное развёртывание (Initial deployment) должно быть документировано и автоматизировано в разумной степени для выбранной архитектуры.

22.2. Состав программного контура (software contour)

Развёртывание (Deployment) должно охватывать необходимые компоненты выше ОС, включая, где применимо:

  • Tibbo AggreGate;
  • frontend;
  • СУБД;
  • MQTT-брокер (broker);
  • nginx/обратный прокси/балансировщик нагрузки (reverse proxy/load balancer);
  • компоненты кластеризации/репликации (clustering/replication);
  • среда выполнения/промежуточное ПО/вспомогательные сервисы (runtime/middleware/auxiliary services);
  • компоненты Jasper (Jasper-related components);
  • конфигурации приложения (application configurations).

Конкретный состав определяется архитектурой подрядчика.

22.3. Режим обслуживания / Maintenance mode

Режим обслуживания (Maintenance mode) должен существовать на уровне всей инсталляции.

Режим обслуживания (maintenance mode) для отдельных Пространств данным ФТТ не требуется.

При входе в режим обслуживания (maintenance):

  • новые выполнения Automation (executions) не запускаются;
  • существующим экземплярам выполнения (instances) по умолчанию дают штатно завершиться;
  • телеметрия/архив/События/Аварии/уведомления (telemetry/archive/Event/Alarm/notifications) продолжаются до фактической остановки компонентов, насколько это возможно;
  • администратор видит остаточную активность;
  • доступна единая команда Остановить все ``Automation`` / ``Stop`` ``all`` ``Automation с корректной фиксацией результата/аудита (audit).

Выход из режима обслуживания (maintenance) не должен переписывать пользовательские состояния включения триггеров (trigger enabled states) сценариев.

Обязательный базовый процесс:

Процедура обновления (Update procedure) должна быть документирована и воспроизводима для обеспечения жизненного цикла ПО (добавление фич и исправление багов, система релизов).

Отдельная сложная предварительная проверка прогнозной совместимости профилей (predictive compatibility pre-check profiles) не требуется.

22.5. Политика версий AggreGate (version policy)

Конкретная базовая версия (baseline-version) Tibbo AggreGate, стратегия перехода на новые версии и возможность оставаться на старой поддерживаемой версии с патчами вендора (vendor patches) определяются на этапе ТЗ.

ФТТ не должно жёстко закреплять правило обязательного немедленного перехода на каждый новый выпуск (release) AggreGate.

Выход новой версии AggreGate не должен автоматически блокировать выпуск исправлений RatioT.Cloud на согласованной базовой версии (baseline).

22.6. Откат и восстановление (Rollback/recovery)

Откат (Rollback) должен опираться на поставляемые механизмы и скрипты резервного копирования/восстановления (backup/restore).

Требование обновления без простоя (zero-downtime update) не предъявляется. Допускается согласованное окно обслуживания (maintenance window) после корректной остановки/дренирования пользовательской активности.

22.7. Индивидуальный FQDN (Custom FQDN) и ingress

Программный контур (Software contour) должен поддерживать индивидуальный FQDN Пространства без ручной переработки приложения (application) для каждого домена.

Механизм доверенной передачи (trusted propagation) исходного Host/FQDN через nginx/обратный прокси (reverse proxy) и определение Пространства до аутентификации (authentication) разрабатывается на этапе ТЗ.

Произвольный переданный frontend идентификатор Пространства (frontend-provided Space ID) не должен быть доверенным источником определения tenant.

DNS/домен/выпуск сертификатов (domain/certificate provisioning) выполняет Заказчик согласно разделу 27.

23. Проверки работоспособности (Health checks) и регрессионные тесты backend

23.1. Набор регрессионных тестов backend (Backend regression suite)

Backend RatioT.Cloud должен быть покрыт автоматизированным набором регрессионных тестов (regression suite).

Основная цель — после обновления Tibbo AggreGate, RatioT.Cloud или существенных компонентов программного контура (software contour) автоматически выявлять регрессии (regression) до выпуска в продуктивную эксплуатацию (production release).

Тесты должны проверять критические сквозные backend-сценарии (scenarios), а не только отдельные REST-эндпоинты (endpoints).

23.2. Обязательные области покрытия

Набор регрессионных тестов (Regression suite) должен включать как минимум проверки:

  • аутентификацию (authentication);
  • RBAC;
  • тарифные/лицензионные права и ограничения (entitlement/licensing);
  • жизненный цикл Пространства;
  • операции с Объектами/Device (Asset/Device);
  • Профили сопряжения (Coupling Profiles);
  • Параметры (Parameters);
  • Automation;
  • События/Аварии (Events/Alarms);
  • связанные с уведомлениями backend-потоки (Notification-related backend flows) в согласованной части;
  • резервное копирование/восстановление (backup/restore);
  • дымовые/регрессионные проверки обновления (update smoke/regression);
  • Application API;
  • интеграции протоколов (protocol integrations).

23.3. Эталонные протокольные стенды (Protocol reference stands)

Интеграционные тесты протоколов (protocol tests) должны использовать независимые эталонные реализации (reference implementations) там, где это предусмотрено ФТТ.

В частности OPC UA Client RatioT.Cloud проверяется на независимом программном OPC UA Server (software server), а OPC UA Server — независимым программным Client (software client).

Для Modbus/MQTT/Шлюза (Gateway) должны быть подготовлены воспроизводимые тестовые/эталонные стенды или симуляторы (test/reference stands, simulators), достаточные для регрессионного тестирования backend (backend regression).

23.4. Использование после обновлений AggreGate

Набор регрессионных тестов (Regression suite) должен быть пригоден для запуска после обновления Tibbo AggreGate и подтверждать совместимость приложения RatioT.Cloud с новой/обновлённой версией.

Конкретный CI-runner не является частью требования: тесты и инструкции должны принадлежать Заказчику и запускаться независимо от закрытого CI/CD (private CI/CD) подрядчика.

23.5. Автотесты frontend (Frontend autotests)

Полный набор автотестов frontend (autotest suite) не является обязательным требованием текущего объёма работ (scope).

Это не отменяет ручные/приёмочные UX/UI проверки и ПСИ.

23.6. Постоянные проверки работоспособности (health checks)

Набор регрессионных тестов (Regression suite) не заменяет постоянно работающие проверки работоспособности (health checks).

Обязательны машиночитаемые (machine-readable) уровни:

  • liveness — процесс/узел (process/node) жив;
  • readiness — узел (node) реально способен обслуживать трафик (traffic);
  • system`` ``health — сводное состояние критических компонентов/зависимостей (dependencies) инсталляции с причиной нездорового состояния (unhealthy).

HTTP 200 от nginx или страницы входа (login page) AggreGate не является достаточным сигналом работоспособности (health signal).

Если критичный компонент application/backend недоступен, readiness/system health должны показывать отказ (failure), например через false/unhealthy/HTTP 503 в принятом контракте.

23.7. Использование сигнала работоспособности (health signal)

Health/readiness должны быть пригодны для использования внешним мониторингом (monitoring).

Специальная интеграция именно с Zabbix/Grafana согласуется на этапе ТЗ.

Контракт эндпоинтов/метрик работоспособности (health endpoints/metrics) и перечень критических зависимостей (critical dependencies) фиксируются на этапе ТЗ.

24. Архитектура, HA, масштабирование и расчёт ресурсов (sizing)

24.1. Базовая архитектурная платформа

Backend RatioT.Cloud строится на Tibbo AggreGate Server.

Архитектура промышленной инсталляции должна использовать штатные механизмы кластеризации, распределённой обработки и отказоустойчивости AggreGate в той мере, в которой они применимы к выбранной версии и профилю нагрузки.

Собственные механизмы аварийного переключения (failover) для AggreGate не должны разрабатываться, если задача решается штатными средствами платформы.

24.2. Горизонтальное масштабирование / Horizontal scaling

Архитектура должна поддерживать горизонтальное масштабирование (horizontal scaling) обработки Devices/телеметрии (telemetry) путём добавления узлов обработки (processing nodes) при сохранении одной логической RatioT.Cloud.

Единицей изоляции арендатора/размещения нагрузки (tenant isolation/load placement) является Пространство, а не пользовательская учётная запись (account).

Одна учётная запись (account) может работать с Пространствами, обслуживаемыми разными физическими узлами/группами узлов (physical nodes).

Исходная формулировка о закреплении клиента за конкретным узлом не означает обязательное правило одна учётная запись = один узел / ``one`` ``account`` = ``one`` ``node или одно Пространство = один сервер / ``one`` ``Space`` = ``one`` ``server.

Конкретные топология, размещение и планирование ресурсов арендаторов (topology, placement, scheduling tenant resources) должны быть разработаны на этапе ТЗ/прототипа (prototype) на базе реальных возможностей AggreGate.

24.3. Географически распределённое размещение

Архитектура должна допускать географически распределённое размещение узлов обработки (processing nodes)/контуров в пределах возможностей выбранной топологии AggreGate (topology).

ФТТ не фиксирует конкретную схему геораспределения, межЦОД-репликации (inter-DC replication) или active-active-архитектуры (design): они определяются на этапе ТЗ при известной инфраструктуре Заказчика и лицензионных ограничениях.

24.4. HA хранилища данных (data storage)

СУБД/хранилище не должно оставаться очевидной единой точкой отказа (single point of failure) в промышленной схеме.

Подрядчик выбирает СУБД и механизм кластеризации/репликации/аварийного переключения (clustering/replication/failover) с учётом:

  • фактической совместимости с AggreGate;
  • производительности;
  • резервное копирование/восстановление (backup/restore);
  • восстановления (recovery);
  • операционной сложности;
  • требований российского ПО и лицензирования.

Galera или аналогичные технологии могут рассматриваться как вариант, но не являются обязательным решением.

24.5. Логическое разделение приложения и пользовательских данных

Прикладные компоненты RatioT.Cloud и эксплуатационные пользовательские данные должны быть логически разделены.

Это разделение должно позволять:

  • обновлять/развёртывать приложение без ручного переноса эксплуатационных данных;
  • выполнять резервное копирование/восстановление эксплуатационного состояния (backup/restore operational state);
  • переносить/восстанавливать пользовательские данные независимо от low-code-компонентов приложения (application components).

Физическое размещение в двух отдельных БД/СУБД (DB/DBMS) не является обязательным, если выбранная архитектура решает требование иным способом.

24.6. Целевая производительность / NFR (Target performance)

Целевые ориентиры первой промышленной архитектуры:

  • типичное время отклика интерактивного UI (typical interactive UI response) при штатной нагрузке (normal load) — до примерно 1.5 s;
  • не менее 500 одновременно работающих интерактивных пользователей UI (simultaneous interactive UI users) на инсталляцию (installation);
  • горизонтальное масштабирование (horizontal scale) до 50 000+ Devices на логическую инсталляцию (logical installation);
  • не менее 5000 Параметров на Пространство;
  • индивидуальный интервал архивирования (individual archive interval) до 1 s.

Эти значения задают направление архитектуры и нагрузочной приёмки, но не означают, что все максимумы (maxima) должны одновременно складываться в один экстремальный профиль тестирования (test profile).

Тяжёлые отчёты, экспорты и большие исторические диапазоны (Heavy reports, exports, historical ranges) могут выполняться асинхронно/с отображением прогресса (progress-based).

24.7. Требования к времени реакции

Для RatioT.Cloud не устанавливаются требования жёсткого реального времени (hard real-time) и детерминированного времени реакции.

Границы применения понятия «реальное время» и соответствующие ограничения системы определены в разделе 4.4.

24.8. Изоляция отказов / Fault isolation

В пределах рассчитанного профиля нагрузки (load profile) проблемы одного Пространства не должны существенно ухудшать (materially degrade) работу других Пространств.

К таким проблемам относятся, например:

  • неконтролируемая Automation (runaway Automation);
  • шумный Device (noisy Device);
  • ошибочная конфигурация;
  • отказ (failure) конкретного профиля/коннектора (profile/connector);
  • превышение разумной частоты событий.

Это требование не означает обязательный отдельный процесс/контейнер/БД (process/container/DB) на каждое Пространство.

24.9. Нагрузочные испытания

На этапе ТЗ подрядчик должен сформировать согласованный профиль нагрузки (load profile) и методику нагрузочных испытаний.

ПМИ должна включать проверки согласованных NFR и поведения масштабирования (agreed NFR, scaling behaviour).

Нагрузочное тестирование должно использовать сценарии, соответствующие реальному сочетанию Devices, Parameters, опроса/подписок (polling/subscriptions), пользователей UI (UI users), архива (archive) и Automation.

24.10. Расчёт ресурсов / Sizing

Подрядчик на этапе ТЗ должен выполнить расчёт ресурсов (sizing) и обосновать как минимум:

  • CPU;
  • RAM;
  • хранилище (storage);
  • сеть (network);
  • узлы обработки (processing nodes);
  • топологию БД (DB topology);
  • подход к резерву/росту (reserve/growth approach);
  • влияние срока хранения архива (archive retention) и частоты телеметрии (telemetry rate).

Желательно представить эталонные конфигурации (reference configurations) уровня small/medium/target или эквивалентную понятную шкалу роста.

24.11. Границы доступности / Availability boundaries

Формальный SLA 99.9%/99.99%, фиксированный RTO/RPO и обновление без простоя (zero-downtime update) данным ФТТ не задаются.

При этом обязательны:

  • мехнизмы обеспечивающие “высокую доступность” (HA architecture);
  • резервное копирование/восстановление (backup/restore);
  • проверки работоспособности (health checks);
  • изоляция отказов (fault isolation);
  • нагрузочная верификация;
  • возможность планового окна обслуживания (planned maintenance window).

25. Безопасность и аудит (Security, audit)

25.1. Общий принцип

Security controls должны применяться на backend и infrastructure software contour и не полагаться только на скрытие функций frontend.

Приоритет — штатные механизмы Tibbo AggreGate и стандартные проверенные компоненты вместо разработки собственной криптографии/IAM без необходимости.

25.2. 2FA

Двухфакторная аутентификация входит в первую версию.

По возможности должны использоваться штатные механизмы AggreGate.

Конкретные вторые факторы (second factors), процесс восстановления (recovery flow), регистрация фактора (enrollment) и политика (policy) фиксируются на этапе ТЗ.

25.3. Доверенное устройство/браузер (Trusted device/browser)

Должна поддерживаться возможность доверенного устройства/браузера (trusted device/browser), чтобы 2FA не требовалась при каждом обычном входе (login).

Срок доверия (trust lifetime), отзыв (revoke), защитные триггеры (security triggers) и условия повторной аутентификации (re-authentication conditions) определяются на этапе ТЗ.

25.4. Защита от перебора (Brute-force protection)

Backend должен иметь защиту от перебора/подбора паролей (brute-force/password guessing).

Captcha допускается как один из механизмов защиты, но не является отдельным обязательным продуктовым компонентом при наличии иного достаточного механизма.

25.5. Безопасность Web/API (Web/API security)

Web frontend и Application API должны работать через HTTPS с актуальными защищёнными версиями TLS/наборами шифров (TLS versions/cipher suites).

TLS 1.3 является желательным целевым режимом, но не должен становиться искусственным препятствием совместимости (blocker), если корпоративные требования допускают иной актуальный безопасный режим.

Точная политика TLS (TLS policy) фиксируется в ТЗ и документации по развёртыванию (deployment documentation).

25.6. Безопасность протоколов (Protocol security)

Для протоколов, имеющих штатные механизмы безопасности (security mechanisms), должны применяться защищённые режимы, включая:

  • MQTT over TLS;
  • механизмы безопасности OPC UA (OPC UA security) в согласованной конфигурации;
  • индивидуальные учётные данные Шлюза (Gateway credentials) и ACL брокера.

Для Modbus RTU/TCP собственная криптографическая обёртка (wrapper) RatioT.Cloud не разрабатывается. Защита обеспечивается доверенной LAN/VPN/Шлюзом/сетевым периметром (trusted LAN/VPN/Gateway/network perimeter).

25.7. Пароли и учётные данные (credentials)

Пароли пользователей не должны храниться в открытом или обратимо расшифровываемом виде. Должно применяться стойкое хеширование паролей с солью (password hashing with salt) или эквивалентным современным механизмом, предпочтительно штатными средствами AggreGate.

Секреты, токены, закрытые ключи и учётные данные устройств (secrets, tokens, private keys, device credentials) не должны попадать в диагностические логи.

25.8. Журнал аудита безопасности / Security Audit

Журнал аудита безопасности (Security Audit) должен быть неизменяемым для обычного пользователя/Владельца (User/Owner) и отделён от Журнала событий/аварий (Event/Alarm Journal).

Минимально он должен фиксировать:

  • действия аутентификации/значимые для безопасности (authentication/security-relevant actions);
  • изменения RBAC;
  • передачу владения (ownership transfer);
  • назначение/отзыв SuperAdmin;
  • сервисный вход SuperAdmin в клиентское Пространство;
  • критичные платформенные/административные действия (platform/admin actions);
  • управляющие операции, где требуется фиксация инициатора/результата аудита (audit actor/result).

Запись аудита (Audit record) должна позволять определить инициатора (actor), временную метку (timestamp), цель/ресурс (target/resource), действие (action) и результат (result).

Срок хранения/архивирование Журнала аудита безопасности (Retention/archiving Security Audit) фиксируются на этапе ТЗ.

Удаление Пространства не должно автоматически уничтожать платформенный Журнал аудита безопасности (platform Security Audit).

25.9. Безопасная разработка / Secure development

Подрядчик обязан применять практики безопасной разработки и проверки безопасности приложения в соответствии с общепринятыми открытыми рекомендациями и стандартами OWASP.

Требования к безопасности web/backend-компонентов и их проверка должны ориентироваться на OWASP Application Security Verification Standard (OWASP ASVS) в применимой к RatioT.Cloud части.

Как минимум должны учитываться типовые классы уязвимостей OWASP, включая XSS, SQL injection, CSRF, нарушения контроля доступа, ошибки аутентификации и управления сессиями, небезопасную обработку входных данных и иные риски, применимые к выбранному стеку.

Конкретный уровень OWASP ASVS, перечень применимых требований и состав проверочных мероприятий фиксируются на этапе ТЗ и включаются в ПМИ.

25.10. Внешняя IAM / External IAM

Интеграция с AD/LDAP/OIDC/SSO в первую версию не входит.

Архитектура не должна препятствовать последующей интеграции (future integration) с поставщиками идентификации (identity providers), поддерживаемыми AggreGate или выбранной архитектурой.

25.11. Периметровая безопасность

Не являются функциями приложения RatioT.Cloud:

  • защита от DDoS (DDoS protection);
  • геоблокировки (geoblocking);
  • фильтрация VPN (VPN filtering);
  • межсетевое экранирование/сегментация сети (firewall/network segmentation);
  • иные функции внешнего сетевого периметра (perimeter).

Они относятся к зоне Заказчика.

RatioT.Cloud отвечает за усиление безопасности application/nginx (hardening), аутентификацию (auth), защищённые протоколы (secure protocols) и безопасную разработку (secure development) выше предоставленного сетевого периметра (network perimeter).

25.12. Периодическая смена пароля (Password rotation)

Принудительная периодическая смена пароля (password) не является обязательным отдельным требованием первой версии, если иное не будет согласовано на этапе ТЗ.

29. ПМИ, ПСИ и опытная эксплуатация

29.1. Этапность

29.2. ПМИ

Подрядчик разрабатывает Программу и методику испытаний и согласует её с Заказчиком до ПСИ №1.

ПМИ должна включать как минимум:

  • функциональные/backend-сценарии (functional/backend scenarios);
  • критические сквозные пользовательские сценарии (critical end-to-end user scenarios);
  • RBAC;
  • безопасность (security);
  • протоколы (protocols);
  • резервное копирование/восстановление (backup/restore);
  • обновление/откат (update/rollback);
  • сценарии HA/отказов (failure scenarios);
  • проверки работоспособности (health checks);
  • согласованные нагрузочные/NFR-тесты (agreed load/NFR tests);
  • критерии приёмки (acceptance criteria) по функциональным требованиям ФТТ/ТЗ.

29.3. ПСИ №1

ПСИ №1 проводится перед вводом в продуктивную эксплуатацию (production rollout).

Успешный ПСИ №1 означает готовность системы к запуску в продуктивную эксплуатацию и началу опытной эксплуатации.

По результатам оформляется протокол испытаний.

29.4. Опытная эксплуатация

Опытная эксплуатация длится 12 месяцев и является отдельным активным этапом проекта, а не формальным гарантийным периодом.

Продуктивная эксплуатация (Production) запускается после успешного ПСИ №1.

В течение этого периода подрядчик обязан:

  • исправлять дефекты (defects);
  • выпускать исправления (fixes) в продуктивную эксплуатацию (production);
  • сопровождать процесс выпуска (release process);
  • устранять согласованный технический долг (technical debt);
  • поддерживать документацию и реестр зависимостей (dependency registry) в актуальном состоянии;
  • обеспечивать совместимость с согласованной базовой версией/политикой обновлений AggreGate (baseline/update policy).

Конкретные SLA по важности/реакции/исправлению (severity/reaction/fix) согласуются на этапе ТЗ.

Критические дефекты продуктивной эксплуатации (production defects) имеют приоритет над плановой работой по техническому долгу (technical debt).

29.5. Дефект и запрос на изменение (Defect vs change request)

Исправление несоответствия согласованным требованиям считается устранением дефекта (defect remediation).

Новые продуктовые функции (product features) или изменение согласованного поведения не должны автоматически считаться дефектом (defect) и оформляются как запрос на изменение (change request)/дополнительный объём работ (scope).

29.6. Реестр технического долга (Technical debt register)

На протяжении разработки и опытной эксплуатации ведётся согласованный реестр технического долга (technical debt register) с приоритетом/статусом/ответственным (priority/status/owner).

До ПСИ №2 подрядчик закрывает все пункты (items), совместно помеченные как обязательные к завершению проекта.

Остальные пункты (items) могут быть перенесены в будущий бэклог (future backlog) только с явным согласованием Заказчика.

29.7. ПСИ №2

После завершения 12 месяцев опытной эксплуатации проводится ПСИ №2.

ПСИ №2 является регрессионной проверкой, а не полным механическим повтором ПСИ №1.

Объём ПСИ №2 (Scope) должен покрывать:

  • критические сквозные сценарии (critical end-to-end scenarios);
  • всё изменённое в ходе опытной эксплуатации;
  • отсутствие регрессий (regression) по критичным областям NFR/security/HA;
  • обязательные к закрытию пункты технического долга (technical-debt items).

По результатам оформляется отдельный протокол.

30. Базовые сквозные (end-to-end) пользовательские сценарии

Базовые сценарии используются как сквозная проверка целостности требований. Детальные шаги приёмки (acceptance steps) и тестовые данные (test data) формируются в ТЗ/ПМИ.

30.1. Регистрация и простой старт

  1. Новый пользователь проходит регистрацию с приоритетом телефона (phone-first) и подтверждает телефон SMS-кодом.
  2. Пользователю назначается тариф по умолчанию (Default tariff).
  3. Автоматически создаются первое Пространство и первый Дашборд.
  4. Пользователь попадает в Дашборд, который предлагает добавить оборудование/визуализацию.
  5. Пользователь открывает Системную библиотеку (System Library), находит Заготовку устройства (Device Template) по категории или SKU.
  6. В одной форме вводит данные конкретного экземпляра и параметры подключения.
  7. Device создаётся в корневом Объекте-Пространстве либо выбранном Объекте (Asset).
  8. После проверки соединения/получения текущих данных (connection test/current data) пользователь получает оперативные значения и может разместить представление Device/Parameter на Дашборде.

Цель: готовое оборудование первой очереди должно подключаться без обязательного использования Конструктора Заготовок устройств (Device Template Builder), Automation или иных продвинутых инструментов (advanced tools).

30.2. Дашборд (Dashboard) технолога/оператора

  1. Пользователь переводит Дашборд в режим Edit.
  2. Добавляет несколько Параметров/Devices (Parameters/Devices).
  3. Выбирает подходящие Визуальные заготовки/виджеты (Visual Templates/widgets).
  4. Настраивает тренд (trend), индикаторы состояния (status indicators), уставку/управление (setpoint/control) и при необходимости SVG HMI.
  5. Настраивает вид для ПК и при необходимости отдельную мобильную компоновку (mobile layout) Дашборда.
  6. Сохраняет изменения Дашборда.
  7. Оператор открывает тот же Дашборд в режиме View с правами View/базовыми правами Device (underlying permissions).

30.3. Авария (Alarm) и уведомление

  1. Мастер создаёт Правило аварии (Alarm Rule) для Параметра (Parameter) либо использует типовое правило из Заготовки устройства (Device Template).
  2. Настраивает порог (threshold), TON/TOFF/гистерезис (hysteresis), уровень важности (severity) и Acknowledgement`` ``required.
  3. Назначает группы получателей/маршрутизацию (recipient groups/routing).
  4. Пользователи группы имеют собственные матрицы (matrices) тип сообщения × канал.
  5. При возникновении условия создаётся RAISED Событие/Авария (Event/Alarm).
  6. Уведомление (Notification) поступает в Центр уведомлений (Notification Center) и разрешённые внешние каналы (channels), включая Telegram/SMS согласно настройкам/квотам (quotas).
  7. Уполномоченный пользователь выполняет ACK.
  8. При нормализации условия фиксируется CLEARED; история остаётся append-only.

30.4. Automation и вычисляемый Parameter

  1. Пользователь создаёт No-Code сценарий (scenario).
  2. Триггер (Trigger) — изменение одного или нескольких текущих Параметров (Parameters)/периодическое расписание.
  3. Сценарий (Scenario) выполняет условие/арифметику.
  4. Результат записывается в Параметр (Parameter) Device с профилем Internal`` ``Space`` ``Store.
  5. Полученный Параметр (Parameter) используется как обычный источник для Дашборда, архива (archive) и Аварии (Alarm).
  6. Пользователь изменяет сценарий и применяет новую версию только через Deploy.

30.5. Команда Automation с недоступным каналом

  1. Сценарий (Scenario) должен выполнить команду Device.
  2. Automation передаёт операцию единому механизму Device/Profile без отдельной проверки соединения (check`` ``connection).
  3. Профиль (Profile) оценивает текущее состояние доступности/сессии (availability/session state) и пытается выполнить операцию (operation).
  4. При недоступности возвращается нормализованный результат (result) unavailable``/``timeout``/``failed.
  5. Сценарий (Scenario) обрабатывает результат/ошибку по стандартной модели.
  6. Аудит (Audit) фиксирует сценарий (scenario) как инициатора операции.

30.6. Программный прототип Шлюза

  1. Администратор настраивает Программный прототип Шлюза в RatioT.Cloud.
  2. Программный агент Шлюза (Cloud Gateway Agent) запускается на стандартном ПК с минимальной начальной конфигурацией (bootstrap configuration).
  3. Программный агент Шлюза аутентифицируется в MQTT-брокере по индивидуальным учётным данным (credentials).
  4. Программный агент Шлюза получает из RatioT.Cloud эксплуатационную конфигурацию, проверяет её и сохраняет как последнюю валидную применённую конфигурацию.
  5. Программный агент Шлюза выполняет опрос одного Экземпляра устройства (Device) по Modbus RTU в соответствии с полученной конфигурацией.
  6. Полученная телеметрия передаётся в RatioT.Cloud через внутренний протокол MQTT/TLS.
  7. Программный агент Шлюза получает управляющую команду из RatioT.Cloud, выполняет соответствующую операцию Modbus RTU и возвращает результат выполнения, ошибку или тайм-аут с идентификатором корреляции (correlation ID).
  8. После перезапуска программный агент Шлюза использует последнюю валидную применённую конфигурацию, проверяет её актуальность и при наличии новой версии получает и применяет обновление.

30.7. RBAC и доступ дежурного персонала

  1. Владелец/Мастер (Owner/Master) создаёт или использует группу по умолчанию (preset group) Операторы.
  2. Группе назначается View на нужный Дашборд.
  3. На соответствующее поддерево Объектов (Asset subtree) назначаются необходимые права Read``/``Control.
  4. При необходимости AcknowledgeAlarm назначается отдельно.
  5. Оператор видит Дашборд и выполняет только разрешённые операции backend (backend operations).
  6. Попытка доступа к несогласованному действию Device/API (action) отклоняется независимо от UI.

30.8. Integrator Workspace

  1. Клиент делегирует доступ организации-интегратору.
  2. Интегратор назначает своего сотрудника конкретному клиентскому Пространству.
  3. Сотрудник видит клиентское Пространство в Integrator Workspace.
  4. Межпространственный список (Cross-space list) показывает активные Аварии/События (active Alarm/Event) по доступным Пространствам.
  5. Пользователь переходит к источнику проблемы в клиентском Пространстве.
  6. Аудит (Audit) фиксирует фактического человека, а не безличную организацию.

30.9. Резервное копирование/миграция (Backup/migration) Пространства

  1. Владелец (Owner) запускает экспорт (export) конфигурации одного Пространства либо всех собственных Пространств.
  2. Получает самодостаточный пакет конфигурации (self-contained config package) без телеметрии/истории (telemetry/history).
  3. При необходимости отдельно экспортирует историю (history).
  4. На совместимой другой инсталляции запускает мастер импорта (import wizard).
  5. Мастер (Wizard) сопоставляет существующие ссылки на пользователей (existing user references) и запрашивает решения по отсутствующим пользователям (users).
  6. После импорта (import) восстанавливаются конфигурация (configuration), Дашборд, Automation, ACL, настройки Аварий/уведомлений (Alarm/notification) и другие зависимости.

30.10. Обновление/восстановление (Update/recovery)

  1. Администратор (Administrator) переводит инсталляцию (installation) в режим обслуживания (maintenance).
  2. Выполняется резервное копирование перед обновлением (backup-before-update).
  3. Применяется обновление (update).
  4. Запускаются дымовые/регрессионные проверки (smoke/regression checks).
  5. При успехе инсталляция (installation) возвращается в штатную эксплуатацию (normal operation).
  6. При отказе (failure) выполняется откат/восстановление из резервной копии (rollback/restore backup) по документированной процедуре.

30.11. Нарушение лицензии On-Premise (license violation)

  1. На On-Premise-инсталляции устанавливается подписанная лицензия (signed license) с идентификатором инсталляции (Installation ID) и лимитами (limits).
  2. Среда выполнения (Runtime) проверяет подпись открытым ключом (public key).
  3. При совместимой лицензии (compatible license) система работает штатно.
  4. При истёкшей/некорректной лицензии (expired/invalid license) штатная лицензируемая среда выполнения (normal licensed runtime) блокируется, но административная диагностика/замена лицензии (admin diagnostics/license replacement) остаются доступны.
  5. При установке лицензии (license) с лимитами (limits) ниже текущего использования (usage) данные не удаляются; система переходит в ограниченный режим (Restricted) до устранения нарушений (violations)/замены лицензии.
