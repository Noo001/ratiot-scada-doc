## Кейс 1. Ошибки создания ресурсов при первом запуске сервера

**Критичность:** Low  
**Тип:** Ошибка инициализации
**Категория:** 2. Ошибки OEM

### Описание
При первом запуске `RatioT_server_console.exe` сервер стартует, но в журнале фиксируются 3 ERROR. Часть встроенных моделей и отчётов не инициализируется.

### Воспроизведение
1. Установить RatioT SCADA 6.41.09 на чистую Windows.
2. Запустить `C:\Program Files\RatioTScada\RatioT_server_console.exe`.
3. Дождаться строки `Starting web server`.
4. Открыть `C:\Program Files\RatioTScada\logs\server.log`.
5. Найти строки с `ERROR ag.context`.

### Ожидаемый результат
Первый запуск завершается без ERROR/FATAL.

### Фактический результат
```
13.08.2026 12:47:25,471 ERROR ag.context
  Error creating resource 'users.admin.models.avatarManagement':
  Cannot invoke "...Context.callFunction(...)" because "container" is null

13.08.2026 12:47:25,733 ERROR ag.context
  Error creating resource 'users.admin.reports.maintenance':
  Контекст недоступен: users.admin.reports

13.08.2026 12:47:26,509 ERROR ag.context
  Error creating resource 'users.admin.models.workflowModel':
  Cannot invoke "...Context.callFunction(...)" because "container" is null
```

### Скриншоты
- ![ERROR в server.log при первом запуске](tests/screenshots/case1_server_log_errors.png) — фрагмент `server.log` с ошибками инициализации ресурсов
- Лог-файл: см. `C:\Program Files\RatioTScada\logs\server.log`
- Автотест фиксирует проблему: `tests/test_ui_ux.py` → `test_log_errors()`

### Проверка в 6.41.11 (ASD-6474, ответ АГ: «состав лицензий пересмотрен и перегенерирован, новые сборки не содержат ERROR ag.context»)

Проверено на свежей установке RatioT SCADA 6.41.11 (сборка 2532), лог `server.log` начинается с первого запуска сервера (строка «First launch detected», «Starting RatioT Server v6.41.11-2532»):

- Все три исходные ошибки из кейса — `users.admin.models.avatarManagement`, `users.admin.reports.maintenance`, `users.admin.models.workflowModel` — **отсутствуют в логе**. Исходный дефект устранён.
- Однако утверждение «логи сервера более не содержат строки с ERROR ag.context» на сборке 2532 **не подтверждается полностью**: при «Создание ресурсов (Mode: 0, server machine)» остаётся одна ERROR того же класса:
  ```
  09.09.2026 16:47:26,827 ERROR ag.context
    Error creating resource 'users.admin.models.deviceImages':
    Переменная 'deviceImages' недоступна в контексте 'users.admin.models.deviceImages'
  ```
- Дополнительно при инициализации фиксируются WARN со стектрейсами `ag.statistics`: «Переменная 'status' недоступна в контексте 'users.admin.models.tabList'» и «Переменная 'eventStatistics' недоступна в контексте 'users.admin.models.tabList'».

**Итог: частично исправлено. Три исходных ресурса создаются корректно, но при первом запуске остаётся одна ERROR ag.context (users.admin.models.deviceImages) и два WARN ag.statistics (users.admin.models.tabList). Возможно, перегенерация лицензий вошла в сборку новее 2532 — просим подтвердить номер сборки и проверим повторно.**

## Кейс 2. Режимы лицензирования free / trial не описаны в документации

**Критичность:** Medium  
**Тип:** Документация / лицензирование
**Категория:** 1. Ошибки кастомизации

Тикет АГ: `ASD-6482`.

### Описание
Инсталлятор RatioT SCADA 6.41.09 предлагает выбор между двумя режимами на **этапе установки**:
- **Пробная лицензия (30 дней)**
- **Бесплатная лицензия на 100 тэгов**

> **Важно:** режим с ограничением в 100 тегов устанавливается исключительно через инсталлятор при первой установке. В самом веб-интерфейсе RatioT SCADA и в документации нет управления или описания этого режима.

Однако в официальной документации (`licensing.htm`, `ls_license_server.htm`, `ls_config_license_server.htm`, `ls_requirements.htm`) описаны только именные лицензии, привязанные к инсталляции, и централизованный сервер лицензий. Пробный и бесплатный режимы не упоминаются.

### Воспроизведение
1. Запустить установку `RatioT SCADA 6.41.09`.
2. На шаге «Выберите тип лицензии» увидеть два варианта: «Пробная лицензия (30 дней)» и «Бесплатная лицензия на 100 тэгов».
3. Открыть `https://localhost:8443/static/docs/licensing.htm`.
4. Убедиться, что раздел описывает только именные лицензии и активационный ключ.
5. Проверить `ls_license_server.htm` и `ls_config_license_server.htm` — там также нет описания free/trial.

### Ожидаемый результат
Документация должна содержать раздел о бесплатном и пробном режимах: какие ограничения, как переключаться, что происходит по истечении срока/при превышении лимита тегов, можно ли использовать в продакшене.

### Фактический результат
Пользователь видит в инсталляторе режимы, о которых в документации ни слова. Непонятно:
- чем отличаются free и trial;
- что будет после 30 дней или после 100 тегов;
- можно ли перейти с free/trial на полную лицензию без переустановки.

## Кейс 3. Инсталлятор запрашивает перезапись собственных файлов

**Критичность:** Low  
**Тип:** Установка / UX
**Категория:** 2. Ошибки OEM

Тикет АГ: `ASD-6483`.

### Описание
При установке RatioT SCADA 6.41.09 инсталлятор выдаёт диалог «Файл уже существует. Вы хотите, чтобы программа установки заменила его?» для файлов внутри `C:\Program Files\RatioTScada\admin\custom\templates\docs_ru\wizard_1.png` и `wizard_2.png`. Это создаёт впечатление, что установка повторяется поверх существующей, или что инсталлятор не может корректно управлять своими же файлами.

### Воспроизведение
1. Запустить установку RatioT SCADA 6.41.09.
2. Пройти шаги до копирования файлов.
3. Дождаться диалога с предложением заменить `docs_ru\wizard_1.png`.
4. Нажать «Да для всех».
5. Через некоторое время появится аналогичный диалог для `docs_ru\wizard_2.png`.

### Ожидаемый результат
На чистой установке инсталлятор не должен спрашивать о перезаписи собственных файлов. Если это обновление — должен быть единый диалог «Заменить все» или тихая перезапись без лишних подтверждений.

### Фактический результат
Пользователь вынужден несколько раз вручную подтверждать перезапись файлов, которые только что были скопированы установщиком. Это выглядит как ошибка упаковки инсталлятора: одни и те же файлы попадают в разные компоненты/директории и конфликтуют при распаковке.

**Подтверждено в 6.41.11 (01.09.2026):** при установке RatioT SCADA 6.41.11 проблема сохраняется — инсталлятор снова выводит диалог «Файл уже существует... docs_ru\wizard_1.png. Вы хотите, чтобы программа установки заменила его?».

## Кейс 4. Импорт Modbus-регистров из CSV/XML теряет имена, описания и адреса; экспорт в CSV портит русскую кодировку

**Критичность:** High  
**Тип:** Импорт / экспорт данных
**Категория:** 3. Ошибки платформы партнёра

### Описание
При создании пустого Modbus-устройства и импорте регистров из ранее экспортированных файлов CSV/XML теряются имя, описание, адрес, размер и другие поля. Импорт того же файла в формате `.tbl` работает корректно. Кроме того, окно экспорта не содержит кнопки закрытия — чтобы выйти, пользователь вынужден что-то экспортировать. При экспорте регистров с русскими именами/описаниями в CSV в полученном файле русский текст отображается кракозябрами.

### Воспроизведение
1. Открыть `https://localhost:8443` и войти под `admin / admin`.
2. Перейти в дереве: **Устройства → modbus → Конфигурация → Регистры устройства**.
3. Создать несколько регистров с именами и описаниями на русском языке.
4. Нажать кнопку экспорта и сохранить файл в форматах `.csv`, `.xml`, `.tbl`.
5. Удалить все регистры или создать новое пустое Modbus-устройство.
6. Импортировать сохранённые `.csv` и `.xml`.
7. Сравнить заполненность полей с исходными данными и с импортом `.tbl`.
8. Открыть экспортированный `.csv` в Excel/Notepad++ и проверить кодировку русских строк.

### Ожидаемый результат
- CSV и XML импортируют все поля аналогично `.tbl`.
- Диалог экспорта можно закрыть без выполнения экспорта.
- CSV-файл содержит корректную UTF-8 / Windows-1251 кодировку для русских символов.

### Фактический результат
- После импорта CSV/XML поля **Имя**, **Описание**, **Десятичный адрес**, **Размер** остаются пустыми.
- Диалог экспорта нельзя закрыть без экспорта.
- CSV-файл содержит нечитаемые символы вместо русского текста.

### Уточнение по лицензированию
При проверке на текущей trial-лицензии (`Trial License`, 0/100 устройств) в диалоге добавления устройства драйвер **Modbus** отсутствует. В списке доступны IEC-104, Агент, BACnet, DNP3 и др., но Modbus нет. Это не позволяет лично воспроизвести импорт/экспорт регистров в данном контуре. Скриншоты самого бага (пустые поля, кодировка) предоставлены коллегами с полноценной лицензией.

### Статус (ASD-6484)
Тикет АГ `ASD-6484` (критический, создан 20.08.2026) закрыт, обновлён 24.08.2026. Тикет коллег `ASD-6455` (Сыченко Артем, 10.08.2026) — также закрыт. Самостоятельная проверка исправления в новой сборке не проводилась (в trial-контуре нет драйвера Modbus).

**Итог: закрыто АГ (ASD-6484; тикет коллег ASD-6455 тоже закрыт), самостоятельно не проверялось.**

## Кейс 5. Настройки колонок компонента eventLog сбрасываются при поступлении событий

**Критичность:** High  
**Тип:** Web UI / дашборды / компонент eventLog
**Категория:** 3. Ошибки платформы партнёра

### Описание
В дашборде добавлен элемент **Журнал событий (eventLog)**. В расширенных настройках на вкладке **Колонки** включена опция «Ширина колонок настроена вручную», задан порядок колонок, их ширина и видимость. Настройки применяются, пока событий нет; как только поступает событие, таблица возвращается к дефолтному виду и отображаются все колонки, включая скрытые.

### Воспроизведение
1. Открыть дашборд (например, `АВР.Главный экран`).
2. Добавить или отредактировать компонент **Журнал событий**.
3. В разделе **Расширенные → Колонки** включить «Ширина колонок настроена вручную».
4. Скрыть колонки **Подтверждение** и **Обогащение**, задать порядок и ширину остальных.
5. Сохранить дашборд.
6. Дождаться/сгенерировать событие (например, переключение режима работы).
7. Убедиться, что таблица вернулась к стандартному набору колонок.

### Ожидаемый результат
Настроенные колонки сохраняются независимо от наличия событий.

### Фактический результат
При поступлении события отображаются все колонки, настройки не применены.

### Уточнение по лицензированию
При проверке на trial-версии редактор дашбордов в веб-клиенте недоступен (нет кнопки/раздела для добавления/редактирования компонентов), поэтому лично воспроизвести настройку колонок eventLog в данном контуре не удалось. Скриншоты бага предоставлены коллегами с полноценной лицензией.

### Скриншоты

- ![настройки колонок без данных](tests/screenshots/eventlog_columns_nodata.png) — настройки колонок без данных
- ![список полей eventLog](tests/screenshots/eventlog_columns_list.png) — список полей eventLog
- ![журнал с событием: видны все колонки](tests/screenshots/eventlog_with_event.png) — журнал с событием: видны все колонки

## Кейс 6. В дереве тегов невозможно выбрать абсолютную модель в качестве источника

**Критичность:** Medium  
**Тип:** UX / дерево тегов / документация

## Кейс 9. Установка в нестандартную папку + замена лицензии приводит к отказу лицензирования и новому activation key

**Критичность:** High  
**Тип:** Установка / лицензирование
**Категория:** 2. Ошибки OEM

Тикет АГ: `ASD-6487`.

### Описание
При установке RatioT SCADA в папку, отличную от предыдущей, инсталлятор всё равно запрашивает согласие на копирование/перезапись файлов. После замены файла лицензии в новой папке программа продолжает сообщать об отсутствии лицензии. Служба сервера запускается и перезапускается, но веб-сервер не отвечает. В итоге требуется полное удаление всех версий; при новой установке генерируется новый activation key, и старая лицензия не принимается.

### Воспроизведение
1. Установить RatioT SCADA в папку A (например, `C:\Program Files\RatioTScada`).
2. Получить и сохранить файл лицензии для activation key A.
3. Установить ту же или новую версию RatioT SCADA в папку B (например, другой диск или подпапку).
4. На шаге копирования согласиться с перезаписью/копированием файлов.
5. Подменить файл лицензии в папке B файлом от папки A.
6. Запустить сервер.

### Ожидаемый результат
- Инсталлятор корректно определяет новую директорию и не запрашивает перезапись.
- Замена файла лицензии приводит к её активации, либо в интерфейсе есть понятная инструкция, как обновить ключ.
- Веб-сервер становится доступен после запуска службы.

### Фактический результат
- Инсталлятор требует подтверждения копирования даже при разных папках.
- Лицензия не активируется; сервер не отвечает по вебу.
- После удаления и переустановки генерируется новый activation key, и старая лицензия не подходит.

## Кейс 27. Прямые ссылки на настройки сервера и лицензии возвращают JSON 404

**Серьёзность:** Medium  
**Тип:** Web UI / обработка ошибок
**Категория:** 3. Ошибки платформы партнёра

### Описание
Прямые URL, которые могут использоваться в закладках, документации или внутренних ссылках, возвращают сырой JSON-ответ об ошибке 404 вместо HTML-страницы 404. При этом пользовательский путь через кнопку **Настроить сервер** и вкладку **Лицензионная информация** внутри **Информации о сервере** работает корректно.

### Воспроизведение
1. Войти в веб-клиент или открыть новую вкладку браузера.
2. Перейти по URL `https://localhost:8443/web/context/users.admin.server.properties`.
3. Перейти по URL `https://localhost:8443/web/context/users.admin.licenseInfo`.
4. Убедиться, что в обоих случаях отображается JSON-ответ `{"type":"about:blank","title":"Not Found","status":404,...}` вместо HTML-страницы.

### Ожидаемый результат
По прямым ссылкам на внутренние разделы открывается либо сам раздел, либо единая HTML-страница 404 с понятным сообщением.

### Фактический результат
Отображается сырой JSON 404.

### Проверка в 6.41.11 (ASD-6505, ответ АГ: «не является ошибкой, единая модель данных; используйте редирект-дашборды или REST API с Bearer-токеном»)

Проверено на локальной установке 6.41.11 (сборка 2544):

1. **Прямые URL.** Анонимно оба адреса теперь возвращают JSON 401 `{"error":"AUTHENTICATION_REQUIRED"}` (в 6.41.10 был сразу JSON 404). После входа в веб-клиент тот же URL возвращает JSON 404: `No endpoint GET /web/context/users.admin.licenseInfo.` — эндпоинтов «страница по пути контекста» действительно нет, сырой JSON вместо HTML-страницы 404 по-прежнему отображается.
2. **Пользовательский путь через UI работает.** Системное дерево → правый клик по корневому узлу «RatioT Server v6.41.11» → «Показать информацию о сервере» → вкладка «Лицензионная информация» открывается корректно (Trial License, испытательный период 30 дней, макс. 100 устройств). Пункт «Настроить сервер» доступен в том же контекстном меню.
3. **REST API (предложение АГ) функционирует.** `POST /rest/auth` с логином/паролем возвращает токен; `GET /rest/v1/contexts/users.admin` с заголовком `Authorization: Bearer <токен>` возвращает 200 и данные контекста. Это интеграционный API: для «прямой ссылки в закладках браузера» неприменим, так как обычный переход по ссылке не передаёт кастомный заголовок Authorization.

**Итог: принимаем позицию АГ по сути обращения — прямой доступ к настройкам «к к файлу» по URL является by design.** Ответ на вопрос АГ «на основании чего предположили, что должно работать иначе»: ожидание касалось не доступа к переменным, а единообразия обработки ошибок в веб-клиенте — пользователь по любой «битой» ссылке внутри `/web/*` видит сырой JSON, тогда как другие разделы сервера отдают HTML-страницу 404. Это непоследовательное поведение зафиксировано отдельно в **кейсе 14** и остаётся актуальным; настоящий кейс можно закрывать. Тикет ASD-6505 закрыт АГ: статус «Закрыто», решение «Done».

Окно «Результат обновления» пустое (No Data). Невозможно перенести разработки между серверами.

### Ответ АГ (ASD-6521)
«Провели тестирование на версии 6.41.11-2553 — проблема отсутствует». Алгоритм проверки АГ (воспроизводим на одном сервере): создать приложение «test» → добавить ресурс и сохранить изменения → упаковать и выгрузить приложение как ZIP-архив → удалить все ресурсы из приложения и сохранить → выполнить обновление ранее выгруженным архивом (окно «Результат обновления» заполнено: «Контекст обновлён», «Контекст пропущен») → ресурс добавлен обратно («Мастер настроек тревог»).

**Итог: по ответу АГ исправлено в 6.41.11-2553. Самостоятельная проверка нашей командой не проводилась — сценарий переноса требует двух контуров (полигон → эталон); при наличии двух серверов рекомендуется контрольная проверка по алгоритму АГ.**

### Скриншоты

## Кейс 29. Не работают дополнительные свойства при использовании относительных инструментальных панелей

**Серьёзность:** Low  
**Тип:** Инструментальные панели / дополнительные свойства  
**Категория:** 3. Ошибки платформы партнёра
**Источник:** коллеги (ilya.tarynin@dkc.ru), тикет [ASD-6523](https://tibbotech.atlassian.net/servicedesk/customer/portal/1/ASD-6523)

### Описание
При использовании относительных инструментальных панелей не работает функционал дополнительных свойств: на мнемосхеме панель дополнительных свойств («Общие данные») отображается, но все её поля пустые (Статус ПВ, Сезон, Наличие аварий, Режим управления, Уставка темп. ПВ, Полоса регулирования, Температура ПВ, Уставка наружного возд., Задание на ПЧ вент.).

### Воспроизведение (по описанию коллег)
1. Открыть инструментальную панель, использующую относительные инструментальные панели (мнемосхема контролируемого агрегата, вкладки «Графические данные / Свойства / Аварийные сигналы / Тренды»).
2. Открыть панель дополнительных свойств («Общие данные»).
3. Убедиться, что значения дополнительных свойств не подгружаются (все поля пустые).

### Ожидаемый результат
Дополнительные свойства отображают актуальные значения.

### Фактический результат
Все поля дополнительных свойств пустые.

**Итог: по ответу АГ исправлено в 6.41.11-2553 (задача разработки №20649). Самостоятельная проверка нашей командой не проводилась — требуется контур с мнемосхемой, использующей относительные инструментальные панели.**

<a id="case-30"></a>
## Кейс 30. Не работает eventLog при использовании относительных инструментальных панелей

**Серьёзность:** Low  
**Тип:** Инструментальные панели / eventLog  
**Категория:** 3. Ошибки платформы партнёра
**Источник:** коллеги (ilya.tarynin@dkc.ru), тикет [ASD-6522](https://tibbotech.atlassian.net/servicedesk/customer/portal/1/ASD-6522)

### Описание
Для элемента eventLog нет возможности указать маску контекстов отображаемых событий посредством контекстной ссылки, возвращаемой контекстом по умолчанию (`{.:}` или `dc()`). Такой подход нужен при реализации имплантов, когда относительная инструментальная модель, используемая для реализации импланта, содержит элемент «Лог Тревог», в котором должны быть отражены события контекста, к которому привязан имплант.

### Воспроизведение (по описанию коллег)
1. Реализовать имплант на основе относительной инструментальной модели, содержащей элемент eventLog («Лог Тревог»).
2. В настройках элемента eventLog указать маску контекстов отображаемых событий контекстной ссылкой `{.:}` (или `dc()`), чтобы лог показывал события контекста, к которому привязан имплант.
3. Сохранить и открыть панель импланта.

### Ожидаемый результат
События контекста, указанного для импланта, отображаются в логе.

### Фактический результат
События не отображаются.

### Ответ АГ (ASD-6522)
«Чтобы мы могли оперативно и точно разобраться в ситуации, нам очень не хватает деталей. Не могли бы вы дополнить запрос: приложите, пожалуйста, все контексты по задаче и распишите пошаговый сценарий воспроизведения».

**Итог: ожидает ответа коллег — АГ запросили контексты и пошаговый сценарий воспроизведения.**

### Скриншоты
- Скриншоты приложены в тикете ASD-6522. Файлы `tests/screenshots/case30_*.png` — вносятся.
