Руководство пользователя RatioT SCADA

Эта страница — подробная выжимка из официальных руководств. Здесь собрано то, как устроена система, как в неё входить, как работать с устройствами, дашбордами, данными, авариями и правами доступа.

Материал опирается на «Руководство по развёртыванию» и «Руководство по эксплуатации». Если какой-то момент в руководстве не раскрыт, это отмечено отдельно.

Что такое RatioT SCADA и зачем она нужна

RatioT SCADA — это программная платформа для диспетчеризации, мониторинга и управления промышленными объектами, инженерными системами и оборудованием.

Что умеет платформа

Сбор данных

Подключает PLC, RTU, датчики, счётчики, IoT-устройства по десяткам промышленных протоколов и считывает текущие значения.

Визуализация

Показывает состояние объектов на мнемосхемах, дашбордах, трендах, таблицах и SVG-схемах в реальном времени.

Управление

Позволяет оператору подавать команды на оборудование: включить/выключить, изменить уставку, запустить тест, квитировать аварию.

Аварии и события

Фиксирует отклонения, формирует аварийные сообщения, журналы, отправляет уведомления (e-mail/SMS) и контролирует SLA.

История и отчёты

Хранит временные ряды, события и архивы. Позволяет строить отчёты и аналитику через SQL, R, Python или встроенные инструменты.

Разделение доступа

Каждый пользователь видит только свои объекты и дашборды. Поддерживаются роли, группы устройств, интеграция с LDAP/AD.

Кто работает с системой

  • Операторы / диспетчеры — смотрят текущее состояние, реагируют на аварии, управляют оборудованием.
  • Инженеры / наладчики — настраивают устройства, создают дашборды, пишут скрипты.
  • Администраторы — управляют пользователями, лицензиями, сервером, резервным копированием.
  • Руководство / аналитики — используют отчёты и исторические данные для принятия решений.

Вход и первые шаги

Как открыть Web UI

  • С этого же ПК: клик ПКМ по иконке RatioT Server в системном трее → Open RatioT Server Web UI.
  • С любого устройства в сети: браузер Google Chrome или Mozilla Firefox → https://<IP_сервера>:8443/web.
  • HTTP-вариант работает только если в глобальной конфигурации сервера включён незащищённый доступ к веб-приложениям: http://<IP_сервера>:8080/web.
  • Если сервер запущен локально — https://localhost:8443/web.
  • Если браузер ругается на самоподписанный сертификат, нужно принять исключение и продолжить.
  • Нестандартные порты уточняйте в конфигурации сервера (server.xml → webAppsSslPort/webAppsNonSslPort) или через RatioT Client.

Авторизация

  • Логин и пароль по умолчанию у администратора: admin / admin.
  • Вход выполняется через React-приложение (SPA). Страница входа отрисовывается в браузере; кастомизация возможна через настройки сервера / встроенные механизмы брендинга.
  • При включённой саморегистрации (usersSelfRegistration = true) на странице входа доступна кнопка Зарегистрироваться.

Что видно после входа

  • Открывается Default Dashboard — стартовая инструментальная панель.
  • По умолчанию она содержит Системное дерево и Приветствие с подсказками дальнейших действий.
  • Если у пользователя не настроен автозапуск и используется упрощённый режим, после входа можно увидеть пустую страницу. Это не ошибка — нужно задать автозапуск или перейти к нужному дашборду.
  • В шапке основные пункты: логотип/ссылка на домашний дашборд, Home, Logout.
  • Дальше пользователь перемещается по дашбордам через кнопки, ссылки, таблицы и динамические панели.

Как устроена система: иерархия объектов

Вся конфигурация RatioT SCADA хранится в виде иерархии контекстов. Каждый объект — это узел в дереве, у которого есть свойства, функции, события и дочерние объекты.

Общее дерево

users
  └── <username>
        ├── dashboards
        │     └── <dashboard_name>
        ├── deviceservers
        │     └── <device_server_name>
        │           └── devices
        │                 └── <device_name>
        │                       └── <tags / properties>
        ├── devgroups
        │     └── <group_name>
        ├── models
        │     └── <model_name>
        ├── queries
        │     └── <query_name>
        ├── alerts
        │     └── <alert_name>
        └── autorun

Ключевые понятия

Как обращаться к объектам

Каждый объект имеет путь в дереве. Примеры путей, которые встречаются в документации:

  • Устройство: users.admin.deviceservers.ds1.devices.thermostat
  • Тег температуры: users.admin.deviceservers.ds1.devices.thermostat:temperature$temperature
  • Дашборд: users.admin.dashboards.overview
  • Модель: users.admin.models.pump
  • Запрос: users.admin.queries.energy_consumption
  • Авария: users.admin.alerts.water_level_warning

Маска users.* означает «все пользователи». Маска users.*.devices.* означает «все устройства всех пользователей».

Устройства и теги

Из чего состоит работа с устройством

Чтобы получать данные из оборудования, в системе нужно настроить цепочку:

  1. Device Server — канал/протокол/шлюз.
  2. Device — конкретное устройство на этом канале.
  3. Tag / Property — переменная внутри устройства, которую нужно считывать или записывать.

Пример пути к тегу

users.admin.deviceservers.ds1.devices.thermostat:temperature$temperature

Здесь:

  • users.admin — пользователь-владелец.
  • deviceservers.ds1 — Device Server с именем ds1.
  • devices.thermostat — устройство «термостат».
  • temperature — контекст/сущность тега.
  • temperature$temperature — значение температуры.

Как читать значение в binding

{users.admin.deviceservers.ds1.devices.thermostat:temperature$temperature}

Такое выражение можно привязать к label, gauge, chart, table или использовать в условии.

Как вызвать действие на устройстве

У устройств и Device Server есть функции. Примеры из документации:

  • Перезагрузить устройство: users.admin.devices.dev1:reboot()
  • Подать сигнал на Device Server: users.admin.deviceservers.ds1:buzz()
  • Запустить самотестирование: users.admin.deviceservers.ds1.devices.1:selfTest("quick")

Действие вызывается через binding или скрипт:

{users.admin.deviceservers.ds1:buzz()}

Качество и статус тега

У каждого тега есть не только значение, но и качество (quality) — насколько актуальны данные. Например, если связь с устройством пропала, качество меняется, и это можно отобразить цветом или диагностической панелью.

Статус Device Server

Device Server имеет объект deviceServerInfo и status. Через них можно узнать:

  • Кто владелец, имя сервера.
  • Статус соединения (status).
  • Объём трафика: servertods (сервер → DS) и dstoserver (DS → сервер).

Пример SQL-запроса для мониторинга Device Server:

SELECT
  info.deviceServerInfo$owner,
  info.deviceServerInfo$name,
  info.status$servertods,
  info.status$dstoserver
FROM
  users.*.deviceservers.*:status:deviceServerInfo as info
ORDER BY
  info.deviceServerInfo$owner,
  info.deviceServerInfo$name

Модели и группы устройств

Модель (Model)

Модель — это шаблон. Она описывает, какие теги, свойства, события и функции есть у типового устройства. Например, модель «насос» может содержать теги:

  • state — включён/выключен.
  • pressure — давление.
  • temperature — температура двигателя.
  • runtime — наработка.

Когда инженер создаёт реальное устройство, он может указать, что оно основано на модели users.admin.models.pump. Тогда устройство автоматически получает все теги и функции модели.

Группы устройств (devgroups)

Группы позволяют объединять устройства для удобного доступа и запросов. Пример:

users.admin.devgroups.genericGroup.virtural

Маска users.admin.devgroups.genericGroup.* покроет все устройства группы. Это удобно, когда нужно:

  • Отобразить таблицу по нескольким устройствам.
  • Применить один запрос или аварию к группе.
  • Ограничить права пользователя не одним устройством, а группой.

Пример функции для получения переменной из группы:

getVariable("users.admin.devgroups.genericGroup.virtural", "info")

Наследование и копирование

Контексты можно копировать. Функция makeCopy() создаёт копию объекта с его дочерними элементами и переменными. Это полезно, когда нужно быстро размножить похожие устройства или дашборды.

Дашборды и Конструктор Web UI

Что такое дашборд

Дашборд (в терминологии документации — инструментальная панель) — это основная единица интерфейса Web UI. Технически панель — это контекст сервера, который в runtime отображается как динамическая веб-страница.

Панели хранятся в контексте пользователя:

users.<username>.dashboards.<dashboard_name>

Примеры:

  • users.admin.dashboards.overview — общий обзор.
  • users.admin.dashboards.landingDashboard — посадочная страница.
  • users.admin.dashboards.administration — административный дашборд.

Default Dashboard

Сразу после входа открывается Default Dashboard. По умолчанию он содержит:

  • Системное дерево — навигация по объектам сервера.
  • Приветствие — подсказки по дальнейшим действиям.

Если включён упрощённый режим и у пользователя не настроен автозапуск, после входа может отображаться пустая страница. Для операторов нужно настроить список автозапуска, чтобы сразу открывался целевой интерфейс.

Как открыть дашборд по прямой ссылке

Можно дать оператору конкретный URL:

https://<host>:8443/web/dashboards/users.admin.dashboards.overview

Если для дашборда настроен alias, можно использовать короткое имя:

https://<host>:8443/web/dashboards/landingDashboard

Конструктор Web UI (Web UI Builder)

Конструктор Web UI — это low-code среда разработки пользовательских веб-интерфейсов прямо в браузере. Интерфейсы строятся на той же модели данных, что и серверные объекты. Поддерживается пиксельная точность, адаптивность и маршрутизация между панелями.

В редакторе можно:

  • Создать форму (form) и многоуровневые контейнеры.
  • Добавить компоненты: label, button, text field, number field, image, gauge, chart, data table, panel, векторные изображения и др.
  • Настроить свойства компонентов.
  • Привязать компоненты к данным через binding.
  • Добавить обработчики событий: click, mouseClicked, valueChanged и т.д.
  • Стилизовать через CSS.

Важно: в документации внутри программы встречается также термин Редактор виджетов / GUI Builder. Это отдельный инструмент десктопного RatioT Client для редактирования шаблонов виджетов, а не Web UI.

Структура адреса компонента

Каждый компонент внутри формы имеет адрес:

form/<component_name>:<property>

Примеры:

  • form/label1:text — текст label.
  • form/textField1:value — значение текстового поля.
  • form/button1:click@ — событие клика кнопки.
  • form/gauge:datasets[1] — первый набор данных gauge.
  • form/image1:imageTable$imageData[0] — данные изображения.

Пример из руководства: простая мнемосхема

На форме размещены:

  • Label label0 — показывает значение.
  • Label label1 — показывает округлённое значение.
  • Button button0 — обновляет значение.

Binding label:

{users.admin.devices.virtual:random}

Округление и масштабирование:

round(10 * {users.admin.devices.virtual:random})

Обработчик кнопки:

form/button0:mouseClicked@

Адаптивность и CSS

Каждый компонент можно стилизовать через CSS. Пример из руководства:

{
  font-size: 1.5em;
  margin-left: 20%;
}

Дашборд поддерживает адаптивные breakpoints: Mobile, Tablet, Laptop, Full HD, QHD, Ultra HD. Для каждого breakpoint можно задать своё поведение компонентов.

Компоновка контейнеров

Каждый контейнер в панели использует одну из компоновок:

  • Сетка (Grid) — компоненты размещаются по ячейкам. Удобно для адаптивных форм.
  • Абсолютное позиционирование (Absolute) — компоненты размещаются по координатам X/Y. Удобно для точных мнемосхем и HMI.
  • Плавающие элементы / Dockable — компоненты «прилипают» к сторонам контейнера или могут свободно позиционироваться.

Переходы между дашбордами

Из binding или скрипта можно открыть другой дашборд:

{web/redirect("users.admin.dashboards.detail")}

Можно передать параметры:

{web/redirect("users.admin.dashboards.detail", false, false, 'structure("key","value1","value2")')}

Аргументы:

  • Первый — целевой дашборд.
  • Второй — менять ли URL в истории (false — не менять).
  • Третий — открывать в новой вкладке (false — текущая).
  • Четвёртый — параметры, которые попадут в целевой дашборд.

Компоненты и binding

Основные категории компонентов

  • Контейнеры — panel, form, вкладки, группы. Поддерживают сетку, абсолютное и плавающее позиционирование.
  • Элементы ввода — label, button, text field, number field, checkbox, radio, slider, dropdown, date/time picker и др.
  • Отображение данных — Data Table, Event Log, таблицы, журналы.
  • Навигация — меню, breadcrumbs, кнопки перехода.
  • Графики и диаграммы — line, area, bar, pie, polar, spider, gauge, map, Gantt и др.
  • Графика — Image, Векторное изображение (SVG), Динамическое векторное изображение, Библиотека символов HMI (трубы, котлы, вентиляторы и т.д.).
  • HMI-шаблоны — Имплант (встроенный reusable-блок) и Вложенная панель (subdashboard) для сборки сложных мнемосхем.

Binding — связывание с данными

Binding — это low-code механизм, при котором свойство компонента автоматически обновляется из значения тега или выражения. Синтаксис:

{context:property}

Примеры:

  • Простое значение: {users.admin.devices.virtual:random}
  • Масштабирование: {form/numberField1:value} * 100
  • Округление: round(10 * {users.admin.devices.virtual:random})

В редакторе таблиц данных (Data Table Editor) привязки редактируются двумя полями: Цель — куда записывается значение, и Выражение — вычисляемое выражение.

Условия и цвета

Можно менять внешний вид компонента в зависимости от данных:

{.:voltageAlert$voltageAlert}
  ? "background-color: red"
  : "background-color: green"

Или:

({.:voltage$voltage} > 50)
  ? "background-color: red"
  : "background-color: green"

События

События обозначаются через @:

  • form/button1:click@ — клик левой кнопкой.
  • form/button1:mouseClicked@ — клик мышью.
  • form/numberField0:value — значение поля.

SVG-графика и HMI

RatioT SCADA поддерживает SVG и библиотеку динамических символов для HMI. Доступны:

  • Векторное изображение — статичный SVG.
  • Динамическое векторное изображение — SVG с привязкой состояния.
  • Библиотека символов HMI — готовые элементы: трубопроводы, котлы, вентиляторы и т.д.

Пример с вентилятором:

  • SVG-элемент Fan привязан к состоянию form/Fan:state.
  • Индикатор Indicator меняет цвет в зависимости от состояния.
  • Клик по вентилятору переключает состояние: {form/Fan:state} == "on" ? 'off' : 'on'.

Для SVG-манипуляций используется библиотека svgManipulation.

Имплант и вложенная панель

Для повторяющихся и сложных блоков используются:

  • Имплант — встроенный reusable-шаблон (например, мотор с SVG, кнопками, заданными значениями, мини-трендом).
  • Вложенная панель (subdashboard) — вставка одной панели внутрь другой.

Динамические панели

Панель может генерировать дочерние компоненты из таблицы. Это позволяет рисовать списки, карточки, повторяющиеся блоки. В руководстве пример с торговым автоматом: у автомата 6 ячеек, каждая ячейка — это динамически созданная панель с label и кнопкой.

Действия (Actions)

Действие — это вызов функции или метода контекста. Примеры:

  • {cardholders:import!} — импортировать карточки.
  • {users.admin.deviceservers.ds1:buzz()} — подать сигнал.
  • callFunction("", "executeQuery", {form/queryText:text}) — вызвать функцию executeQuery с параметром.

Данные, запросы, отчёты

SQL внутри RatioT SCADA

RatioT SCADA позволяет писать SQL-запросы к данным системы. Это не классическая БД, а специальный SQL-подобный слой, который работает с контекстами и тегами.

Пример запроса к событиям входа:

SELECT *
FROM events:get('users', 'login') as logins
WHERE logins.get$username = 'john'

Пример с использованием внешней БД:

{users.admin.devices.linkserver_database:executeQuery(
  "SELECT * FROM logins WHERE username = 'john'"
)}

Именованные запросы (Queries)

Запросы можно сохранять в контексте пользователя и вызывать по имени:

users.<username>.queries.<query_name>

Пример из руководства:

{users.admin.queries.energy_consumption:execute()}

Data Table

Data Table — основной компонент для отображения табличных данных. Он может показывать:

  • Результат запроса.
  • Значения нескольких тегов.
  • Исторические данные.
  • Фильтрованные события.

В таблице можно настраивать столбцы, фильтры, сортировку, подсветку строк и действия по клику.

Группировка и агрегаты

В SQL-запросах поддерживаются агрегатные функции: COUNT, MIN, MAX, SUM, AVG. Пример мониторинга загрузки процессоров:

SELECT
  info.info$description AS device,
  avg(processors.hrProcessorTable$hrProcessorLoad) AS processor_utilization_percentage
FROM
  users.*.devices.*:hrProcessorTable AS processors
LEFT OUTER JOIN
  users.*.devices.*:info as info
ON
  processors$CONTEXT_ID = info$CONTEXT_ID
GROUP BY
  device
HAVING
  avg(processors.hrProcessorTable$hrProcessorLoad) > 90
ORDER BY
  processor_utilization_percentage DESC

Историк и временные ряды

Исторические данные хранятся в historian'е. По умолчанию используется Apache Cassandra, но можно подключить и другие хранилища. Для получения истории используются функции типа statistics или SQL-запросы к историческим таблицам.

Пример статистики по энергопотреблению из руководства:

SELECT
  stats.statistics$context as "Device Context",
  stats.statistics$end as "Period",
  stats.statistics$average * 60 as "Average kW per hour"
FROM
  utilities:statistics("users.admin.devices.virtual", "energy_consumption", null, "hour") as stats

Аварии и события

Что такое события и аварии

  • Событие — любая запись в журнале: вход, изменение значения, действие оператора.
  • Авария (Alert) — событие, требующее реакции. Имеет уровень критичности и может быть квитирована.

Структура активной аварии

Активные аварии хранятся в контексте activeAlerts. Основные поля:

ПолеСмысл
locationГде произошла авария (контекст).
eventID события.
alertТекст/имя аварии.
typeТип аварии.
timeВремя возникновения.
levelУровень критичности (0 — самый высокий).
keyКлюч, по которому аварии группируются.
messageСообщение для оператора.
triggerУсловие, по которому сработала авария.
causeПричина.
acknowledgementsКто и когда квитировал.

Уровни аварий

В документации встречаются уровни от 0 до 5. Обычно:

  • 0 — критичный.
  • 1 — высокий.
  • 2 — средний.
  • 3 — низкий.
  • 4–5 — информационный.

Конкретная расшифровка уровней зависит от настройки проекта.

Квитирование

Аварии можно квитировать из таблицы или по нажатию кнопки. В binding/скрипте используется соответствующее действие над контекстом аварии.

SLA и мониторинг

В руководстве развёртывания приведён пример SLA: если процессор загружен более 80% и текущая загрузка на 20% выше средней за 6 периодов, фиксируется событие. Это показывает, что система умеет строить условия на основе исторических данных и временных окон.

Фильтры событий

Оператор может настроить фильтры, чтобы видеть только свои события, события по устройству или за период. Фильтры хранятся в контексте пользователя, например:

users.<username>.filters.<filter_name>

Пользователи и доступ

Иерархия доступа

Вся модель безопасности построена на иерархии контекстов. Пользователь видит только те объекты, которые лежат в его ветке users.<username>.*.

  • Администратор users.admin видит практически всё, включая users.*.
  • Обычный пользователь видит только users.<свой_логин>.*.
  • Можно задать доступ через группы устройств: users.<username>.devgroups.<group>.

Примеры путей доступа

users.admin.devices.thermometer1          // устройство администратора
users.user1.devices.gateway1              // устройство пользователя user1
users.*.devices.*                         // все устройства всех пользователей (для админ-запросов)

Регистрация пользователей

В конфигурации сервера есть параметр usersSelfRegistration:

  • true — новые пользователи могут зарегистрироваться сами через Web UI.
  • false — только администратор создаёт пользователей.

Интеграция с корпоративной системой

RatioT SCADA поддерживает аутентификацию через LDAP/Active Directory и RADIUS. Это позволяет использовать корпоративные учётные записи и централизованное управление правами.

Типовые задачи

1. Просмотр текущих значений

Открыть дашборд → посмотреть на label, gauge или chart. Значения обновляются сами, потому что привязаны к тегам.

2. Управление оборудованием

Нажать кнопку → вызвать action → устройство выполняет команду. Например, buzz(), reboot(), selfTest().

3. Подтверждение аварии

В таблице активных аварий нажать кнопку «Квитировать» или выполнить соответствующее действие над контекстом аварии.

4. Просмотр истории

Открыть Data Table с историческими данными, выбрать период, применить фильтр.

5. Переход к деталям объекта

Клик по строке или кнопке → web/redirect() → открывается детальный дашборд устройства.

6. Построение отчёта

Ввести параметры в поля формы → нажать кнопку → таблица обновляется результатом SQL-запроса или вызова функции.

7. Настройка нового устройства

Создать Device Server, внутри него создать Device, настроить теги. Устройство можно привязать к модели, чтобы унаследовать стандартный набор тегов и функций.

8. Создание дашборда

Открыть Web UI Builder, создать форму, добавить компоненты, настроить binding и CSS, сохранить как дашборд в users.<username>.dashboards.

Что нужно уточнить

Руководства описывают модель данных, binding, SQL и примеры дашбордов, но не всегда дают пошаговые клики для каждого экрана. Для полного руководства «кнопка за кнопкой» нужно либо дополнительное руководство от разработчиков, либо практическая запись экрана.

  • Точные шаги создания Device Server и Device в Net Admin/Web UI Builder — не раскрыты в доступных PDF.
  • Детали настройки конкретных протоколов (Modbus, OPC UA, SNMP и т.д.) лежат в отдельных разделах руководства по эксплуатации.
  • Административные операции (пользователи, лицензии, backup) выполняются в Net Admin на порту 6440.
