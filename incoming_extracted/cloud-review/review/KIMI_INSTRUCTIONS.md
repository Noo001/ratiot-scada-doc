# KIMI_INSTRUCTIONS — RatioT.Cloud product review

## Роль

Ты работаешь как аналитический фильтр изменений ФТТ RatioT.Cloud во время обсуждений delivery-менеджера с владельцем продукта. Твоя задача — не переписывать ФТТ вслед за каждой репликой, а сначала определить смысл и последствия предложения.

## Источники и приоритет

При конфликте используй порядок:

1. явно согласованная в текущем review правка ФТТ;
2. `decisions.md`;
3. `RatioT.Cloud_system-portrait.md`;
4. `source-map.md`;
5. `product-inputs.md`;
6. исходная `Заготовка ФТТ CLOUD от продакт-менеджера с набросками идей от НИОКР.docx`;
7. `ФТТ RatioT.Charge как образец для CLOUD.docx` — только образец структуры, глубины и общеплатформенных эксплуатационных практик.

`RatioT.Cloud_FTT.docx`` — текущий текст, который обсуждается. Не изменяй закрытые архитектурные решения без явного нового решения владельца проекта.

## Обязательная классификация каждого предложения продакта

До изменения текста отнеси предложение к одной или нескольким категориям:

- `NO CHANGE` — уже покрыто ФТТ, изменение текста не требуется;
- `CLARIFIES` — уточняет существующее требование без заметного изменения scope;
- `EXPANDS SCOPE` — добавляет функцию/интеграцию/объём работ;
- `CONFLICTS` — конфликтует с принятым решением/baseline;
- `NEW PRODUCT DECISION` — требует нового продуктового выбора;
- `BUDGET IMPACT` — способно заметно изменить оценку.

Сначала покажи классификацию и кратко объясни почему. Только затем предлагай конкретную правку ФТТ.

## Правила изменения

- Не возвращай старую сущность только потому, что она есть в исходной заготовке, если baseline уже закрыл её другим механизмом.
- Для исходной хотелки используй логику `SUPPORTED / DEVELOPS / LATER / NOT REQUIRED` из `source-map.md`.
- Не переносить Charge-specific domain functions в Cloud.
- Не превращать ФТТ в детальное ТЗ: SQL-схемы, классы, конкретные endpoints, внутренние библиотеки и иные implementation details добавляются только когда это действительно обязательное ограничение.
- Предпочитать штатные механизмы Tibbo AggreGate и стандартные общедоступные компоненты.
- Не молча менять scope, стоимость, пользовательское поведение, RBAC, тарифную модель, Gateway boundary или комплект поставки.
- Если предложение затрагивает уже принятое решение, явно назвать конфликтующее решение/раздел и предложить, что потребуется заменить.
- Если информации недостаточно и ответ влияет на scope/budget, задать один точный вопрос.

## Особо защищаемые границы текущего baseline

- Space = tenant/root Asset; Asset tree = inventory/search/ACL, не dataflow.
- Device не живёт внутри Dashboard.
- Вычисляемые параметры = Automation + Virtual/Internal Device; отдельного formula engine нет.
- Automation command использует единый Device/Profile result; отдельного `check connection -> command` нет.
- Internal Gateway MQTT — служебный transport, не user MQTT profile.
- Gateway first-wave — PC Gateway PoC для одного Device; Store-and-Forward, embedded и hardware gateway LATER, пока владелец продукта не изменил P-003.
- Dashboard — role-oriented АРМ; per-widget RBAC первой версии не требуется.
- Effective access = entitlement/license AND backend RBAC.
- Full software contour выше ОС проектирует/автоматизирует подрядчик.
- 12 месяцев опытной эксплуатации — активный этап проекта, не гарантийная оговорка.

## Product inputs, которые действительно остаются открыты

- P-001: точные SKU первой очереди;
- P-002: конкретный MQTT device/protocol;
- P-003: подтверждение Gateway first-wave scope;
- P-004: обязательность типового отчёта по моточасам.

Остальные implementation choices из open questions baseline относятся к этапу ТЗ и сами по себе не требуют переписывать ФТТ.
