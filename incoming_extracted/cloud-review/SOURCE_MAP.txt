SOURCE MAP — исходные продуктовые требования → текущий ФТТ RatioT.Cloud

Назначение файла — помогать при review быстро отвечать на вопрос: где и каким образом идея из исходной продуктовой заготовки Марко отражена в текущем ФТТ.

Карта не заменяет ФТТ и не является дополнительным перечнем требований.

Классификация

-   SUPPORTED — требование исходной заготовки сохранено по смыслу.
-   DEVELOPS — исходная идея сохранена, но конкретизирована или реализована более общей моделью.
-   OWNER INPUT — окончательная граница сознательно вынесена в раздел 2 ФТТ.
-   LATER / OUT — идея исходника сознательно не входит в первую поставку.
-   NOT REQUIRED — конкретная исходная форма требования не переносится, потому что задача закрывается другой моделью либо не требуется текущему продукту.

13. Сквозной пользовательский сценарий технолога

Исходная заготовка содержит сценарий: регистрация → Space → добавление прибора через Wizard → проверка телеметрии → Dashboard → Alarm/Telegram → выдача доступа оператору.

В текущем ФТТ эта линия разложена в проверяемые end-to-end сценарии раздела 30:

-   30.1 — регистрация и простой старт;
-   30.2 — Dashboard технолога/оператора;
-   30.3 — Alarm и Notification;
-   30.4–30.5 — Automation;
-   30.6 — Программный прототип Шлюза;
-   30.7 — RBAC;
-   30.8 — Integrator Workspace;
-   30.9–30.11 — эксплуатационные сценарии backup/update/licensing.

Классификация: SUPPORTED / DEVELOPS.

14. Ключевые осознанные изменения границы относительно исходной продуктовой заготовки

Эти пункты особенно полезно проверять при review, потому что здесь текущий ФТТ не является буквальным переносом исходника.

1.  Gateway: Store-and-Forward, embedded-agent и серийные аппаратные Шлюзы — LATER; текущая поставка содержит программный прототип. Окончательная граница подтверждается в 2.3.
2.  MQTT: первая версия не обещает совместимость с произвольным MQTT-оборудованием; конкретный сторонний протокол задаётся в 2.2.
3.  OPC UA: Client/Server входят, но Methods, Historical Access и Alarms & Conditions не входят в первую версию.
4.  Моточасы: обязательность типового отчёта требует решения владельца продукта в 2.5.
5.  MAX: не входит в первую поставку; остаётся примером будущего канала.
6.  Тарифы: значения 100/500/2000/5000+ не зашиваются как обязательная тарифная сетка.
7.  Device Group / Панель настроек: отдельные ACL-сущности не создаются; задачи закрываются Asset hierarchy и Space-level permissions.
8.  Automation check-before-command: требование реализуется внутри Device/Profile execution mechanism, без отдельной пользовательской последовательности check → command.
9.  Computed Parameter: отдельный formula engine не создаётся; Automation пишет результат в Parameter Virtual/Internal Device.
10. Dashboard API: входит в общий Application API вместо отдельной параллельной API-подсистемы.

Если Андрей или Марко считают любой из этих пунктов неверной интерпретацией продукта, это должно оформляться отдельным CR-xxx в REVIEW_PROTOCOL.md.
