О методике

Настоящая методика устанавливает порядок регулярных испытаний (приёмки и тестирования) новых версий дистрибутивов ПО Ratiot SCADA, предоставленных поставщиком — ООО «Объединение Агрегейт», — и применяется при каждой регистрации новой версии по → Регламенту жизненного цикла (процесс П-2).

Основание

  • ТЗ на разработку нового продукта (служебная записка ДКС №15528_2026-1100 от 14.07.2026) — «Приёмка и тестирование новой версии дистрибутива RatioT SCADA».
  • Технические требования к приёмке и тестированию дистрибутивов ПО RatioT SCADA (редакция v1) — детальные процедуры, команды и чек-листы, на которые даны ссылки ниже.

Адресаты и задачи

Методика предназначена для специалистов, развёртывающих стенд экспертной проверки, администраторов стенда и членов экспертной группы. Задачи испытаний: воспроизвести установку, проверить устранение ранее предъявленных дефектов (бэклог), выполнить регрессионное тестирование, проверить новые функции.

Методика рассчитана на одиночный тестовый экземпляр ПО и ориентирована на экспертное развёртывание. Для промышленного внедрения параметры серверов уточняются по фактической нагрузке. Все пути и имена файлов приведены в типовом виде; фактические значения могут отличаться в зависимости от версии поставочного комплекта и параметров установки.

Требования к стенду

Операционная система

Продукт межплатформенный (Java). Для приёмки версии Windows достаточно одной 64-битной ОС из ряда: Windows 7, 10, 11, Windows Server 2016/2019/2022/2025. Для версии Linux — 64-битные ОС с поддержкой Java: Astra Linux, РЕД ОС, Alt Linux. Все команды Linux выполняются от root (или через sudo bash).

Программные требования

  • JVM: минимум Java 17 (может входить в инсталлятор или устанавливаться в ОС заранее).
  • RDBMS обязательна; поставочные комплекты включают базовый сервер БД. Внешние СУБД: MySQL, PostgreSQL, Tantor, Microsoft SQL Server. По умолчанию для низкой/средней нагрузки — Apache Cassandra (NoSQL).
  • SMTP-сервер — только при проверке email-уведомлений о тревогах; DNS-сервер, совместимый с RFC-2136, — только при проверке динамического DNS.

Сетевые требования

Для базовой проверки открыты порты 6460 (десктоп-клиент и API), 8080/8443 (HTTP/HTTPS), 6440 (Net Admin). Дополнительно: 162/UDP — SNMP-ловушки (при проверке SNMP), 6470/6480 — взаимодействие серверов в распределённой архитектуре. Для Linux учитывать привилегированные порты <1024 (например, UDP 162). Экземпляр, лицензия и БД привязаны к конкретной установке — в протоколе развёртывания фиксируются хост, каталог установки, версия ПО, параметры лицензии и перечень открытых портов.

Порядок установки

Режимы установки

Проверяются три режима, в каждом не должно быть проблем:

  1. Графический (GUI) — по умолчанию: выбор языка и каталога (Linux — /opt/RatioT SCADA, Windows — Program Files\RatioT SCADA), выбор компонентов, БД (по умолчанию NoSQL Cassandra), завершение, проверка логов, открытие портов на МЭ.
  2. Консольный — установщик с параметром -c (преимущественно Linux): диалог выбора языка, каталога, компонентов (1-Full/2-Server/3-Web), БД (1-Cassandra/2-External SQL), портов.
  3. Скрытый (silent) — установщик с параметром -q и файлом response.varfile (создаётся автоматически при интерактивной установке в RatioT SCADA/.install4j/response.varfile; формировать на той же версии комплекта). Linux: ./installer.sh -q -varfile response.varfile; Windows: installer.exe -q -varfile response.varfile. Проверка кода возврата (%ERRORLEVEL% = 0) и логов.

Docker (при необходимости)

Образ собирается на базе установленного каталога: установка Docker → установщик RatioT SCADA → Dockerfile → docker build -t RatioT_SCADA → docker run (порты 6460, 8080, 6480; запуск через xvfb-run --auto-servernum ./ag_server -r).

Обновление с предыдущей версии

  1. Подготовка: остановка клиентов и сервера (systemctl / services.msc), полный бэкап каталога установки (tar), бэкап БД, бэкап conf/server.xml.
  2. Процесс: запуск инсталлятора новой версии → «Upgrade existing installation» → путь к существующей установке → сохранение БД и конфигурации.
  3. Проверка после обновления: версия сервера (curl http://localhost:8080/api/version — JSON с новой версией), статус БД («Schema up to date» в server.log), существующие ресурсы на месте, лицензия активна и прежняя.

Этапы испытаний

Этап 1. Тестирование установки и обновления

  • Чистая установка Windows (GUI): шаги мастера, постусловия — каталог установки, служба «RatioT SCADA Server» в services.msc, иконка в трее, лог .install4j\installation.log.
  • Чистая установка Windows (silent): код возврата 0, проверка логов.
  • Чистая установка Linux (консольная, -c) и проверка сервиса systemd (ratiot_server.service — active/running).
  • Обновление с предыдущей принятой версии (см. «Порядок установки»).

Этап 2. Проверка исправления дефектов бэклога

Поставщику направляется перечень предъявленных дефектов; если поставщик не отписался, что дефект не исправлен, — считается, что все дефекты должны быть исправлены в предоставленной версии. Результаты заносятся в таблицу регистрации:

ID багаОписаниеКритичностьСтатусКомментарий
BUG-001Краткое описаниеS2Устранён / НеудачаСборка, замечания

Этап 3. Регрессионное тестирование

Эталонное приложение. Перед циклом испытаний в предыдущей стабильной версии создаётся приложение golden_app с по одному экземпляру всех типов ресурсов (обязательный минимум — 14 позиций):

  1. виртуальное устройство virtual_test;
  2. скалярная переменная random_value (double, 0–100, обновление 10 с);
  3. табличная переменная table_settings (поля string/int/float);
  4. физическое устройство-эмулятор modbus_slave (Modbus TCP, адрес 1, регистры 40001–40010; эмулятор ModbusPal/ModRSsim2, порт 502);
  5. SNMP-устройство snmp_device (community public, OID 1.3.6.1.2.1.1.1.0);
  6. инструментальная панель regression_dashboard (сетка 3×3: надпись, кнопка, текстовое поле, линейный график, таблица данных, индикатор-лампа, SVG с анимацией, журнал событий, вложенная панель);
  7. тревога cpu_alert (порог >80 %, задержка 10 с, email);
  8. отчёт consumption_report (SQL к статистике);
  9. статистический канал stat_channel (к virtual_test, среднее, период час);
  10. модель device_model (переменная status типа string);
  11. запрос test_query (SELECT * FROM users.admin.devices.*);
  12. фильтр событий error_filter (маска контекста .devices., уровень ошибки);
  13. учётная запись testuser (роль operator);
  14. приложение golden_app, включающее всё перечисленное.

Результат упаковывается (golden_app.jar + полный дамп БД) и сохраняется в хранилище тестовых артефактов. Развёртывание на тестируемой версии: golden_app.jar в plugins/, в Web UI «Приложения → Импортировать → Развернуть».

Тест-кейсы регрессии выполняются по типам ресурсов: виртуальное устройство (REG-VD), Modbus (REG-MB), панель (по 9 компонентам), тревоги (REG-AL, SMTP через MailHog/smtp4dev, порт 1025), отчёты (REG-RP: PDF/Excel/печать/расписание), статистика (REG-ST), экспорт/импорт приложений (REG-EX: JAR, папка .prs, Git, зависимости), безопасность (REG-SEC). Полный чек-лист — в Приложении.

Регрессионный сценарий «Критический путь» — 15 шагов от запуска сервера до экспорта/удаления/импорта панели и остановки; выполняется не более 30 минут, критерий успеха — все шаги без ошибок.

Этап 4. Тестирование новых функций

Продукт ОЕМ: новые функции поставщика частично добавляются в дистрибутив ДКС; после релиза поставщик проводит онлайн-вебинар с демонстрацией. Для каждой значимой новой функции оформляется тест-кейс (feature_id, feature_name, version_introduced, preconditions, configuration, steps/expected) со сводной таблицей результатов (тест-кейсов / успешно / неудачно / блокирующих / готовность).

Этап 5. Дополнительные виды тестирования — только по запросу

Выполняются только при запросе ДИР, ОТП или ДПМ; если запрос не указан — не выполняются:

  • Производительность: открытие Web UI < 3 с; создание устройства < 1 с; опрос 1000 тегов ≈ 1000 тегов/с; отчёт 1000 строк < 2 с; память сервера при 1000 тегах < 1 ГБ; запуск сервера < 30 с. Протокол замеров: сценарий, количество, базовая версия, тестируемая версия, отклонение, статус.
  • Безопасность: сканирование портов (nmap 1–65535; открыты только 6440/6460/8080/8443/9042); SEC-01..06 — SQL-инъекция, XSS, доступ к API без авторизации (401), смена пароля, блокировка после 5 неудачных входов на 5 минут, HTTPS с самоподписанным сертификатом; матрица ролей admin/engineer/operator/viewer.
  • Миграция данных: старая версия → эталонное приложение с 3 месяцами истории → бэкап → обновление → сравнение (COUNT(*) из ag_events/ag_data/ag_properties до и после, целостность ссылок LEFT JOIN ag_contexts = 0 строк; db.version, устройства, история, тревоги, панели, экспорт/импорт).
  • Кросс-браузерное: Chrome 120+, Firefox 115+, Edge 120+, Opera 100+, Яндекс Браузер 26.4+ (Win/Linux); Safari 17+ (macOS — при наличии доступа).
  • Восстановление после сбоя (REC-01..06): kill -9 процесса, остановка/восстановление Cassandra, переполнение диска, обрыв и восстановление сети.

Оформление результатов

Шаблон протокола испытаний

  1. Общие сведения: продукт, версия (X.Y.Z, build), дата теста, тестировщик, платформа, окружение (тестовый стенд №X).
  2. Цель тестирования (например: «Приёмочное тестирование версии X.Y.Z перед выпуском»).
  3. Состав тестирования — перечень блоков с числом тест-кейсов и итог «Всего».
  4. Результаты — таблица: категория, количество успешных, неудачных, блокирующих тестов, процент успешных + строка ИТОГО.
  5. Критические дефекты (блокирующие выпуск): N; значительные: N; незначительные: N.
  6. Дефекты (кратко) — нумерованный список вида «1. [S2] Описание (BUG-099)».
  7. Рекомендация (например: «Релиз с задержкой — требуется исправление значительных дефектов»).
  8. Подпись и дата.

Образец заполненного протокола: → Протокол испытаний № TRiiot.26.0015.

Шаблон отчёта о дефекте

Поля отчёта: ID (BUG-NNN), Статус (OPEN), Критичность (S0–S4), Обнаружил, Дата, Версия (X.Y.Z build NNNN), Окружение (ОС, браузер, RAM), Заголовок, Описание, Шаги воспроизведения, Ожидаемый результат, Фактический результат, Приложение (скриншоты, образцы, последние 100 строк server.log), Дополнительная информация, Приоритет для исправления, Назначено («Создан запрос в Aggregate», ASD-xxxx), Планируемый срок исправления.

Идентификаторы документов

Протоколы испытаний нумеруются TRiiot.26.NNNN (реестр ведёт руководитель тестирования); дефекты — BUG-NNN; регрессионные кейсы — REG-…; безопасность — SEC-NN; восстановление — REC-NN; новые функции — FEAT-NNN. Внешние тикеты поставщика — ASD-xxxx (Jira Service Desk АГ).

Периодичность

  • Полный цикл испытаний (этапы 1–4) выполняется при каждой регистрации новой версии дистрибутива от поставщика — это и есть «регулярные испытания».
  • Подтверждающие проверки исправлений выполняются на каждой контрольной сборке поставщика по затронутым кейсам.
  • Этап 5 (дополнительные виды) — по отдельному запросу ДИР, ОТП или ДПМ; без запроса не выполняется.
  • Результат каждого цикла — протокол с номером TRiiot.26.NNNN, опубликованный на портале в разделе «Испытания».

Быстрые команды проверки стенда
